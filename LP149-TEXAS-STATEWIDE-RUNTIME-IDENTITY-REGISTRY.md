# LP149 — Texas Statewide Runtime Identity and Operational Registry Expansion

LP149 adds a deterministic runtime identity registry for all Texas counties while preserving the governed LP138 operational activation boundary.

## Authoritative inputs

LP149 consumes only existing certified artifacts:

- LP137/LP148 statewide geometry source and runtime package recognition via `assets/location-resolution/gridly-authoritative-texas-county-geometry-v1.manifest.json`.
- LP138 operational membership via `evidence/lp138/county-geometry-membership-contract.baseline.json`.
- LP140 activation planner invariance through explicit registry validation fields; LP149 does not import or alter planner logic.
- LP147 production Storage verification artifacts remain read-only and unmodified.

No geometry, package, or certificate artifact is regenerated by LP149.

## Runtime identity model

Each county identity in `data/lp149/runtime-county-registry.json` includes:

- `countyName`
- `countyId`
- `fips`
- `runtimeGeometry.present`
- `runtimeGeometry.packageVersion`
- `packageIdentity.packagePath`
- `packageIdentity.packageSha256`
- `certificateAvailability.available`
- `certificateAvailability.certificateRefs`
- `operationalMembership.active`
- `operationalMembership.authority`
- `operationalReadinessClassification`

The registry is sorted by ascending numeric FIPS and contains 254 unique Texas county identities.

## Identity versus membership

LP149 makes identity and operational membership independent concepts:

- A county may be known to runtime identity systems because it is represented by the LP148 statewide runtime geometry package.
- A county is operationally active only when it is part of the LP138 current operational baseline.

Identity does not authorize routing, address lookup, crossing lookup, containment selection, planner selection, deployment, Storage writes, or activation.

## Registry classifications

The registry uses these operational-readiness classifications as registry state only:

- `ACTIVE_OPERATIONAL` — the county is in the LP138 28-county operational baseline.
- `KNOWN_NOT_OPERATIONAL` — the county has LP148 geometry recognition and at least one tracked runtime certificate artifact, but is not in LP138 operational membership.
- `CERTIFICATION_BLOCKED` — the county has LP148 geometry recognition but no tracked runtime certificate artifact available to this repository.

These classifications do not authorize runtime use.

## Runtime preservation

LP149 records preservation flags in the registry boundary:

- `activationPerformed: false`
- `deploymentPerformed: false`
- `runtimeSelectionChanged: false`
- `plannerChanged: false`
- `statewideGeometryRecognizedOnly: true`

The current runtime remains the same 28 operational counties. LP149 does not change address lookup, crossing runtime, Storage retrieval, certificate validation, planner logic, activation governance, awareness, route intelligence, or protected systems.

## Validation

Run:

```bash
npm run verify:lp149
npm run test:lp149
```

Validation verifies:

- 254 unique runtime identities.
- Deterministic ascending FIPS ordering.
- No duplicate counties.
- Every LP148 geometry county is represented.
- Operational membership remains exactly 28 counties.
- No activation is performed.
- Runtime selection is unchanged.
- Planner is unchanged.
- Deployment is unchanged.
- Statewide geometry is recognized but not operationally used.

## LP148 pre-existing deterministic preflight reconciliation

The LP148 regression command `npm run test:lp148` has been independently reproduced on both authoritative `main` and the current LP149 branch. In both places, the LP148 suite passes its two builder-contract cases and fails only the existing production preflight comparison with:

```text
[LP148] tracked/generated package does not match deterministic rebuild
```

LP149 records this as a verified pre-existing baseline condition, not a regression introduced by LP149.

LP149 does not modify:

- the LP148 geometry package;
- the LP148 geometry manifest;
- the LP148 builder; or
- the LP148 tests.

LP149 consumes tracked LP148 metadata in recognition-only mode. No attempt was made to regenerate, overwrite, normalize, or repair LP148 artifacts. Investigation or repair of LP148 deterministic reproducibility is explicitly deferred to a separate milestone because it is outside LP149 scope.
