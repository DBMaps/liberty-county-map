# LP167.1 — Post-Commit Protected Artifact Identity Reconciliation

## Observed difference and root cause

Owner-side Windows validation regenerated `reports/lp167/protected-artifact-hashes.json` with only `package.json` changed. LP167 generated the governed report before its final commit, while the generator resolved every listed path from `HEAD:<path>`. The report therefore captured the pre-LP167 package blob. Once the commit added the four LP167 npm commands, `HEAD:package.json` correctly named different canonical bytes. Isolated verification runs both used the same current `HEAD`, so they agreed with each other; governed drift was exposed only when those bytes were compared with (or written over) the stale committed report.

The audit found no other LP167-owned file in the protected list. Future milestone-owned tracked files would have the same lifecycle risk if incorrectly classified as unchanged.

## Governed identity strategy

Schema `gridly.lp167.protected-artifacts.v2` separates:

- `unchangedProtectedArtifacts`: protected pre-existing files resolved fail-closed from canonical `HEAD` Git blob bytes; and
- `intentionalMilestoneChanges`: LP167-owned files, currently `package.json`, with the reason for the change and their final canonical Git identity.

Both sections use SHA-256 over Git blob content, deterministic path order, canonical LF JSON, and no filesystem-content fallback. Working-tree CRLF conversion therefore cannot alter identity. Verification remains read-only and compares two isolated generations with exact governed bytes, reporting the path, expected and actual SHA-256, and first differing byte on drift.

## Decision and execution boundary

LP167 remains `CONDITIONALLY_READY_BLOCKERS_REMAIN` with 13 blockers. Deployment, activation, app distribution, and public launch remain `NOT_AUTHORIZED`. This reconciliation performs no runtime, deployment, activation, storage, routing, awareness, notification, address, destination, crossing, or production-configuration change; `js/app.js` is unchanged.

PowerShell 5.1 owner validation must begin and end clean, run assessment, certification, verification, and tests, and confirm that repeated generation produces no report diff. This validates the post-commit and merged-main lifecycle without deploying or activating anything.
