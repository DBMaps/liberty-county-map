# LP169.2 — Windows PowerShell 5.1 Evidence Capture Compatibility

## Observed owner error and root cause

The authenticated owner ran the LP169.1 capture from the authoritative Windows environment. Windows PowerShell 5.1 rejected `-Encoding utf8NoBOM` with `Cannot bind parameter 'Encoding'` because that encoding name is not part of its cmdlet encoding enumeration. This was a script compatibility defect, not an authentication, GitHub, Supabase, or production-readiness finding. No production mutation occurred.

Replacing it with plain `-Encoding UTF8` would be insufficient: Windows PowerShell 5.1 commonly writes a UTF-8 byte-order mark for that setting. Governed JSON requires canonical UTF-8 without BOM and LF, so accepting the cmdlet default would change governed bytes.

The next authoritative run exposed a second compatibility defect at the repository Actions-secret inventory. The exact producer was `gh secret list --repo <repository> --app actions --json name`, parsed by `ConvertFrom-Json` and then passed to `Select-Object -ExpandProperty name`. At least one returned record was not the documented `{ "name": "..." }` shape, so Windows PowerShell 5.1 stopped with `Property "name" cannot be found`. The former mixed-object pipeline also existed for environment Actions secrets, while the Supabase secret pipeline silently discarded missing names. Those behaviors could neither distinguish a schema change from an empty inventory nor safely identify the source.

The owner's following authoritative run exposed a third contract defect: `gh secret list --repo <repository> --app actions --json name` correctly returned `[]` because the repository currently has zero repository-level GitHub Actions secrets. The normalizer rejected every zero-record inventory, so it misclassified this valid observation as an invalid schema. A parsed empty JSON array is valid inventory evidence; it is not evidence that any required secret is present and it does not establish readiness.

The subsequent owner validation exposed the recurring Windows PowerShell 5.1 cardinality defect: a pipeline can assign zero results as `$null`, one as a scalar, and many as an array. Strict mode then rejected `.Count` on the scalar inside `Get-NormalizedInventoryNames`. This was not isolated to the reported line: every command, JSON conversion, and `Where-Object`, `ForEach-Object`, and `Select-Object` result in the capture script required a full scalar/array audit before another production capture could be requested.

The fourth owner-observed defect was a `CommandNotFoundException` where the blank-output matrix expected `LP169InventoryBlankOutput`. The rejection path was reached, but its nested diagnostic helper used `New-Object System.ArgumentException($Message)` and `New-Object System.Management.Automation.ErrorRecord(...)`. That is not Windows PowerShell 5.1 `New-Object` constructor syntax: PowerShell interpreted the parenthesized type/expression as command syntax and failed before it could create the governed error record. The defect was therefore in diagnostic construction, not in the blank-output classifier.

The fifth owner-observed compatibility failure was `Direct diagnostic construction lost its governed identifier.` Although the fourth correction changed both diagnostic objects to `New-Object -TypeName ... -ArgumentList`, Windows PowerShell 5.1's `ArgumentList` binding and array-enumeration behavior still made that constructor path unreliable: the terminating error did not consistently retain the supplied governed identifier.

The remaining `New-Object` constructor path has therefore been removed completely. `Stop-InventoryNormalization` uses the Windows PowerShell 5.1-supported direct constructors `[System.ArgumentException]::new($Message)` and `[System.Management.Automation.ErrorRecord]::new(...)`. It remains an advanced function with its own local `$PSCmdlet`, passes the safe source classification as `TargetObject`, and calls `ThrowTerminatingError` exactly once. The matrix's direct-construction failure now displays only the actual `FullyQualifiedErrorId` and exception type, never production or captured inventory values.

## Full-file cardinality audit and stable return contract

The completed full-file search finds five `.Count` expressions and no `.Length` expressions. All five are now definitely array-safe:

* `WrapperMatches.Count` (two expressions) follows `$WrapperMatches = @( ... Where-Object ... )`.
* `Records.Count` follows the explicit declaration `[object[]]$Records = @()` and every later assignment uses `@(...)`.
* `Supported.Count` (two expressions) follows `$Supported = @( ... Where-Object ... )`.

The unsafe pre-correction assumption was `Records.Count` after a conditional assignment whose `[]`, singleton, and multi-record paths were not held to an explicit typed-array contract. It is corrected. No string uses `.Count` or `.Length`; blank raw command output uses `[string]::IsNullOrWhiteSpace`. All other variable-cardinality pipelines in the capture are either captured directly inside `@(...)`, assigned to a typed `Object[]`, consumed without a cardinality property, or serialized through `ConvertTo-Json -InputObject`.

The normalizer now checks the raw JSON root before record normalization. Blank, whitespace, literal `null`, scalar roots, and unsupported objects are distinct failures; `[]` remains distinct from all of them. An object root is accepted only as an explicitly named wrapper whose value is itself a JSON array. Only after root validation does `[object[]]$Records` receive `@($Parsed)` or `@($WrappedRecords)`. This prevents pipeline enumeration from changing the command contract.

Every valid return is an explicit `Object[]`. Empty output uses `return ,([object[]]@())`; nonempty output is sorted and deduplicated into `[object[]]$NormalizedNames` and returned with `return ,$NormalizedNames`. Each secret-inventory call site assigns that result to its own `[object[]]` variable and uses an explicit `foreach` to build safe records. Zero, one, and many results therefore do not depend on incidental pipeline wrapping.

The repository static regression rejects a parenthesized pipeline followed by `.Count`, `(ConvertFrom-Json ...).Count`/`.Length`, raw-text cardinality properties, or any new `.Count` receiver not explicitly audited. Its allow-list is deliberately limited to the three normalized array variables above, so legitimate explicit arrays remain possible without permitting an unaudited scalar assumption.

## Complete strict-mode regression matrix

`tests/lp169/inventory-normalization.ps1` runs under `Set-StrictMode -Version Latest` and covers: (1) blank text, (2) whitespace, (3) JSON `null`, (4) `[]`, (5) `[{}]`, (6) one valid record, (7) multiple valid records, (8) a string scalar, (9) a numeric scalar, (10) an unsupported wrapper, (11) a mixed valid/invalid array, (12) conflicting properties, (13) one normalized result, (14) zero normalized results, and (15) multiple normalized results. It additionally covers malformed JSON, empty-without-opt-in, valid explicit wrappers, null wrapper values, and scalar wrapper values.

Valid zero, one, and many returns are asserted to have exact runtime type `System.Object[]`; `.Count` is exercised for every valid cardinality. Deterministic sorting/deduplication is asserted. Every invalid family must produce a governed source/schema diagnostic, must not raise `PropertyNotFoundException`, and must not reveal the supplied captured marker. A mixed array is rejected as a whole.

The thirteen governed rejection cases now also require a fully qualified error identifier beginning with the expected LP169 identifier, exact exception type `System.ArgumentException`, and explicit exclusion of both `CommandNotFoundException` and `PropertyNotFoundException`. A separate direct diagnostic-construction case invokes `Stop-InventoryNormalization` outside its parent function. It proves both the PowerShell 5.1 constructor path and local advanced-function ownership of `$PSCmdlet` before any JSON classification is involved. The valid matrix continues to prove explicit `System.Object[]` results for zero, one, and many records, deterministic sorting/deduplication, and wrapper acceptance only when explicitly permitted.

Another owner production run was intentionally withheld while this audit and matrix were incomplete. The repository matrix is wired to run with `powershell.exe` on Windows; this implementation environment does not provide that executable, so the authoritative Windows matrix result remains pending rather than being represented by a non-Windows substitute. The owner must not rerun capture unless the complete matrix prints `inventory normalization regression tests passed` on Windows PowerShell 5.1.

### Durable diagnostic contract

The previous matrix treated `Exception.Message` as both the machine-readable
classification and the human-readable safety diagnostic. Its generic failure at
line 28 discarded the caught error's type and `FullyQualifiedErrorId`, so it
could not distinguish an intended normalizer rejection from PowerShell wrapping,
parameter binding, or another premature failure. The matrix now captures the
caught `ErrorRecord` first and, outside the `try`/`catch`, inspects
`FullyQualifiedErrorId` and `Exception.Message` separately. The identifier's
first comma-delimited component is the governed identifier; Windows PowerShell
may append command context to the fully qualified value.

`Get-NormalizedInventoryNames` now creates an explicit
`System.Management.Automation.ErrorRecord` with category `InvalidData` and one
of these identifiers:

* `LP169InventoryBlankOutput`
* `LP169InventoryNullOutput`
* `LP169InventoryMalformedJson`
* `LP169InventoryScalarRoot`
* `LP169InventorySchemaMismatch`
* `LP169InventoryAmbiguousProperty`
* `LP169InventoryEmptyNotAllowed`

Every governed message independently retains the source-command label, expected
record-property names, and observed property names only. Matrix assertions prove
the identifier and each safe message component, and check every supplied marker
value—including values from otherwise-valid records in an atomically rejected
mixed array—is absent. The matrix never prints an exception message or captured
inventory material.

## Implementation

The capture now constructs `System.Text.UTF8Encoding` through `[System.Text.UTF8Encoding]::new($false)`, which is supported by Windows PowerShell 5.1 and explicitly disables the BOM. The complete constructor audit replaced the former UTF-8, `System.ArgumentException`, and `System.Management.Automation.ErrorRecord` `New-Object` sites with direct .NET constructors. The capture script now enforces a zero-`New-Object` rule. Other construction uses compatible static .NET methods, including `[Guid]::NewGuid()`, `[System.IO.Path]::GetFullPath/GetFileName()`, and `[System.IO.File]::WriteAllText()`. The only `ErrorRecord` and exception construction occurs inside the advanced diagnostic helper, and the only `$PSCmdlet` use is that helper's local `ThrowTerminatingError` call. `System.IO.File.WriteAllText` writes canonicalized LF content to a unique same-directory temporary file. Capture occurs in a unique staging directory; only a fully successful bundle is moved to the review path. An existing bundle is backed up during the final swap, restored if publication fails, and temporary paths are removed in `finally` blocks.

Every JSON artifact and the database JSONL artifact uses that one writer. No `Set-Content`, `Out-File`, `Add-Content`, redirection, default text encoding, PowerShell 7-only `utf8NoBOM` enum, or PowerShell 7-only constructor syntax remains in the output path. Repeated equivalent content therefore has byte-identical UTF-8-no-BOM and LF representation.

## Command shims and fail-closed execution

Authenticated `gh` and `supabase` commands are invoked by command name with PowerShell's call operator. Applications, aliases, functions, and session shims—including an owner function that delegates to `npx.cmd --yes supabase`—are accepted without an Application-only `Get-Command` restriction. Before each capture the native exit status is reset, and a nonzero result terminates capture without publishing captured output.

`Get-NormalizedInventoryNames` now governs the Supabase secret-name, GitHub repository Actions-secret, and GitHub environment Actions-secret result families. Each call supplies its source-command label, exact allowed schema (`name`), and an explicit empty-inventory policy. The helper validates and parses the captured JSON text itself, preserving the difference between a successfully parsed `[]` and blank, null, or unparseable command output. It reads only properties found through `PSObject.Properties`, accepts non-empty string names, trims them, and returns deterministically sorted unique names. It can unwrap only a wrapper property explicitly allowed by its caller; none of these three current command contracts permits a wrapper.

GitHub repository Actions secrets, GitHub environment Actions secrets, and Supabase secrets each opt in with `-AllowEmpty`: zero secrets is a valid observed state for all three list commands. Their safe capture artifacts contain `[]`, so governed inventory count is zero and every required secret is still evaluated individually as `ABSENT` or `OWNER_ACTION_REQUIRED`. No `PASS`, presence, or readiness is inferred from an empty inventory. Supabase uses the same explicit policy because an initialized project can validly have zero configured secrets; its governed required-secret checks remain fail-closed.

An empty array without caller opt-in, blank stdout, JSON `null`, unparseable JSON, scalars, primitive records, missing supported properties, multiple supported properties, non-string names, blank names, and multiple allowed wrappers terminate the entire staged capture. Blank and null output classify as `SOURCE_UNAVAILABLE`; a parse failure classifies as `CAPTURE_FAILED`. The error identifies the source command, expected property names, and observed property names only, and never prints captured values. Because publication happens only after all normalization and writes succeed, a mixed valid/invalid array cannot publish partial evidence.

## Safety preservation

The existing field projections remain narrow: secret presence names/statuses and metadata are captured, never credential values. A pre-write safety boundary rejects JWT-like strings, bearer or authorization material, private keys, database connection strings, Supabase secret/service tokens, and cookies. Rejection messages never repeat captured material. The governed evidence ingester remains the final strict sanitizer.

All remote commands remain metadata reads: project, secret-name, function, repository, workflow, permissions, environment, database catalog, aggregate, and storage metadata inspection. The patch does not run a migration, deployment, upload, policy change, storage write, county activation, runtime change, or public launch.

## Exact authoritative Windows validation procedure

From a clean checkout on the LP169.2 branch, in the already-authenticated **Windows PowerShell 5.1** owner session:

```powershell
$PSVersionTable.PSVersion
git status --short
Get-Command gh
Get-Command supabase

$ProjectRef = '<20-character-project-reference>'
$Repository = 'DBMaps/<repository-name>'
$ReviewDirectory = Join-Path $env:TEMP 'gridly-lp169-owner-review'

& .\tools\lp169\capture-owner-production-evidence.ps1 `
  -ProjectRef $ProjectRef `
  -Repository $Repository `
  -ReviewDirectory $ReviewDirectory

# The capture must complete without a schema-normalization exception. If it
# reports observed property names, stop and retain no evidence from that run.
# Do not paste the command output or any captured values into the repository.
# A secret-name file containing [] is successful zero-inventory evidence. It
# must produce count 0 and missing-secret statuses, never PASS or readiness.

Get-ChildItem $ReviewDirectory -File | Sort-Object Name |
  ForEach-Object {
    $bytes = [System.IO.File]::ReadAllBytes($_.FullName)
    if ($bytes.Length -ge 3 -and $bytes[0] -eq 0xEF -and $bytes[1] -eq 0xBB -and $bytes[2] -eq 0xBF) {
      throw "UTF-8 BOM found in $($_.Name)"
    }
    $strictUtf8 = [System.Text.UTF8Encoding]::new($false, $true)
    $text = $strictUtf8.GetString($bytes)
    if ($text.Contains("`r")) { throw "Non-LF newline found in $($_.Name)" }
    [pscustomobject]@{ Name = $_.Name; Sha256 = (Get-FileHash $_.FullName -Algorithm SHA256).Hash.ToLower() }
  }

npm run audit:lp169
npm run certify:lp169
npm run verify:lp169
npm run test:lp169
npm run test:lp168
npm run test:lp167
git diff --exit-code -- js/app.js
git diff --exit-code -- reports/lp162 reports/lp163 reports/lp164 reports/lp165 reports/lp166 reports/lp167 reports/lp168
git diff --check
git status --short
```

Review the temporary bundle without copying it into the repository. Create only the schema-v2, owner-reviewed draft described by `evidence/lp169/README.md`, then invoke its governed ingester. Do not paste authentication status, tokens, passwords, connection strings, headers, or raw command output into evidence or documentation.
