# LP188.11C protected-environment provisioning and owner handoff

## Decision and discovered infrastructure

LP183.7 proves that the owner created the **`gridly-preview` Cloudflare Pages project**, deployed one immutable preview (`458fa7f4-ba68-44c7-82ea-c5e6475e456e`), bound **`preview.gridlygo.com`**, and preserved the Access application **`preview`** with policy **`Gridly Preview Approved Testers`**. Approved-user admission, anonymous denial, device validation, production isolation, and removal of the temporary deployment token were recorded. The existing project, hostname, and Access application are therefore reusable; duplicate infrastructure is neither needed nor authorized.

The existing deployment is not reusable as the LP188.11C deployment. Its 493-file LP183 artifact predates the LP188.3 packages and does not prove either the 215 `counties/{FIPS}.json` objects or `gridly-protected-build-identity.json`. Its Access evidence proves email/OTP allowlisting, not a service-token policy. A new, narrowly scoped Direct Upload to the existing project and a new service-token Include policy are required. This is not a production deployment or activation.

The selected environment is `OWNER_CONTROLLED_PROTECTED_NON_PRODUCTION` at `https://preview.gridlygo.com`. The contracts are:

* root: `https://preview.gridlygo.com/`;
* identity: `https://preview.gridlygo.com/gridly-protected-build-identity.json`;
* packages: `https://preview.gridlygo.com/counties/{FIPS}.json`.

The repository does not contain the LP188.3 package byte directory used for LP188.5 capture. It contains the authoritative FIPS, byte length, schema, and SHA-256 inventory. The staging command therefore accepts an owner-local source directory, verifies every byte sequence against LP188.5, and copies bytes without parsing, normalization, or rewriting. It stops on any mismatch. After all owner bytes pass, the command invokes the existing LP183.1 deterministic stager to materialize the canonical tracked Gridly browser runtime, then adds the exact packages, protected build-identity document, and cohort manifest. The protected files are additive; they no longer replace `index.html` with a validation shell. The 215 files are small JSON objects; LP183.2/LP183.3 already resolved the earlier Pages 25 MiB per-file issue, and the LP188.5 inventory shows no comparable package-size constraint.

The first LP188.11C upload accidentally contained only a static root validation shell plus the protected artifacts. The resulting Wave 0 timeout was therefore `PRECONDITION/HARNESS_ENVIRONMENT_FAILURE`, not a product regression. The corrective upload below rematerializes the intended governed bundle with the already-governed release ID and package-cohort build identity; the owner must separately retain the new Cloudflare provider deployment ID as redeployment reconciliation evidence.

## Immutable identities

`GRIDLY_PROTECTED_BUILD_IDENTITY` is the deterministic `sha256:` digest of the canonical 215-entry protected-cohort manifest. The current computed value is recorded in `reports/lp18811c/protected-environment-provisioning.json`; the staging tool computes it rather than asking the owner to invent it.

The original staging required a unique immutable release identifier (for example, a UUID prefixed with `lp18811c-`) passed as `--deployment-id`; values such as `latest`, `current`, and `preview` remain rejected. This release identifier is written into the exact three-field identity-document schema required by LP188.11B. The corrective procedure below explicitly preserves the already-governed release and package-cohort build identities while replacing the incomplete shell upload with the intended runtime bundle. The owner must reconcile and retain Cloudflare's newly returned immutable provider deployment ID/URL separately. Any later deployment outside this bounded corrective repair requires a new governed release identifier and must not silently reuse this identity.

## Exact owner provisioning procedure

Perform these actions only in the owner-controlled Cloudflare account. Do not commit the local source, staged directory, Wrangler output, service-token values, or executor evidence containing personal data.

1. Check out this commit, run `npm ci`, materialize the deterministic runtime package with `npm run build:lp1833`, and confirm `npm run verify:lp18811c` and `npm run test:lp18811c` pass.
2. Locate the owner-local LP188.3 package root whose child path is `counties/48001.json` and whose bytes produced LP188.5. Do not regenerate it.
3. For this corrective redeployment only, reuse the existing governed LP188.11C release identifier and stage the corrected bundle:

   ```powershell
   $releaseId = 'lp18811c-c5cc6370-412c-487e-b3d3-3ff8350b6f98'
   node .\tools\lp18811\provision-protected-environment.mjs stage --source $env:GRIDLY_LP1883_PACKAGE_ROOT --output .\.artifacts\lp18811c\cloudflare-pages --deployment-id $releaseId
   ```

4. Re-run the staging command into a second temporary directory and compare all file hashes. Stop if any LP188.5 check or comparison fails.
5. In Cloudflare Zero Trust, open **Access > Applications > preview**. Preserve the existing approved-tester policy. Create a service token named for this LP188.11C release, then add a narrowly scoped **Service Auth / Include Service Token** policy for that token to the same `preview.gridlygo.com` application. Do not add Bypass, Everyone, or public access. Set the shortest practical expiration and retain the ID/secret only in the owner's secret manager.
6. Confirm the staged `index.html` contains `gridlyWelcomeCountySelect`, `js/app.js` contains `data-gridly-active-county-fips`, and both protected JSON documents and all 215 county files are present. Then direct-upload only the staged directory to the existing project (never `gridlygo.com`):

   ```powershell
   npx wrangler pages deploy .\.artifacts\lp18811c\cloudflare-pages --project-name gridly-preview --branch preview --commit-dirty=true
   ```

7. Capture Cloudflare's immutable deployment ID and URL locally. Verify the deployment is the single intended upload, the custom hostname remains protected, and production is unchanged. Set `$releaseId` to the exact value used during staging; do not substitute the Cloudflare ID for it after bytes have been uploaded. In this contract, `GRIDLY_PROTECTED_DEPLOYMENT_ID` is the immutable governed release ID in the deployed identity document; Cloudflare's provider ID is separately retained reconciliation evidence.
8. Through the Access service token, GET the identity URL and several package URLs. Confirm no redirects, the three identity fields match, and downloaded SHA-256 values match LP188.5. Revoke/withdraw on any mismatch.
9. Select a portable, non-secret executor reference such as a governed owner-local evidence record ID. It identifies the operator/workload and retained attestation; it is not an email address, token, cookie, or secret.
10. Load all values from the owner secret manager into the current PowerShell process (the secret lines below refer to secret-manager lookups, not literal examples):

   ```powershell
   $env:GRIDLY_PROTECTED_URL = 'https://preview.gridlygo.com'
   $env:GRIDLY_PROTECTED_DEPLOYMENT_ID = $releaseId
   $env:GRIDLY_PROTECTED_BUILD_IDENTITY = (Get-Content -Raw '.\reports\lp18811c\protected-environment-provisioning.json' | ConvertFrom-Json).selectedEnvironment.buildIdentity
   $env:GRIDLY_VALIDATOR_ACCESS_CLIENT_ID = (Get-Secret 'gridly/lp18811c/access-client-id' -AsPlainText)
   $env:GRIDLY_VALIDATOR_ACCESS_CLIENT_SECRET = (Get-Secret 'gridly/lp18811c/access-client-secret' -AsPlainText)
   $env:GRIDLY_EXECUTOR_IDENTITY_REFERENCE = 'owner-evidence://lp18811c/executor/<owner-assigned-record-id>'
   ```

11. Confirm all six variables are nonempty. Only then run the real repository-relative adapter:

   ```powershell
   Set-Location C:\GitHub\liberty-county-map
   powershell.exe -NoProfile -ExecutionPolicy Bypass `
     -File .\tools\lp18811\invoke-owner-validation.ps1
   ```

12. Remove the six process variables, revoke the service token after the validation window, and preserve only sanitized evidence. Independent review, owner consumer/telemetry/rollback/operational observations, and evidence ingestion remain separate.
