# LP219.2B — Current-county visible-incident identity RCA

## Scope and accepted starting evidence

Owner browser acceptance for LP219.2A in Town of Pecos / Reeves County established a Location Context production and DOM count of **3**, with parity, and `currentVisibleIncidentCount` as the sole winning operand. Its value comes from `gridlyGetCurrentCountyVisibleIncidentAudit(activeCountyId).currentVisibleReportCount`. This supersedes the deterministic LP219.2 hypothesis that `counts.activeIssueCount` directly won reconciliation.

The governed LP219 view contains two active records, while the production visible-report scalar is three. LP219.2B adds read-only identity instrumentation; it does not claim a new browser observation. The exact final live RCA remains pending the owner replay described below.

## Complete production trace

`gridlyGetCurrentCountyVisibleIncidentAudit` constructs `reportInventory` by concatenating, in order:

1. every row in the global `activeHazards` array;
2. every row in the global `activeReports` array.

`currentVisibleReports` applies exactly one inclusion predicate: `gridlyReportMatchesActiveCounty(item, normalizedCountyId)`. `currentVisibleReportCount` is exactly `currentVisibleReports.length`. The scalar does not come from `getUnifiedIncidents`; that separately filtered collection supplies `currentVisibleIncidentCount` and the parity lineage only.

### Filter matrix

| Concern | Count behavior |
|---|---|
| County | Included only when `gridlyReportMatchesActiveCounty` matches the normalized active county. |
| Community/geography | Whatever county inference is embedded in that matcher; there is no additional community/place or viewport test here. |
| Visibility | Membership in the two runtime “active” registries plus county match; no DOM, marker, viewport, hidden-state, or surface-policy test. |
| Reportability | Not tested. |
| Lifecycle / active | Not tested. |
| Cleared / inactive | Not filtered. |
| Stale | Not filtered. |
| Duplicate | Not filtered. |
| Source type | Not filtered after the two source arrays are selected. |
| Generated incidents | Not directly included unless also retained in one of the two arrays. |
| Community reports | Included when present in `activeReports` and county-matched. |
| Active hazards | Included when present in `activeHazards` and county-matched. |
| DriveTexas | Not directly included from `window.__gridlyDriveTexasAlerts`. |
| Crossing reports | Included when represented in `activeReports` and county-matched. |
| Retained history | Included when it remains in either source array and county-matches. |

Therefore “visible” in this function means **present in the active-hazard/active-report map/report inventory for the current county**. It does not automatically mean lifecycle-active, rendered as a marker, inside the viewport, reportable to a surface, or visible in the DOM.

## Instrumentation and reconciliation

The source function now produces a bounded audit (maximum 100 projected rows total across included and excluded items) containing the count, safe item projections, identities, source/lifecycle breakdowns, county and generation, filter-stage cardinalities, exclusions, duplicate IDs, stale IDs, and inactive-history IDs. Full provider payloads are never returned. Stable production/governed IDs are matched before classification; labels are not used as identity.

Classifications are `MATCHED_GOVERNED_ACTIVE`, `MATCHED_INACTIVE_HISTORY`, `MATCHED_STALE`, `MATCHED_DUPLICATE`, `MATCHED_NON_ACTIVE_PROJECTION`, `UNMATCHED_REAL_INCIDENT`, and `IDENTITY_UNAVAILABLE`.

The `currentVisibleIncidentCount` reconciliation candidate now carries these projected rows into LP219.2A invocation capture. Consequently a winning event can expose all three `winningCollectionIdentities` and its contributor identities without a custom console script. `window.gridlyLocationContextProductionAudit()` embeds `currentVisibleIncidentAudit`; `window.gridlyCurrentCountyVisibleIncidentAudit()` exposes the source audit directly.

## Count contract and LP214 relationship

Implementation evidence supports contract **B: map/report visibility count**, more precisely current-county runtime report-inventory membership. It is not an active-issue lifecycle count and not merely a diagnostic parity count. It is broader incident presence only within the two selected registries, rather than all possible incident providers.

LP214 nevertheless permits this scalar to participate in the active-issue `Math.max` reconciliation. LP219.2A proved it wins live for Pecos. LP219.2B leaves that relationship and every return value unchanged; whether to lifecycle-filter the source or remove/change this operand is the next repair boundary.
