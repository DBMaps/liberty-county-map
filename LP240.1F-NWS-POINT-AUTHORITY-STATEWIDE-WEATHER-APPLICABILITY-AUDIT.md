# LP240.1F — NWS point authority / statewide Weather applicability audit

**Audit date:** 2026-08-26

**Disposition:** `POINT_AUTHORITY_READY_FOR_BOUNDED_WEATHER_INTEGRATION`
**Scope:** audit-only. Weather remains disabled; no polling, publication, presentation, geography, identity, coordinate, provider, connector, statewide-feed, Alerts, LP236, or KBYG behavior changed.

The bounded claim supported by this audit is **“Official NWS alerts applying at your selected Gridly awareness point.”** A point result does **not** establish that every part of a municipality or community is covered. Suitable copy is “Heat Advisory affecting your area” or “Heat Advisory for your Dayton area”; “All of Dayton is under…” requires stronger boundary evidence.

## 1. NWS point API capability map

The current NWS API is a government source. Its [API documentation](https://www.weather.gov/documentation/services-web-api) requires an identifying `User-Agent`, describes JSON-LD/GeoJSON responses, cache headers and common error behavior, and links the live [OpenAPI contract](https://api.weather.gov/openapi.json). Gridly should request GeoJSON/JSON-LD, validate the documented shape rather than merely HTTP status, honor response cache headers, and fail closed on transport error, timeout, non-2xx, `application/problem+json`, parse failure, or schema mismatch.

| Resource | Successful response and useful authority | Empty/failure semantics | Cache/request role |
|---|---|---|---|
| `GET /points/{lat},{lon}` | GeoJSON `Feature`; `properties` includes `cwa`, `forecastOffice`, `gridId`, `gridX`, `gridY`, `forecast`, `forecastHourly`, `forecastGridData`, `observationStations`, `forecastZone`, `county`, `fireWeatherZone`, `timeZone`, `radarStation`, and relative location. These are NWS routing metadata for that point, not a community boundary. | A valid point produces metadata. Invalid/out-of-domain points and unavailable grid mapping return a problem response/non-success; absence cannot prove alert quiet. | Long-lived metadata cache; respect `Cache-Control`/`Expires`, use conditional requests where supported, and re-resolve after a persistent 404/changed link. Recommended ceiling: 24 h with stale metadata never substituted for an alert response. |
| `GET /alerts/active?point={lat},{lon}` | GeoJSON `FeatureCollection`; each `features[]` member has provider `id`, optional geometry, and CAP-derived properties including `event`, `status`, `messageType`, `severity`, `certainty`, `urgency`, `effective`, `onset`, `expires`, `ends`, `areaDesc`, `affectedZones`, `references`, headline, description and instruction. The endpoint performs NWS applicability filtering for the point, including alerts represented by zones. | HTTP 200 plus a structurally valid, fresh `features: []` is authoritative for “NWS currently reports no active alerts applying at this point.” It is not authority for no weather risk and is not reusable after freshness expiry. Error/problem/invalid/stale data is `UNAVAILABLE`, never `QUIET`. | Selected point only. Respect response headers; operational proposal is refresh every 2–5 min with jitter/backoff, 10 min hard authority ceiling. No 2,341-point fan-out. |
| Point `forecast` link | GeoJSON `Feature`; `properties.periods[]` includes `number`, `name`, `startTime`, `endTime`, `isDaytime`, `temperature`, `temperatureUnit`, `temperatureTrend`, `probabilityOfPrecipitation`, `windSpeed`, `windDirection`, `icon`, `shortForecast`, and `detailedForecast`. | An empty/malformed periods list is not a usable forecast and says nothing about alerts. Forecast failures do not negate a separately successful point-alert query. | Follow the link supplied by `/points`; respect cache headers, normally refresh about hourly or when its expiry demands. |
| Point `forecastHourly` link | Same forecast `Feature`/period schema, with hourly periods and normally an empty or less-useful `detailedForecast`. | Same fail-closed forecast semantics; it is forecast awareness, not official-alert evidence. | About 30–60 min, response-header led. Fetch only for the selected point when used. |
| Point `forecastGridData` link | Gridpoint GeoJSON `Feature`; properties are value-series objects with `uom` and `values[{validTime,value}]`. Relevant series include `temperature`, `apparentTemperature`, `relativeHumidity`, `probabilityOfPrecipitation`, `quantitativePrecipitation`, `windSpeed`, `windDirection`, `windGust`, `weather`, and `hazards` (availability/value density varies). | Missing series/value intervals remain unknown, not zero. Hazard grid values are forecast guidance and must not be promoted to active CAP alert identity. | About 30–60 min or response-header led; larger and more complex than period forecast, so defer unless the product uses the data. |
| Point `observationStations` link | GeoJSON `FeatureCollection` of stations considered appropriate for the gridpoint. Station features expose station ID/name/location and observation links; `/stations/{stationId}/observations/latest` returns an observation `Feature`. | Empty stations, stale latest observation, missing sensor values, or station failure means observation unavailable; it does not affect alert authority. List order is an NWS suitability list, not proof the first station lies inside the selected community. | Cache station list for 24 h; selected station observation about every 5–10 min, cache-header led, with timestamp/staleness exposed. |

NWS documentation notes that rate limits are not published as a fixed quota and that excessive requests can be blocked. Therefore the safe contract is identifying `User-Agent`, cache-header compliance, conditional reuse, bounded concurrency, jitter, exponential backoff, and no statewide point sweep.

## 4. `ACTIVE` / `QUIET` / `UNAVAILABLE` contract

`ACTIVE` requires: supported eligible identity; valid governed point; request attempted and successful; valid fresh FeatureCollection; and `features.length > 0`. `QUIET` requires every same condition and `features.length === 0`. This follows the active-alert collection/filter contract: an empty collection is a successful evaluation with no matching active features. It proves only point-alert quiet at fetch time.

`UNAVAILABLE` is mandatory for unsupported/ineligible identity, missing/invalid coordinate, required request not attempted, failure/non-2xx/problem response, invalid schema, explicit inability to evaluate, future-dated fetch time, or a success older than the authority ceiling. Stored/cached emptiness without a successful fresh query never proves quiet. Suggested reason codes are `UNSUPPORTED_IDENTITY`, `INVALID_GOVERNED_COORDINATE`, `REQUEST_NOT_ATTEMPTED`, `REQUEST_FAILED`, `INVALID_RESPONSE_SCHEMA`, `STALE_RESPONSE`, `NWS_POINT_NOT_EVALUABLE`, `CURRENT_POINT_ALERTS_RETURNED`, and `CURRENT_POINT_QUERY_RETURNED_ZERO_ALERTS`.

## 5. Point query versus Texas-wide feed

| Concern | Selected point | `area=TX` statewide feed |
|---|---|---|
| Authority role | **Primary bounded applicability authority** for current selected awareness point. | Preserve for diagnostics, broad discovery/ingestion, comparison and operational monitoring; not the first point applicability decision. |
| Request/payload | One small selected-context request; scales with active users/cache keys. | One broadly cacheable request but potentially large payload and downstream matching work. |
| Precision | NWS directly evaluates the point. | Gridly must resolve polygon/zone/county/text applicability. |
| Zone-only (`geometry:null`) | Applicable feature may still be returned; Gridly need not fetch/reconstruct the zone polygon for the point decision. | Requires zone resolution or remains unresolved; text matching is insufficient. |
| Polygon | Returned if point-applicable; raw geometry is supplemental. | Enables broad spatial discovery but requires correct intersection logic. |
| Failure | One point can be unavailable while other cached points remain independently known. | One failure blinds statewide discovery; stale feed cannot prove local quiet. |
| Deduplication | Provider ID deduplicates the same alert returned at multiple points. | Provider ID deduplicates ingestion; downstream geographic evidence still needs evaluation. |
| Cacheability | Per normalized governed coordinate/identity, short TTL; identical coordinates can share response while identities remain separate. | Highly shareable single response; payload changes frequently and must retain provider expiry/update semantics. |

Neither source should silently substitute for a failed other source. A future reconciler may compare them and surface disagreement diagnostically, but point-query success is sufficient for the bounded claim.

## 8. Alert identity contract

Use the feature’s provider-issued absolute `id` as `providerAlertId` and evidence key (optionally namespaced `NWS:<id>`). Do not hash headline/event text. Preserve `properties.messageType` (`Alert`, `Update`, `Cancel`), `status`, `sent`, `effective`, `expires`/`ends`, and `references`.

An update may arrive with a new provider ID and reference an earlier product; do not overwrite history by headline. Maintain a CAP lineage edge from each reference and let current active-query membership plus status/expiry govern currentness. The same provider ID returned for Dayton and Tarkington is one official evidence object with two applicability observations, not duplicate evidence. Removal from the active collection after cancel/expiry ends current applicability; it does not erase audit history.

Recommended future identity (not implemented): `{ provider:"NWS", providerAlertId, applicabilityMode:"NWS_POINT_QUERY" }` for evidence, plus `{ providerAlertId, awarenessKey, governedCoordinateKey, fetchedAt }` for the per-awareness applicability observation.

## 9. Forecast capability inventory

Official alerts and forecasts remain distinct. Forecast periods reliably offer temperature/unit, precipitation probability, wind speed/direction, short forecast, start/end, and (especially daily periods) detailed forecast.

| Capability | Classification | Rationale |
|---|---|---|
| start/end, temperature/unit, precipitation probability, short forecast | `HIGH_VALUE_FOR_KBYG` | Compact, time-bounded trip planning context. |
| wind speed/direction and detailed daily forecast | `HIGH_VALUE_FOR_KBYG` | Direct travel context, but keep advisory language separate. |
| hourly periods | `USEFUL_LATER` | Valuable timing detail with larger presentation/refresh cost. |
| apparent temperature, relative humidity, wind gust | `USEFUL_LATER` | Useful heat/wind context; parse unit/value intervals and tolerate gaps. |
| quantitative precipitation and structured `weather` grid | `USEFUL_LATER` | Useful but needs unit/time-series normalization. |
| grid `hazards` | `LOW_VALUE` for first KBYG | Supplemental forecast signal only; must never replace CAP alerts. |
| missing grid values treated as zero | `NOT_RELIABLE_ENOUGH` | Missing is unknown. |

## 10. Observation capability inventory

Follow the `/points` station-collection URL, retain the ordered candidates, and request `/stations/{stationId}/observations/latest` for the first responsive, sufficiently fresh appropriate candidate. Record station ID/name/coordinates and observation timestamp. A latest-observation feature can contain unit/value/quality-control objects for temperature, heat index, wind chill, relative humidity, wind speed, wind gust, visibility, precipitation (including recent interval accumulations where reported), plus text description and timestamp. Individual sensors commonly return `null`; never synthesize a value.

Station-list order is NWS gridpoint suitability, not municipal containment or guaranteed nearest straight-line distance. Gridly may calculate distance for disclosure, but must not override NWS suitability solely by distance. Use **“Nearby observation from {station name}, observed {time}”** unless the station’s actual location authority proves it is in the named place. Classification: temperature/timestamp/description `HIGH_VALUE_FOR_KBYG`; wind/gust/visibility/heat index/wind chill/humidity `USEFUL_LATER`; precipitation `USEFUL_LATER` with interval and null handling; an unlabeled claim “in Dayton” is `NOT_RELIABLE_ENOUGH`.

## 11. Cache and request strategy

1. Query only the selected/current eligible awareness identity; cancel/deprioritize a superseded selection. Never launch 2,341 simultaneous requests.
2. Normalize coordinates consistently and coalesce identical in-flight/cache keys, while retaining separate Gridly identities.
3. `/points` and station list: honor server headers, with 24 h application ceiling. Forecast/grid/hourly: headers first, target 30–60 min. Latest observation: headers first, 5–10 min. Point alerts: headers first, 2–5 min refresh with jitter; allow a successful result to prove authority for **at most 10 min**.
4. An expired active alert is filtered by provider/current-time semantics even inside a response cache. If refresh fails, prior active evidence may be labeled stale historical context internally, but the authority state is `UNAVAILABLE`; prior empty data never remains `QUIET`.
5. Use conditional requests if NWS supplies validators, bounded concurrency, exponential backoff for 429/5xx/network failure, and no retry storm. Do not use the statewide feed as an invisible fallback for point quiet.

These are conservative Gridly ceilings, not claims of fixed NWS TTLs. Actual `Cache-Control`/`Expires` wins when shorter.

## 14. Reconciliation with LP240.1A–E

- **LP240.1A:** the false-quiet repair remains valid. Point `QUIET` exists only after a fresh successful valid empty query; disabled/unattempted/failed/stale remains `UNAVAILABLE`.
- **LP240.1B:** exact PLACE geometry remains absent from current runtime. Point authority neither supplies nor claims it.
- **LP240.1C:** county geometry remains available and supplies existing county-wide presentation coordinates, but point semantics do not turn that point into whole-county coverage.
- **LP240.1D:** community radius/roadway selection remains non-authoritative for Weather. The NWS point endpoint, not Gridly’s radius/road line, decides point applicability.
- **LP240.1E:** incomplete exact PLACE-boundary recovery remains true. It is not a blocker for bounded point applicability and remains relevant to any future whole-community statement.

Thus **point authority** answers selected awareness-location applicability; **PLACE polygon authority** could later answer boundary-wide precision. Proceeding with the former does not invalidate any earlier finding or manufacture 1,859 polygons.
