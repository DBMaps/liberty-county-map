# LP241.15A — Local frozen-authority input boundary audit

## Decision

`RUNTIME_SHARD_MATERIALIZATION_BLOCKED_NODE_PARQUET_CAPABILITY_NOT_AVAILABLE`

Repository-side architecture was audited on 2026-08-29. Implementation stops
before adding a dependency, as required. The repository has no installed or
locked Node-compatible Parquet reader. Its existing Parquet path shells out to
the DuckDB CLI; `duckdb` is not available in this execution environment. That
CLI is therefore not a portable Node capability for the requested owner-local
command.

The narrowest capability to approve is a pure JavaScript, streaming-capable
Parquet reader (proposed package: `hyparquet`). No package or lockfile change was
made. Approval must include a pinned version and lockfile update before the
materializer can be implemented.

This capability stop is not evidence that the frozen authority is absent from
the owner's checkout. `/owner-local/` remains intentionally ignored, and the
Parquet must not be committed.

### Source columns and runtime projection

The frozen D.3 Parquet was produced from these columns, in this order:
`id`, `display_name`, `normalized_name`, `brand_text`, `gridly_category`,
`address_text`, `phone_text`, `website_text`, `domain_text`, `latitude`,
`longitude`, `county_fips`, `locality`, `operating_status`, `categories_text`,
and `taxonomy_text`. It already excludes `CHILD_POI` and `LIKELY_DUPLICATE`.

The certified LP241.12 runtime contract requires `id`, `displayName`,
`gridlyCategory`, `latitude`, `longitude`, `countyContextId`, and
`communityIdentity`; optional runtime fields are `brand` and an approved
`provenanceSummary`. It forbids free-form address, raw source metadata,
conflation evidence, and suppressed members.

There is an unresolved, fail-closed projection prerequisite: the frozen Parquet
does not contain the required `communityIdentity`, and repository evidence does
not certify a deterministic join from `county_fips`/`locality` to either a
`CANONICAL_PLACE` or `GOVERNED_NON_PLACE` object for every one of the 391,772
rows. Also, D.5's design-only contract names `identityDisposition` and
`provenanceSummaryAfterLegalClearance`, while LP241.12 uses the narrower record
above. The implementation must not invent either field. A release-bound,
row-conserving community-identity/provenance binding must be approved or the
runtime contract must be reconciled before materialization.

### Sharding and bytes

- One-degree shard ID:
  `tx-{floor(latitude), two digits}-{abs(floor(longitude)), three digits}`.
- Records sort lexically by `id` within each shard; shard entries sort lexically
  by shard ID.
- Historical D.3 measurement: 86 shards for the pre-D.4 projection, not a final
  runtime certification.
- Runtime cache name:
  `gridly-poi/{authorityReleaseId}/{schemaVersion}/{shardId}.json.gz`.
- Release output root:
  `poi/lp24111-d5-standalone-2026-08-28/runtime/`.
- JSON must use a fixed key order and LF separators. GZIP must use fixed headers
  (`mtime=0`) and a fixed compression level so identical records create
  identical bytes.

### Future child manifest and certification

After the two prerequisites above are approved, the child manifest should bind
the release ID, runtime schema, source path identity (never an absolute owner
path), source bytes/SHA-256/row count, tool hash, projection contract hash,
legal-manifest hash, and a lexically sorted shard list containing shard ID,
relative path, row count, byte size, and SHA-256. Certification must prove:

1. exactly 391,772 unique input IDs and exactly 391,772 output IDs;
2. no duplicate, missing, or extra ID and one shard assignment per record;
3. the legal exposure counts `355925`, `23248`, and `12599` sum to 391,772 and
   remain bound to the unchanged release/legal manifest;
4. every shard byte/hash matches the child manifest;
5. a rebuild in a separate temporary directory has identical manifest and shard
   hashes before atomically publishing the runtime directory.

Negative coverage must include missing input; byte-size/hash mismatch; row-count
mismatch; missing/wrong-type schema fields; invalid coordinates; empty or
duplicate IDs; forbidden fields; projection/community-identity failure; shard
conservation failure; legal conservation failure; mutated shard; and
non-deterministic rebuild. All failures must leave pre-existing release bytes
untouched.
