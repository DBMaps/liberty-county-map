# LP241.15B — POI community identity authority reconciliation

**Evidence date:** 2026-08-29  
**Scope:** repository-only authority audit; no row data, network, spatial classification, or runtime materialization  
**Decision:** `COMMUNITY_IDENTITY_CONTRACT_DEFECT_REQUIRES_RUNTIME_SCHEMA_RECONCILIATION`

## 1. Executive conclusion

There is no repository evidence that each of the 391,772 frozen governed POIs has
an intrinsic governed `communityIdentity`. The frozen D.3/D.5 row projection has
governed county assignment but no PLACE or governed-non-PLACE membership field.
No release-bound, POI-keyed certified lookup covers those rows. Canonical PLACE
membership artifacts govern **PLACE-to-county memberships**, not POI-to-PLACE
membership. Governed non-PLACE artifacts govern supported search/awareness
contexts and presentation anchors, not POI membership polygons.

LP241.12 put two distinct concepts into its record contract: the POI's structured
location (`countyContextId`) and the user's governed search context
(`communityIdentity`). Its own resolver searches by coordinates and radius,
including an explicitly allowed map center, and selects one-degree shards from a
radius bounding box. Its identity contract says `countyContextId` describes the
**result** while `communityIdentity` is the **search** community. Consequently a
community identity is request/diagnostic metadata when a governed community
started the search; it is not a mandatory property of every returned POI.

The exact answer for all frozen rows is therefore:

* `countyContextId` is deterministically obtained by an exact, validation-only
  lookup of frozen `county_fips` in the governed 254-county registry.
* `communityIdentity` is not derivable per POI from the frozen authority. It is
  supplied by the already-governed query origin when one exists
  (`CANONICAL_PLACE` or `GOVERNED_NON_PLACE`), and is null/absent for an allowed
  map-center/county-only query. It must not be serialized as intrinsic POI
  authority.

This conclusion needs no refetch, normalization rerun, coordinate change, county
change, fabricated GEOID, authority mutation, new authority release, or spatial
guess. Materialization remains blocked until the runtime schema is explicitly
reconciled; a Parquet reader does not cure a semantic contract defect.

## 4. `countyContextId` versus `communityIdentity`

1. **County context is mandatory for all governed POIs.** `county_fips` was
   assigned spatially during the already-frozen manufacturing chain. Its safe
   runtime transformation is an exact `county_fips` lookup in
   `data/lp104/texas-counties.json`, requiring exactly one governed county ID.
   Missing, duplicate, or unknown FIPS must fail the build; no text fallback is
   allowed.
2. **Community identity is not mandatory for all POIs.** It identifies a
   governed search/awareness origin, not necessarily the result's containing
   community.
3. **Null/absent is semantically required.** Map-center, county-only, rural, and
   unincorporated searches can have no governed named-community origin.
4. **When present, it is required only on the request/search context** and must
   already have passed the canonical PLACE or governed non-PLACE resolver.
5. **Consumer search is spatial.** Latitude/longitude choose intersecting
   one-degree shards; Haversine distance enforces the 5/10/25-mile radius. A POI
   may be returned across community or county boundaries.
6. **It is context metadata, not POI authority.** Diagnostics may report the
   request's community and county context. It must not claim the returned POI is
   a member merely because that context initiated the search.

The two fields remain deliberately separate. In particular, the result's county
does not replace a query community, and the query community does not replace the
result's county.

## 5. Canonical PLACE authority

The certified statewide registry contains 1,859 canonical PLACE identities,
2,058 PLACE-to-county memberships, and 163 multi-county identities. Those counts
certify which counties a PLACE intersects and preserve one canonical identity
across its county projections. They do **not** assign POIs to a PLACE.

LP231 establishes that the intended Census TIGER/Line 2025 PLACE polygon archive
and derived polygons are neither committed nor present, and that no browser
canonical geometry index exists. Therefore no final certified polygon artifact
is available here for a POI join. More importantly, no evidence shows that a
391,772-row POI-to-PLACE spatial join was previously executed and certified.
Recovering polygons and freshly joining frozen points would create a new
classification product/authority release and is outside this materialization.

For Austin, Abilene, Midland, Katy, and all other multi-county PLACEs, a governed
query identity alone is insufficient to describe a result location. The query
retains the one canonical PLACE identity; each result independently retains its
`countyContextId`. The existing 2,058 membership rows validate possible PLACE
county memberships, but cannot select POI membership or a containing PLACE.

## 6. Governed non-PLACE authority

The supported-awareness registry certifies 29 governed non-PLACE contexts. For
example, Tarkington has class `GOVERNED_NON_PLACE`, stable identity
`liberty-tx:tarkington`, null `placeGeoid`, a fixed presentation anchor, and a
radius. This is sufficient to originate and bound a Tarkington search. It is not
a polygon, parcel, or POI-membership index.

The broader supported inventory also contains county-wide selectors, a fallback,
multi-county PLACE projections, and presentation anchors. Treating anchor radius,
proximity, label, or source locality as membership would silently invent an
authority relation. Thus no frozen governed non-PLACE artifact supplies a
one-to-one POI join.

## 7. Rural and unincorporated behavior

A governed POI outside a canonical PLACE and outside any governed non-PLACE
membership remains a valid POI. Its runtime location is:

```text
countyContextId: exact governed ID for frozen county_fips
communityIdentity: absent on the POI record
```

If the search started at a county-only/map-center context, the request-level
`communityIdentity` is null/absent. If the same rural POI falls within a radius
started at a governed community anchor, the request may carry that community,
but the result does not acquire membership in it. Sparse/zero results remain
valid spatial outcomes.

## 8. Lookup and derivation findings

### Separate certified lookup

**None exists.** No catalogued artifact has all of: release binding to
`lp24111-d5-standalone-2026-08-28`, POI `id` join key, one-to-zero/one governed
community value, `391,772`-row coverage accounting, immutable hash, and one-to-one
cardinality certification. Relevant existing artifacts instead contain:

* PLACE identity-to-county membership (1,859 identities / 2,058 memberships);
* governed supported-area contexts/anchors (29 non-PLACE identities within the
  broader supported-area inventory);
* aggregate POI counts/measurements with no row-bearing membership relation; or
* missing build-only PLACE polygon sources.

None may be substituted as an uncatalogued historical intermediate.

### Deterministic derivation

There is **no deterministic frozen per-POI community derivation**. The only
approved identity-related projection is:

```text
frozen county_fips
  -> exact equality lookup in governed Texas county registry
  -> exactly one countyContextId
```

Expected cardinality is one county match for every frozen POI and all 391,772
rows; any exception fails materialization. `locality`, names, address text,
nearest anchors, radius inclusion, county-to-PLACE membership, and newly executed
point-in-polygon are prohibited substitutes.

The deterministic request-level community contract is separate:

```text
already resolved query selection
  -> exact canonical PLACE identity OR exact governed non-PLACE identity
  -> request.communityIdentity
```

It has zero-or-one cardinality per query, not per POI. Canonical multi-county
queries retain one community identity plus their governed selected/authoritative
membership or county search context; returned rows retain their own county
contexts. County-only/map-center queries allow null. Unknown/stale/unresolved
identities fail before shard loading.

## 9. Runtime schema correction

### Old contract (`gridly.poi.runtime.v1`)

`record.required.communityIdentity` is a `CANONICAL_PLACE` or
`GOVERNED_NON_PLACE` object for every record. This cannot represent rural POIs,
map-center searches, or cross-boundary radius results without asserting false
membership. It is unsupported by the frozen schema.

### Corrected contract

* Remove `communityIdentity` from the POI record.
* Keep `countyContextId` required on every record.
* Add/retain `communityIdentity` as nullable/optional **request context** and
  bounded diagnostic metadata; populate it only from an already governed query
  origin.
* Name diagnostics unambiguously (for example
  `queryCommunityIdentity`/`queryCountyContextId`) so they cannot be read as
  result membership.
* Preserve coordinate/radius shard selection and Haversine filtering unchanged.
* Do not infer a containing community during serialization.

Affected contracts/tests/tools are
`tools/lp24112/runtime-activation-design.mjs`, generated LP241.12 runtime-data,
identity-context, diagnostics, acceptance-plan and certification artifacts,
`tests/lp24112-runtime-activation-design.test.mjs`, LP241.13 release bindings,
LP241.14 rehearsal validation, and future LP241.15 materializer/validator tests.
This audit intentionally changes none of them.

Because v1 explicitly declares the field required, silently weakening or moving
it under the same schema identifier would change validation and cached-record
semantics. Use `gridly.poi.runtime.v2` (or an owner-approved equivalent new
schema identifier), update the immutable cache namespace and downstream legal
release bindings, and preserve v1 artifacts as historical design evidence. The
frozen POI authority release itself remains unchanged because this is a runtime
projection correction, not an authority-data change.
