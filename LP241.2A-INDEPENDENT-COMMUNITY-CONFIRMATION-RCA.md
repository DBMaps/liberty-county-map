# LP241.2A — Independent Community Confirmation RCA

## Acceptance status

This bounded repair is **not Community Reports launch acceptance**. Owner live acceptance must still prove that two independently issued pseudonymous contributor identifiers produce two persisted evidence rows which group into one governed condition.

## Exact root cause and execution decision

The rendered popup lineage is intact. The delegated `pointerup`/`click` handler resolves the persisted lifecycle report, canonical hazard type, and coordinates, then invokes `createSharedHazardReport` with `lifecycleTargetReportId`.

The live no-write outcome is explained by the first guard inside that writer: `reportingState.submissionInProgress` caused an immediate `false` return before duplicate lookup, pending-lock acquisition, or Supabase insert. That flag belongs to the report composer and is not contributor identity or lifecycle duplicate authority. The early return emitted no visible error and did not complete the lifecycle diagnostic, matching the owner's observations. `reportHazardTypeResolved: false` is report-composer diagnostic state; it does not invalidate the canonical type already passed by the popup.

The repair classifies a non-empty persisted `lifecycleTargetReportId` as a lifecycle confirmation. Such a confirmation is allowed past the unrelated composer-state guard. It still passes through the existing same-device/type/location active-inventory duplicate guard and the same-device/type/location pending-write lock before the existing Supabase insert. No schema, account, fingerprint, TTL, grouping, or trust-policy change is made.

## Contributor identity audit

Gridly's governed contributor authority today is the persistent pseudonymous `deviceId`:

1. Startup reads `localStorage.gridlyDeviceId`.
2. When absent, it creates `device-${crypto.randomUUID()}` (with a timestamp fallback) and writes it to the same local-storage key.
3. Report inserts persist that value in `reports.device_id`.
4. Duplicate suppression compares canonical hazard type, hazard cluster/location, active lifetime, and the current `deviceId`. The pending key contains the same type, cluster, and device identity. It does **not** suppress every user merely because type/location match.
5. Trust resolution deduplicates active and clear evidence separately by `device_id` (falling back to persisted report identity only for legacy rows without a device identifier).

There is no account, cookie, session-storage ID, Supabase auth identity, source-report ID masquerading as contributor identity, or browser fingerprint in this decision.

### Edge InPrivate

An Edge InPrivate storage partition should not share the normal Edge profile's local storage. Therefore, when it loads Gridly without a pre-existing value in that isolated partition, it receives a new `gridlyDeviceId` and counts as independent under today's product rule. Two separately opened InPrivate windows can share the same continuing InPrivate storage session and are not guaranteed to be independent. Close every InPrivate window between tests (or use a different browser profile/device), then verify `localStorage.gridlyDeviceId` differs before submitting.

This is installation/storage-partition independence, not proof of a distinct human or physical device. It is the existing privacy-safe, pseudonymous approximation and does not use invasive tracking.
