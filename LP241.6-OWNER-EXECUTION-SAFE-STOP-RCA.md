# LP241.6 Owner Execution Safe-Stop RCA

## Scope and evidence state

This RCA is limited to the owner-authorized LP241.6 runner's first-county HTTP 403. Static fixture certification remains **254/254 STATIC_CERTIFIED**. Provider execution remains **0/254 PROVIDER_EXECUTED**. County `48001` and every later county remain `NOT_EXECUTED`; no provider outcome is inferred. The address gate is neither a product PASS nor a product FAIL.

## Exact 403 RCA and returning layer

The Node runner sent the same URL, method, JSON body, public publishable key, and Supabase headers as the browser client, but it omitted `Origin`. Browsers attach `Origin` to the cross-origin POST automatically; Node `fetch` does not. The `gridly-geocode` Edge Function reads `Origin` and immediately returns HTTP 403 when it is absent or not in `GRIDLY_GEOCODE_ALLOWED_ORIGINS`. This happens before request-body validation, database work, or a downstream geocoder call.

The 403 is therefore the deployed **`gridly-geocode` Edge Function origin-policy response**, not a provider coverage result. It is not caused by CORS enforcement in Node (Node does not enforce browser CORS), Supabase JWT verification (`verify_jwt = false`), an authenticated-user/session requirement, provider token handling, or the downstream geocoder. The repository evidence does not identify Cloudflare in this request path, and the matching function-level 403 branch makes Cloudflare an unsupported attribution.

## Intended authorization and execution model

1. `gridly-geocode` is a public browser-facing boundary with an explicit allowed-origin contract. It is not a general origin-free server API.
2. A bounded owner CLI may safely call that same public boundary by declaring the real governed production origin. `Origin` is request context, not elevated authentication; this does not create a second geocoder or weaken the boundary.
3. The runner needs the same public Supabase publishable key already used by the browser.
4. It does **not** need an authenticated-user token, cookies, or a Supabase session.
5. It does **not** need and must not receive a service-role key. The Edge Function uses its service role internally for governed database operations; owner-local execution must not inherit that privilege.
6. The observed 403 maps to the Edge Function's allowed-origin rejection, before the provider.
7. Owner-local certification can safely use the public production boundary without privilege elevation, sequentially and with the existing stop rules.

## Bounded repair

Only the LP241.6 runner is repaired. Its request now adds the existing allowed production `Origin`; endpoint, public key, request shape, and security policy are unchanged. Execution remains concurrency one. On HTTP 401, 403, 429, or 5xx, the runner drains the response, atomically persists a `safeStop` record that truthfully leaves the failed county `NOT_EXECUTED`, prints a concise `SAFE STOP`, and sets a normal nonzero exit code. Successful rows alone enter `rows`; restart retries the first failed county, then continues in deterministic FIPS order.

Mocked tests write only temporary owner-local-style progress. They never update launch evidence and cannot become certification outcomes.

## Windows shutdown assertion

The reported `src\win\async.c` assertion is consistent with Node/libuv shutdown noise after an uncaught top-level exception while Undici still owns an asynchronous network handle. It is secondary to the HTTP 403 and is not evidence of a provider result. The repair consumes the failing response and handles the expected safe-stop at the command boundary by setting `process.exitCode = 1` rather than throwing an uncaught top-level exception or forcing `process.exit()`. This gives outstanding handles an orderly shutdown path and clearer owner UX. The repository evidence cannot prove that every Node/Windows version is free of a libuv defect; recurrence after this repair should be captured with the exact Node version and stack separately.
