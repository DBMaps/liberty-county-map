# LP243.F5 destination result address enrichment audit and certification

## Existing capability audit

Production already contains `gridlyReverseGeocode(lat, lng, options)`, a coordinate-to-address helper backed by the OpenStreetMap Nominatim `/reverse` endpoint. It accepts any valid coordinate pair plus optional zoom/country codes, requests `jsonv2` address details, and normalizes the response through `normalizeGridlySearchResult`. The normalized/raw result can expose `house_number`, `road`, `city`, `town`, `village`, `hamlet`, `municipality`, `county`, state and postcode. It was an active, direct-browser, arbitrary-coordinate helper, but had no cache, timeout, request serialization, or destination-card consumer before F5.

Gridly's established licensing/governance record treats public Nominatim as temporary and light-use only: OpenStreetMap attribution is already rendered with the map, requests must be identified, cached, and globally limited to roughly one per second, and provider capacity is not approved for launch scale. The shared `gridly-geocode` Edge boundary provides forward search, hashed database caching and a global provider lease, but its current request contract accepts only address/business-place queries—not coordinates or reverse intent. F5 therefore adds no provider and reuses the already-shipped reverse helper, while bounding, serializing, timing out, and session-caching its use. A future governed migration should extend the Edge contract rather than introduce another provider.

Other address paths are forward-only: `gridlyGeocodingClient.search` calls the Gridly Edge boundary for destination/address searches; `gridly-geocode` canonicalizes provider address fields and caches forward responses; saved-place address resolution is forward geocoding. None can accept arbitrary POI coordinates under its present contract. These paths can create authoritative search candidates. In contrast, the F5 reverse path can only attach `presentationAddress` to a published runtime-v2 row and cannot replace its identity or coordinates.

## Pipeline and safety contract

F5 retains acquire → normalize → rank → containment → dedupe → five-row projection. The final renderer publishes those rows immediately, then starts enrichment only for the projected runtime-v2 rows. A canonical coordinate key rounded to five decimals backs session memory and in-flight caches. Requests are serialized with at least 1.1 seconds between starts, bounded to the existing five-row render limit, and individually time out after 3.5 seconds. Provider failure, timeout, empty output, or stale-search completion leaves the original card untouched.

The formatter uses only explicit reverse-provider fields. Presentation preference is house number + road + locality, road + locality, locality, then county. It preserves which locality field supplied the value rather than relabeling towns/villages/hamlets as cities. It never manufactures a house number or nearby road.

Results are enhanced in place without reranking or rerendering. Selection continues to pass the original result object to the existing destination handoff. `providerId`/POI ID, coordinates, runtime schema, category, county context, published rank, Home Area, Awareness Area, query intent, and route authority remain unchanged. Reverse county text is display-only and cannot reinterpret Port Arthur's governed multi-county identity.

## Presentation

Cards remain compact:

- title: business name;
- optional location: `1234 Example Rd · Port Arthur` or `Example Rd · Port Arthur`;
- existing category/distance metadata remains independently rendered.

The browser asset identity is `243f5-destination-address-enrichment`.
