## LP244.21C local protocol implementation and certification

This section supersedes the A/B implementation and test status below. Those sections remain dated audit history, not the current protocol. No production mutation, deployment, publication, staging, commit, push, or native package build occurred.

### Root cause and repair

A retry formerly used direct INSERT with a newly generated database report ID and submission clock. Deleting the original row removed the only relevant identity. Physical crossing IDs identify places, and device-derived hazard IDs cannot be retained as replay evidence. The new admission RPC atomically consumes a submission-scoped UUIDv4 digest before creating the original row and private device link. A duplicate returns already_processed without revealing the original row. Separate random tokens permit later observations at the same crossing/location. Deleted rows and device links do not delete consumed-token evidence.

js/gridly-report-protocol.js uses crypto.randomUUID or crypto.getRandomValues with UUIDv4 version/variant bits. No device, timestamp, content, location, or Math.random input enters identity generation. Hazard crossing identifiers also use independent secure UUIDs. Physical crossing IDs remain reusable place identifiers. The server can validate UUID syntax, not prove that an arbitrary hostile client generated its supplied UUID randomly; the supported client generation path supplies that proof of implementation, not a universal claim about malicious input.

### Schema, permissions, and operation semantics

Apply 202609080001_community_report_retention.sql followed by 202609080002_community_submission_protocol.sql only under separate production authorization. The second migration creates private report_retention.replay_evidence with exactly token_digest (32-byte SHA-256, primary key) and first_accepted_at (server timestamptz). Hashing canonical UUID bytes prevents case-variant replay. Atomic INSERT ON CONFLICT serializes concurrent claims. Report/link creation and digest admission share the same transaction; failed creation rolls back the claim so the operation can recover. UPDATE, DELETE and TRUNCATE guards make the ledger append-only under normal execution. Anon, authenticated and service_role have no direct ledger access. Only narrowly granted SECURITY DEFINER RPCs admit ordinary clients; their search paths are fixed. The direct reports INSERT table and column grants are revoked, and existing restricted reads remain.

Public RPCs: submit_community_observation(submission_token, report, reporter_device_id), mutate_community_observation(operation_id, observation_id, action, changes, reporter_device_id), and cancel_community_operation(operation_id). Private helpers claim_operation and public_report expose no ordinary-client execution. Creation returns a safe current report projection or explicit already_processed. Mutations confirm/edit/clear target an existing server report ID and never insert a replacement. Edit requires the live original device association; community confirm/clear retain community participation semantics and do not assert independent contributor counts. Missing/expired targets return gone. Allowed update fields exclude original_submitted_at, linkage_deadline, cleanup_after and device association. Clear changes the original row instead of inserting a new original. Public history is the existing coarse month/condition-family/count aggregate, with no ledger joins or contributor key.

Day 149 remains an internal operational cleanup target; the owner promise is maximum 180 days. Deadline intervals use fixed elapsed UTC hours in timestamptz (149*24 and 180*24), not local calendar arithmetic. Legacy records without trustworthy original timestamps are removed conservatively by migration 001, including old history copies; no device-derived legacy ID is converted into a receipt. Deadline indexes and private ledger uniqueness support cleanup/admission without public device identifiers.

### Pending operation lifecycle and hard cutover

One persisted operation holds its random ID, original pending time, kind, and bounded payload (maximum serialized input length 12,000 characters); the server separately enforces byte limits. The persistent device identifier is attached only to the outgoing RPC argument, not the pending record. Storage succeeds before network admission. An in-flight double tap shares one promise. Network failure/ambiguous result retains the same operation across restart. A pending operation blocks a new observation and exposes a Retry pending report control; terminal status removes its payload. After 24 hours, the next access drops the payload and keeps only ID/time/cancel disposition pending terminal cancellation. An untouched offline installation cannot execute local cleanup until it runs again. Corrupt/unavailable storage fails closed; manual storage recovery may be necessary. No internal ID is rendered in the retry control.

### Required protocol and migration design — not implemented

1. Introduce a required, versioned submission identity for **every** original observation, including crossings. Generate an opaque CSPRNG identifier once before its first attempt; bind it to the pending operation and reuse it for retries, interrupted requests and disconnected recovery. Never derive it from a device, content, place, time or user identity. A genuinely new observation receives a new identity, even for the same hazard/location. Reopening the same pending action must not silently mint a new original identity.
2. Define creation separately from edits, confirmations and clears. Mutations must reference a server-recognized original report and preserve its original clock, with operation-scoped retry handling. A missing/de-linked parent must not be recreated through a mutation. The current 'confirm by creating another original report' path needs an explicit protocol change before it meets this contract.
3. Make the database admission transaction enforce the protocol. Atomically claim a unique digest of the independently random submission identifier in a private replay ledger before creating the report/link. The unique constraint must serialize concurrent identical submissions; duplicate claims must return a non-creating idempotent result. Ordinary anon/authenticated users must have no direct read/update/delete/replacement access to the ledger, and every old direct INSERT/RPC bypass must be rejected. Do not expose existence probes or original reporter data through duplicate responses.
4. Separate this minimum evidence from device links and condition history. Proposed retained evidence is only a cryptographic digest of the opaque submission identifier, with a uniqueness constraint; no device ID/digest, report-row mapping, content/location fingerprint, timestamps, source joins or contributor identity in the surviving ledger. During a live record's lifetime, any needed retry-to-row association must be bounded by that record's existing retention contract. Even random submission evidence must not be labeled anonymous: external captured requests can carry correlation information.
5. Replay-evidence lifetime must match the acceptance rule. If arbitrarily old requests remain acceptable, the minimal digest must remain for the full service lifetime that accepts that protocol; there is no safe finite TTL that merely forgets a still-replayable submission. Its sole purpose is duplicate suppression, not analytics or device tracking. This is a **proposed technical retention design, not an approved policy change or implemented indefinite store**. A finite retention alternative requires server-verifiable expiring issuance/receipts and rejection after their acceptance period, plus replay records for the entire remaining acceptance period. Client-supplied dates or unsigned protocol epochs are not proof of expiry. Decide that protocol/retention contract before implementation.
6. Fail closed for old clients. Server-side rejection must cover missing/invalid new submission identity for crossing and hazard paths, not only the known device-bearing hazard regex. No 'legacy compatibility' path may accept old bodies as fresh submissions. The existing read restrictions remain necessary. If a new receipt-based protocol is chosen, reject legacy/unverifiable receipts as well. This intentionally requires a coordinated client release and may make old/disconnected clients unable to submit; app-only checks are insufficient.
7. At cutover, purge unverifiable legacy associations as already planned; do not seed the ledger from device-bearing IDs, crossing IDs or a guessed content fingerprint. Close legacy admission before accepting the new protocol. The post-cleanup replay regression must be expanded to the new protocol, including lost responses, concurrent attempts, mutation retries and fresh observations. The old-protocol replay should be rejected at admission, not accepted and later cleaned up.
8. Roll forward after accepted submissions/deletions. A rollback must not discard replay evidence, restore erased links, reopen legacy admission or reset issuance validity. Restore snapshots into isolation; verify ledger completeness and the original acceptance boundary before traffic. If replay evidence is missing, keep writes closed or use a separately designed server-verifiable invalidation/recovery boundary. A client-provided new epoch is not sufficient. Provider backups/PITR/WAL, physical remnants, logs and exports still require their own evidence and cleanup controls.

Rejected shortcuts: device hashes or hashes of legacy hazard IDs retain device-derived evidence; crossing/location/content fingerprints confuse recurrence with replay; server UUIDs generated per INSERT cannot deduplicate a lost response; client-only duplicate locks do not protect the database; immediate or finite tombstone expiry without bounded acceptance restores the bug; historical sidecar hashes are neither safe admission tokens nor collision-resistant evidence.

## Exact prepared changes

`supabase/migrations/202609080001_community_report_retention.sql` is transactional and destructive. It is a one-time, versioned migration, not a script to rerun manually after successful application.

- Add non-null original_submitted_at, linkage_deadline and cleanup_after to reports, plus cleanup_after index. Use fixed elapsed-hour intervals: 4320 hours = 180 days; 3576 hours = 149 days, independent of daylight-saving changes.
- Delete live-system links early at **day 149**, reserving **31 days** before the approved maximum. Earlier deletion is within the owner's maximum. It leaves a potential 30-day backup window plus one day of operating margin; this is an engineering reserve, **not evidence of actual backup expiration**.
- For legacy migration only: valid recorded timestamps may contribute a broad monthly count. Missing/future origins produce no historical count. Remove every legacy report and associated historical copy regardless of apparent age; do not copy the identifiers to another archive. The audit found no live reports, but this must be rechecked at cutover.
- `report_retention.device_links`: only report_id and raw device_id, private RLS/no client or service-role privileges, cascading FK to the live report. Before the cutoff, the association exists here; after cleanup, both this row and the original condition row are deleted. There is no retained device hash, encryption key, reidentification lookup or report tombstone.
- `reports.device_id` remains a write-interface compatibility column, always NULL in stored rows. The security-definer trigger moves a new submission's device into its temporary private row in the same transaction, before public-row constraint errors/serializers can include it. Existing rows cannot reassign device or origin. Public reads omit the column entirely.
- Trigger rejects unknown/future/expired imported origins, mutable ID/origin/deadline, and legacy device-bearing hazard IDs. A new ordinary submission gets the database-created created_at; client grants exclude IDs and timestamp controls. Trusted imports/copies must carry original created_at. No new arbitrary import/copy endpoint is exposed. An owner/superuser who bypasses triggers or fabricates a new original record can defeat the contract; no SQL policy can prevent its administrator from rewriting the database. Such copies are prohibited operationally.
- `condition_month_counts`: only submission_month, broad condition_family (`road` or `crossing`) and report_count. No event IDs, source IDs, device IDs, location, free text, exact submission time or join mapping. This is a coarse count of submitted reports, not verified incidents or unique people. It is not exposed publicly and is not labeled anonymous.
- `runs`: start/completion, status, deleted count, SQLSTATE only. Cleanup and counting are atomic; a caught failure rolls back deletions/counts and commits a failed audit row, returning -1. No SQLERRM or payload is stored. Successful repeats return zero without double-counting. Audit rows expire after 30 days during successful cleanup.
- `health`: last successful completion, last status, overdue cleanup count and breached hard-deadline count. `gridly_retention_monitor` is a NOLOGIN role with only schema usage and SELECT on this aggregate view. Stale (>5 minutes) cleanup blocks new submissions as well as alerting.
- The separate activation SQL installs pg_cron and schedules the function every minute. The external Node monitor exits nonzero for failure, stale heartbeat, overdue rows, invalid output or connection failure. Scheduler success alone does not prove cleanup success, because a caught function failure deliberately commits its audit record.

## Backup, log and offline limits — unresolved

[Supabase backup documentation](https://supabase.com/docs/guides/platform/backups) describes daily backup access windows of 7, 14 or up to 30 days by plan and separately configured PITR recovery windows. Those are product options, not this project's verified configuration. Physical backups can contain deleted row/page remnants; WAL can contain earlier row versions. [Supabase Cron](https://supabase.com/docs/guides/cron) records job runs and status, but does not establish successful end-to-end erasure.

With a *verified* maximum backup lifespan B, the latest potential logical copy would expire approximately original submission +149 days +cleanup delay +B. If B=30 days and cleanup completes within one day, that fits the 180-day ceiling. **Actual B is unknown.** That calculation also assumes no new backup can keep capturing old physical page contents. Ordinary DELETE/VACUUM does not prove secure physical erasure. A verified compaction/physical-storage lifecycle (including historic indexes, WAL, snapshots and provider replicas) must be established; no VACUUM FULL or provider storage operation was performed or silently scheduled. The actual final irrecoverability date is therefore not established.

Previously public data may already exist in exports, screenshots, logs, support messages or offline browsers. An upgraded browser removes known local history keys; a browser that never opens the new build cannot execute cleanup. New no-store fetches and writer restrictions do not retroactively erase those copies. Provider HTTP/access logs can associate device/network identity with request bodies/times even when the SQL row later disappears. No request body logging, analytics payload collection, or raw report/device export should be enabled in a future rollout. Verify provider contracts/settings and resolve older copies; do not assume their retention or claim this repository controls them.

The current static build contains client audit/export tools and local review notes. Their ordinary database reads lose device access. Human-authored notes or manually exported/private copies need an actual owner inventory and deletion process; a code scan cannot prove their absence. No stable hashed identifier has been introduced as a substitute for deletion.
