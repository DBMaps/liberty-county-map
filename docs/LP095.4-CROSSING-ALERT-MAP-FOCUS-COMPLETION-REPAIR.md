# LP095.4 — Crossing Alert Map Focus Completion Repair

## 1. Executive summary

LP095.4 repairs the single transition between a settled, visible map focus and canonical crossing-popup dispatch. The production focus path now treats an existing marker inside the usable map viewport as completed focus after sheet closure, map invalidation, movement settlement, target zoom, and awareness-selection preservation. Exact pixel centering and post-open popup containment remain diagnostics and post-open concerns; neither blocks the popup before it can exist.

## 2. LP095.3 live evidence

The product-owner trace for `FRA-762785P` proved tap receipt, delegated handling, canonical identity, crossing record, existing marker, coordinates, and a dispatched focus request. It stopped with `mapFocusRequested: true`, `mapFocusCompleted: false`, `popupRequested: true`, and no popup suppression/open events. That confines the defect to the completion gate in `focusGridlyAlertIncident`.

## 3. Exact root cause

`focusGridlyAlertIncident.complete` assigned `debug.mapMovementCompleted` only when `debug.usableViewportCenteringCompleted` was true. That value required exact pixel centering (`pixelDelta.distance <= thresholdPx`) and, when a popup was requested, pre-dispatch popup viewport acceptance. The canonical crossing popup dispatch was inside the subsequent `if (marker && debug.mapMovementCompleted)` branch. A valid, visible crossing marker therefore could be rejected before `openCrossingPopupFromMarkerInteraction` ran because the pre-popup gate demanded stricter presentation diagnostics than user-visible marker focus.

## 4. Failed focus-completion condition

The failed branch was `if (marker && (debug.mapMovementCompleted || officialMarkerMatched))`: crossing markers are not official-marker exceptions, so a false `debug.mapMovementCompleted` skipped marker activation and popup dispatch. Completion had been calculated from sheet closure, invalidation, settlement, exact zoom, `usableViewportCenteringCompleted`, and preserved awareness selection. The invalid requirement was `usableViewportCenteringCompleted`, not marker identity, coordinates, or marker lookup.

## 5. Interaction path before repair

`delegated Alerts click → canonical crossing resolver → existing marker lookup → focusGridlyAlertIncident → close sheet → invalidate map → fly/set view → settle → exact-centering/pre-popup completion gate → false → popup branch skipped`.

## 6. Interaction path after repair

`delegated Alerts click → canonical crossing resolver → existing marker lookup → focusGridlyAlertIncident → close sheet → invalidate map → fly/set view (or retain an already-visible target) → settle → visible-marker completion contract → focused-marker state → openCrossingPopupFromMarkerInteraction → existing suppression/session logic → one verified popup`.

## 7. Files and functions changed

- `tests/lp0954-crossing-focus-completion-repair.test.js`: covers valid, already-visible, failed, canonical-popup, single-dispatch, marker-reuse, hazard, official, trace-terminal, and fail-closed contracts.
- This document records evidence, scope, certification, and merge gating.

## 8. Why the repair is deterministic

No new timer, listener, marker, popup, or focus implementation was added. The existing two-frame sheet/layout boundary, Leaflet movement completion/fallback, and canonical popup session remain authoritative. The repaired predicate uses state already measured at settlement.

## 9. Already-visible marker behavior

No movement event is required as proof of focus. The existing settlement fallback reaches completion, and a marker already inside the usable viewport satisfies the visible-focus requirement if sheet closure, invalidation, zoom, and awareness preservation also pass.

## 10. Popup dispatch and duplicate suppression

Crossings still use `openCrossingPopupFromMarkerInteraction`, including existing visible-popup suppression, pending-session suppression, content preparation, and verified-open reporting. Generic `marker.openPopup()` remains only the non-crossing fallback. The repair adds no second popup request.

## 11. Hazard and official preservation

Hazards retain `focusGridlyAlertIncident` and the generic marker popup branch. Official records retain pre-focus marker refresh and `officialMarkerMatched` completion allowance. The new visible-marker predicate is shared only at the existing completion boundary and does not alter either marker resolver.

## 12. LP095–LP095.3 preservation

LP095 presentation, LP095.1 spacing, LP095.2 canonical crossing resolution, LP095.2A delegated click/Enter/Space semantics, and LP095.3 tracing remain unchanged. LP095.3 now naturally observes the real successful product path through focus completion, suppression evaluation, popup request, and verified open.
