# LP095.4 — Crossing Alert Map Focus Completion Repair

## 1. Executive summary

LP095.4 repairs the single transition between a settled, visible map focus and canonical crossing-popup dispatch. The production focus path now treats an existing marker inside the usable map viewport as completed focus after sheet closure, map invalidation, movement settlement, target zoom, and awareness-selection preservation. Exact pixel centering and post-open popup containment remain diagnostics and post-open concerns; neither blocks the popup before it can exist.

## 2. LP095.3 live evidence

The product-owner trace for `FRA-762785P` proved tap receipt, delegated handling, canonical identity, crossing record, existing marker, coordinates, and a dispatched focus request. It stopped with `mapFocusRequested: true`, `mapFocusCompleted: false`, `popupRequested: true`, and no popup suppression/open events. That confines the defect to the completion gate in `focusGridlyAlertIncident`.

## 3. Exact root cause

`focusGridlyAlertIncident.complete` assigned `debug.mapMovementCompleted` only when `debug.usableViewportCenteringCompleted` was true. That value required exact pixel centering (`pixelDelta.distance <= thresholdPx`) and, when a popup was requested, pre-dispatch popup viewport acceptance. The canonical crossing popup dispatch was inside the subsequent `if (marker && debug.mapMovementCompleted)` branch. A valid, visible crossing marker therefore could be rejected before `openCrossingPopupFromMarkerInteraction` ran because the pre-popup gate demanded stricter presentation diagnostics than user-visible marker focus.

## 4. Failed focus-completion condition

The failed branch was `if (marker && (debug.mapMovementCompleted || officialMarkerMatched))`: crossing markers are not official-marker exceptions, so a false `debug.mapMovementCompleted` skipped marker activation and popup dispatch. Completion had been calculated from sheet closure, invalidation, settlement, exact zoom, `usableViewportCenteringCompleted`, and preserved awareness selection. The invalid requirement was `usableViewportCenteringCompleted`, not marker identity, coordinates, or marker lookup.

## 5. Interaction path before repair

`delegated Alerts click → canonical crossing resolver → existing marker lookup → focusGridlyAlertIncident → close sheet → invalidate map → fly/set view → settle → exact-centering/pre-popup completion gate → false → popup branch skipped`.

## 6. Interaction path after repair

`delegated Alerts click → canonical crossing resolver → existing marker lookup → focusGridlyAlertIncident → close sheet → invalidate map → fly/set view (or retain an already-visible target) → settle → visible-marker completion contract → focused-marker state → openCrossingPopupFromMarkerInteraction → existing suppression/session logic → one verified popup`.

## LP095.4A — post-dispatch runtime repair

### New browser evidence and repeated sequence

The `FRA-762784H` capture reaches **Popup request issued** but never enters focus completion or popup suppression. Repetition is trace accumulation across separate physical clicks: LP095.3 stayed armed while incomplete and ignored later capture-phase taps, but continued appending every later delegated-handler stage to the original event array. It was not a second delegated listener, pointer/click synthesis, keyboard fallback, renderer duplication, delayed redispatch, or the observer.

### Exact production path and root cause

`gridlyLp019BindAlertFocusHandlers` emits **Popup request issued**. The next executable statement previously evaluated `getGridlySelectedAwarenessArea()` while assigning `window.__gridlyLp019AwarenessSelectionBeforeFocus`. That getter is instrumented and can synchronously invoke `gridlyDriveTexasConnector.refreshAwarenessView("awareness-area-resolved")`; the call was outside the handler's focus-dispatch `try` boundary. In the captured runtime that side-effecting preservation read escaped before `focusGridlyAlertIncident` was called, so no focus callback could be registered and no failure could be finalized.

Required root-cause statement: **After LP095.3 recorded Popup request issued inside `gridlyLp019BindAlertFocusHandlers`, execution proceeded to the assignment of `window.__gridlyLp019AwarenessSelectionBeforeFocus` by calling `getGridlySelectedAwarenessArea()`. It then failed to reach focus dispatch because that side-effecting awareness getter entered connector refresh work outside any interaction error boundary. The repeated sequence occurred because LP095.3 remained armed after the escaped interaction and accumulated delegated-handler stages from each later physical tap in the same trace session.**

### Repair and terminal trace contract

The preservation snapshot now reads the already-resolved awareness cache without invoking refresh. A traced **Post-popup-request dispatch entered** boundary precedes a guarded call to `focusGridlyAlertIncident`; return and synchronous exception paths are explicit. Focus settlement records callback registration, invocation, evaluation, resolution, and exceptions. Both PASS and FAIL set `terminalStateReached` and `completed`, then disarm capture. A reset creates a new `traceSessionId`; one armed click has one `physicalTapCount`, `interactionAttempt`, and `handlerEntryCount`. Re-entry fails closed.

The Alerts insertion pipeline now invokes only `gridlyLp019BindAlertFocusHandlers`. The obsolete inner bridge is no longer called, and bound panels identify that authoritative owner. Keyboard activation continues to synthesize the one canonical click intentionally; no pointer handler, retry loop, per-card listener, marker, or popup implementation was added.

### Before and after

Before: alert click → resolver → existing marker → popup intent trace → side-effecting awareness getter → escaped interaction with trace left armed.

After: alert click → resolver → existing marker → popup intent trace → passive cached preservation snapshot → guarded focus dispatch → deterministic focus completion → canonical crossing popup suppression → one open request → verified popup → terminal PASS (or explicit terminal FAIL).

## LP095.4B — canonical context exception repair

### Certified root cause from the LP095.4A trace

The synchronous exception occurred in `gridlyLp0546ResolveCrossingRecord` at `currentAwareness.identity.canonicalCountyKey` while the return contract was assembled. `currentAwareness.identity` was undefined because the FRA-762784H alert arrived with an absent selected-awareness cache entry and the live current-awareness wrapper therefore did not carry the identity member assumed by the historical crossing-selection resolver. The correct canonical county source for this crossing is the already-resolved runtime crossing record's governed county metadata (`countyId`/`county`/`COUNTYNAME`, normalized by `gridlyLp0546ResolveAwarenessAreaIdentity`).

The reachable-read audit found the unsafe family in the same return expression: `currentAwareness.identity.canonicalCountyKey`, `areaDetails.crossing.canonicalCountyKey`, and `areaDetails.current.canonicalCountyKey`. FRA-762784H's production source supplies `COUNTYNAME: "LIBERTY"`; the runtime adapter promotes county metadata on the crossing record. It does not require `canonicalCountyKey` to be materialized on the alert. The alert's authoritative identity is `crossingId`, the existing marker is an identity/interaction handle rather than the county authority, and neither is duplicated by this repair. Hazard and official alerts do not enter the new crossing-only resolver and continue to use their existing record shapes and generic/official popup handling.

The missing contract was the assumption that every crossing selection necessarily has a fully shaped current community/county identity wrapper. The selected-awareness cache is optional during this transition. The canonical selection resolver now reconstructs its identity from its record when that wrapper member is absent, and safely reconstructs crossing/current area identities at the same boundary. It no longer dereferences an optional wrapper merely to build diagnostic output.

### Narrow focus-path repair and containment

`gridlyLp0954bResolveCrossingCanonicalContext` inspects, in authority order, the resolved crossing record, alert record, and marker context. It normalizes existing `canonicalCountyKey`, `countyId`, `normalizedCountyId`, `county`, county-name, and awareness-area fields through the existing awareness identity resolver. It compares the resulting crossing county with the cached selected-awareness county before focus dispatch.

A missing county is optional only when both the canonical crossing record and its existing marker are present; this preserves the established crossing-visibility decision without inventing a county. A known county mismatch fails terminally before focus or popup dispatch. Thus the repair neither bypasses awareness filtering nor weakens county containment. Compatible targets continue into `focusGridlyAlertIncident`, reuse the existing marker, and dispatch once through `openCrossingPopupFromMarkerInteraction`. Confirm Active and Mark Cleared remain owned by that canonical popup.

Before: delegated alert handler → crossing/marker resolution → historical crossing-selection context construction → unsafe current-awareness identity read → synchronous exception.

After: delegated alert handler → crossing/marker resolution → canonical county source inspection and compatibility decision → guarded historical selection construction → focus completion → canonical crossing popup dispatch.
