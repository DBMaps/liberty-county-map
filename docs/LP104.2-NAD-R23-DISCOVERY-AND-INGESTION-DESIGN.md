## Performance and extraction architecture (conditional design)

These are implementation gates, not claims about R23:

1. Keep the ZIP immutable and calculate its SHA-256. Read it with GDAL's virtual ZIP filesystem where supported; if the FileGDB driver requires materialization, extract once to encrypted temporary storage after verifying adequate free space and delete only that temporary copy after reconciliation.
2. Identify the address layer from the measured schema. Use attribute filtering for Texas only if the observed field is documented, populated, and value-profiled. Otherwise stream features through a Texas boundary prepared in the layer CRS; never load national features into memory.
3. Read batches of **25,000 features initially**, lowering to 5,000 if resident memory exceeds 1.5 GiB. This starting value must be benchmarked; it is not an R23-derived optimum. Keep projection, normalization, validation, and output streaming within a fixed-memory worker.
4. Write append-only county partitions to protected local staging (prefer GeoParquet for typed analytics and compressed NDJSON only for interoperability). Use a run manifest containing archive hash, schema hash, tool/config version, last source feature identifier, per-county accepted/rejected counts, output hashes, and completion flags. Commit by batch through temporary files plus atomic rename.
5. If the source exposes stable unique identifiers, checkpoint by identifier. Otherwise checkpoint by deterministic layer ordinal and validate that the archive and schema hashes match before resume. Sort/deduplicate per county as a separate bounded external-sort pass.
6. Reconcile `read = Texas kept + non-Texas skipped + rejected`, then reconcile Texas output to all 254 county partitions plus explicit unassigned/conflict buckets. Never silently discard a record.

### Memory, temporary storage, and time

On the AMD Ryzen 5 7520U / 8 GB RAM target, cap one extraction worker near 1.5 GiB RSS and use a single concurrent FileGDB reader to avoid paging. Reserve temporary capacity only after the archive reports its extracted byte total. A conservative gate is free space of at least **2 × extracted geodatabase size + projected Texas output + 20% headroom** when extraction is required; `/vsizip` avoids the first copy when supported.

Runtime cannot be honestly estimated until layer count, national/Texas feature count, compression, storage medium, GDAL driver behavior, and a measured 1-million-feature benchmark are known. LP104.3 should record read/filter/write rates and compute `estimated duration = relevant feature count / measured steady-state rate`, plus extraction and external-sort time. Report a range from two repeated cold runs rather than presenting an invented wall-clock estimate.

## Storage recommendation (provisional until measurement)

Retain the existing **hybrid architecture as the candidate**, subject to LP104.3 benchmarks:

* immutable NAD master archive and versioned county build artifacts in private object storage;
* GeoParquet county packages for resumable ETL, audit, rollback, and county rebuilds;
* PostGIS serving tables partitioned by county FIPS for protected exact/ranked lookup, spatial validation, indexes, and controlled updates;
* no address package, source row, coordinate, or bulk endpoint in browser-accessible assets.

Object storage alone is poorly suited to low-latency indexed lookup; PostGIS alone makes immutable source retention, cheap rebuilds, and rollback cumbersome; browser county packages would expose bulk residential address data. Actual row widths, index cardinality, update model, query plans, and county skew must be measured before finalizing partition and index choices.

## Risks and opportunities

### Risks

* The archive may require a GDAL driver/version unavailable on the Windows target.
* State/county fields may be absent, incomplete, inconsistently encoded, or governed by domains not visible in a shallow export.
* Geometry CRS/axis order or invalid points could cause incorrect spatial filtering.
* Record identifiers may not be stable between NAD releases, weakening resume and incremental update logic.
* County and provider distributions may be highly skewed; national totals do not establish local coverage.
* Address precision may be absent or may describe source processing rather than entrance/rooftop accuracy.
* FileGDB indexes and relationship/domain semantics can be lost by premature conversion.
* Residential coordinates and provider-specific terms require privacy and redistribution review even for a federal aggregate.

### Opportunities

* A supplied, well-populated state/county code could eliminate expensive national spatial classification.
* Stable IDs and update dates could support incremental county refreshes.
* Source/provider and precision metadata could enable evidence-based ranking rather than a blanket NAD confidence tier.
* County-partitioned metrics can reveal gaps before any runtime activation.

## Recommended LP104.3 plan

1. Mount or otherwise expose the untouched R23 ZIP at a stable protected path; record source provenance and hash.
2. Install pinned GDAL tooling with verified FileGDB/OpenFileGDB and `/vsizip` support on the inspection host.
3. Run both inventory commands; retain raw reports and command/tool versions.
4. Enumerate every layer/table and its schema constructs, then create the metadata-backed address crosswalk.
5. Profile only aggregate values: null/distinct counts, state encodings, county/FIPS completeness, geometry validity, CRS, precision/provider categories, date ranges, and identifier uniqueness. Publish no address samples.
6. Obtain exact Texas and Liberty County counts using a documented attribute predicate; compare a bounded spatial validation sample/aggregate. Use full spatial classification only if attribute evidence fails.
7. Benchmark two cold 1-million-feature streaming passes on the specified Windows hardware and measure throughput, peak RSS, compressed/extracted I/O, and output ratio.
8. Finalize batch size, checkpoint key, temporary-space requirement, runtime range, county partition strategy, PostGIS schema/indexes, and privacy/licensing gates from those measurements.
9. Only after review approval, schedule LP104.4 extraction. Do not ingest or build county packages in LP104.3 discovery.
