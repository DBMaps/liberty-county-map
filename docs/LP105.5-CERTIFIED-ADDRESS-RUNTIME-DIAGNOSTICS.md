# LP105.5 — Certified Address Runtime Diagnostics

## Audit result

### Verified repository facts

1. The browser sends governed searches through `gridly-geocoding-client.js` to `gridly-geocode`; it does not fetch the certificate or gzip package.
2. The Edge Function invokes the Liberty adapter before its general-provider cache and provider pipeline. Eligible adapter failures return `provider_unavailable` without fallback. Ineligible traffic retains the existing cache and provider pipeline.
3. The adapter selects `GRIDLY_CERTIFIED_ADDRESS_BASE_URL`, defaulting to `https://gridly.app`, then requests and validates the Liberty runtime certificate before requesting, validating, and streaming the gzip package.
4. Before LP105.5, diagnostics reported only coarse outcomes and timing. They could not distinguish request eligibility, selected artifact configuration, certificate request/retrieval/validation, package request/retrieval, gzip opening, exact scan, or routing after the adapter.
5. The prior browser helper tested outcomes but discarded the Edge Function's certified-provider diagnostics in the browser client, so its output could not locate the exit stage.
6. The exact certificate request is the selected base URL (with one trailing slash removed) plus `/data/generated/lp104/txgio-addresses/liberty-48291.runtime-certificate.json`. `gridly-geocode` supplies `GRIDLY_CERTIFIED_ADDRESS_BASE_URL`, or `https://gridly.app` when that variable is absent or empty.
7. The expected certificate and `liberty-48291.addresses.jsonl.gz` are tracked at that repository-relative public path. The checked-in certificate identifies the gzip artifact, byte size, SHA-256 digest, county, FIPS, and exact-only acceptance contract used by the adapter.
8. The only checked-in GitHub Actions workflow is Capacitor validation. It copies the repository's `data` directory into a temporary mobile web directory, but it neither deploys the Edge Function nor publishes a GitHub Pages/site artifact. The repository contains no Pages, static-host, or generated-address publication workflow and no hosting configuration file.
9. Certificate retrieval uses the Edge runtime's `fetch`. A non-2xx response previously became `certificate_unreadable`; a thrown fetch error retained only its exception message. Either path becomes the certified adapter's `package_unavailable`, and an eligible certified request is then returned by `gridly-geocode` as HTTP 503 with response source `certified_provider_unavailable`.

### Verified runtime evidence

The automated fixture-backed runtime executes certificate retrieval and validation, package retrieval, gzip streaming, and exact lookup. It returns the certified 276 address for all governed County Road aliases and a truthful miss for 274. The tests also verify that a malformed certificate stops before package access and reports `certificate_validated` as its failure stage.

The supplied deployed-browser evidence verifies `certifiedProviderExecuted = true`, `lastCompletedStage = failureStage = runtime_certificate_requested`, all three downstream booleans false, response source `certified_provider_unavailable`, and Edge HTTP 503. This proves that the deployed Edge Function selected a non-empty base URL and exited while fetching the certificate, before certificate validation or package access.

An attempted command-line request to `https://gridly.app` from this repository environment was rejected by the environment's outbound CONNECT proxy with HTTP 403 before reaching the host. That is an environment limitation, not evidence of the deployed Edge Function's certificate response.

### Inference boundary

The repository does **not** record the deployed value of `GRIDLY_CERTIFIED_ADDRESS_BASE_URL`, the deployed Edge Function revision, DNS/hosting ownership for `gridly.app`, or the contents and status codes actually served by that host. The absence of a publication workflow is a verified repository gap, but does not prove that an external deployment system is absent. Consequently repository evidence does not prove incorrect URL construction, an incorrect public path, missing deployed artifacts, an environment-variable mismatch, a hosting mismatch, or a runtime fetch bug. Selecting any one as the root cause would be speculation.

## Minimal instrumentation

The adapter now records a bounded allowlisted stage sequence and boolean operational state. It additionally reports the attempted certificate URL stripped of user information, query, and fragment; the HTTP status when a response was received; whether fetch completed; and one safe reason: `http_error`, `network_failure`, `timeout`, `invalid_certificate`, or `successful_retrieval`. Certificate fetches have a ten-second timeout. No headers, request data, environment-variable value, URL credentials/query, response body, artifact content, or exception stack is exposed. The browser client copies only the allowlisted operational fields and caps stage output at 16 entries.

Both of these console calls run the updated certification through the existing client and Edge boundary:

```js
await window.gridlyLp1052RuntimeAddressCertification?.()
await window.gridlyLp1055RuntimeAddressCertification?.()
```

The top-level fields describe the exact-address case. Every case also reports `lastCompletedStage`, `failureStage`, `responseSource`, `certifiedProviderExecuted`, `certificateValidated`, `packageOpened`, `exactLookupExecuted`, `fallbackExecuted`, `certificateUrl`, `certificateHttpStatus`, `certificateFetchCompleted`, `certificateFetchReason`, and `completedStages`. Thus a deployment run distinguishes HTTP 404/403/500 by status, a response from a network failure, timeout, invalid certificate, and successful retrieval. Road-only and business controls remain ineligible and retain existing provider behavior; their diagnostics make that fallthrough explicit.
