# LP108.10 — Harris edge termination and Newton timeout audit

## Decision

This is an audit, not a runtime repair. The single Newton HTTP 0/client timeout is **more likely transient than a demonstrated regression**, because Newton's local governed package is only 349,580 compressed bytes/10,488 records, its prior local load was 42.27 ms, it previously passed repeatedly, and the other 26 counties passed in the same deployment run. That is not proof: Newton remains `UNRESOLVED_LIVE_RERUN_REQUIRED` until isolated owner runs reproduce or clear it. Harris is reproducible locally as a CPU/wall-time-heavy outlier; the live HTTP 546 with no handler diagnostics does not identify the terminating layer.

No authenticated request was made during this audit. No package, certificate, Storage object, matching rule, selection rule, membership rule, or runtime behavior was changed.

## Harris operations and local LP108.9 profile

The deployed source fetches and bounds the certificate, parses and validates it, opens the authenticated package response, then performs the following for **all 1,452,427 records**: pull compressed chunks; count compressed bytes; update incremental SHA-256; pass every byte through a `TransformStream`; gzip-decompress; UTF-8 decode; append to `pending`; split on newline; skip blank lines; `JSON.parse`; normalize FIPS, house, road and (when supplied) city; compare ZIP; retain every match; and finally validate compressed length/digest before promoting provisional matches. It also builds result objects after validation. The representative was record 479,569, leaving 972,858 records (67.0%) parsed after the first match.

Measurements are one local Linux/Node 22 warm-filesystem observation, not deployed Supabase timings. The production-shaped Web Streams pass used a 64 KiB file source and the actual LP108.9 lookup function. Separate Node stream passes isolate work but are not additive because decompression, I/O and parsing overlap.

|---|---:|

| Actual process CPU | 13,654.63 ms (11,835.58 user; 1,819.06 system) |
| Peak RSS | 142,958,592 bytes (136.3 MiB) |

LP108.9 therefore lowered observed peak RSS from the reported prior approximately 372 MB path to 136.3 MiB locally (about 63% lower), while retaining a complete 308 MB decompression and 1.45-million-record parse. Memory is improved but not proven safe on the hosted isolate. The stronger remaining local signal is CPU/wall time.

`TransformStream` applies backpressure and the code does not call `tee()`. No unbounded application queue was found: only the current chunks, the usually sub-line `pending` tail, and matching rows are retained. `DecompressionStream` necessarily has an internal gzip window/input-output queues, but the observed 16 KiB output chunks and 136.3 MiB peak provide no evidence of whole-package buffering. This cannot prove the runtime implementation has no native hidden buffering.

The authenticated Storage HTTP branch returns `Response.body` directly, so the function consumes a genuine Web `ReadableStream` interface. Source inspection cannot establish whether Supabase's Storage gateway or its upstream object service materializes the object before exposing that body. Prove this externally with request-to-first-byte versus request-to-last-byte timing and Edge/Storage logs; do not infer it merely from `response.body`.

**Boundary classification:** CPU/wall-clock is most likely, memory is secondary but not eliminated, Storage/gateway behavior is unmeasured, and the exact live 546 cause remains unknown until platform logs correlate the request. The absence of handler diagnostics suggests termination before a JSON response completed; it does not prove whether that happened before handler entry.

## Supabase log inspection (owner only)

Use the hosted Dashboard; the currently available local environment has no Supabase CLI installed, and the supported CLI surface should not be guessed as a remote-log command.

1. Open the correct Supabase project, then **Edge Functions → `gridly-geocode` → Logs**.
2. Set an absolute UTC range spanning at least five minutes before and after the report's `requestStartTime`; filter to HTTP 546 and then HTTP 0's corresponding server-side time. Inspect both invocation and function logs.
3. Open each candidate invocation and record its platform request/invocation identifier, status, duration, function version/deployment identifier, region, and any shutdown/termination metadata. Do not copy authorization headers, query/address bodies, or credentials.
4. In **Logs → Logs Explorer**, select Edge Function gateway/invocation logs and function execution logs, filter `gridly-geocode`, the same UTC interval, deployment version, and (when displayed) the invocation/request identifier. Search event/metadata fields for `boot`, `shutdown`, `timeout`, `cpu`, `memory`, `isolate`, `uncaught`, and `exception`.
5. Compare Harris with a passing county immediately before/after it and the Newton timestamp. Export only bounded operational metadata with secrets and request bodies redacted.

Platform invocation metadata may reveal gateway status/duration and a shutdown/termination reason; function execution logs reveal worker boot or uncaught output only when the platform/runtime emitted it. Current application code has no safe handler-entry/stage logging, so silence cannot distinguish pre-handler termination from termination before logs flush. CPU exceeded, memory exceeded, wall timeout, and isolate termination are distinguishable **only if the platform supplied an explicit event or metadata field**. Do not translate HTTP 546 into a particular limit or claim a numeric Supabase limit without preserving a current official source alongside the evidence.

A diagnostic request ID is not required to perform the timestamp/function/deployment correlation above, so this audit does not add a header. If timestamps collide in the next implementation, add a random client identifier (no address content) to `certify-remote-runtime.mjs`, allow-list/echo it in `gridly-geocode/index.ts`, and include it in the ignored report and bounded handler log.

## Bounded alternatives (not implemented)

| Option | Memory / CPU | Integrity and fail-closed behavior | Artifact impact / complexity |
|---|---|---|---|
| 1. Continue one-request full scan | Bounded memory; maximum CPU and wall time | Current compressed SHA and gzip integrity both remain; fail-closed | No artifact change; already deployed; Harris evidence is poor |
| 2. Stop parsing after match, hash remaining compressed bytes | Lower parse CPU only if decompression is also bypassed | Compressed byte/SHA remains, but skipping `DecompressionStream` after the match means the gzip trailer/CRC and remaining deflate stream are not validated | No artifact change; moderate custom stream coordination; weaker gzip-integrity evidence |
| 3. Package-order-aware parsing cutoff, hash remainder | Potentially large CPU reduction when cutoff is early; bounded memory | Same limitation as option 2 unless the remaining gzip stream is still decompressed; cutoff itself must be certified | Requires certified ordering/cutoff metadata and builder/certificate changes; medium/high complexity |
| 4. Certified sidecar key → identity/range index | Very low lookup CPU and bounded memory; package hash still costs I/O/hash | Exact package SHA remains possible by consuming package; sidecar must be independently hashed, bound to package SHA/version, and fail closed | New private governed artifact, certificate schema/build/storage/runtime changes; high but clean complexity |
| 5. Partition Harris | Scales compressed/decompressed/parse work to one shard; bounded memory | Each selected shard can have exact byte/SHA/gzip verification; manifest must prove complete deterministic key-to-shard routing | Harris package/certificate and Storage artifacts change; high migration/deployment complexity |
| 6. Precomputed bounded certified lookup structure | Lowest request CPU; fixed bounded reads | Structure must bind normalized key, returned record, source identity, package SHA, normalization version, and completeness; fail closed on any mismatch | New private sidecar and certificate/build changes; medium/high complexity |

With the current **single stream → counting/hash TransformStream → DecompressionStream** topology, it is not possible to stop decompression while continuing to read/hash that same downstream stream: pulling compressed bytes for the hash also feeds them to `DecompressionStream`. Canceling or detaching decompression generally cancels upstream or forfeits gzip trailer/CRC validation. A `tee()` could hash one branch and cancel parsing on the other, but tee buffering can grow when branches run at different rates; after cancellation the hash branch can remain bounded, yet gzip integrity beyond the match is still unvalidated because it is no longer decompressed. Continuing decompression but discarding decompressed output preserves gzip validation and saves decoding/parsing/predicate CPU, not decompression CPU.

## Recommended next architecture and exact future file boundary

Do not spend another milestone optimizing a 1.45-million-`JSON.parse` single request as the primary Harris architecture. A **certified bounded lookup sidecar** is safer than ad-hoc early cutoff and less disruptive than replacing Harris with partitions. It should bind normalized exact keys to the governed record identity (or bounded byte-range/shard), bind its own byte size/SHA and the existing package SHA in the certificate, remain private, and fail closed. If package-level SHA must be recomputed on every request, the sidecar removes parse/decompression CPU but not the 57.7 MB download/hash; the next governance decision must explicitly choose that cost. Harris-only partitioning is the fallback if policy requires validating only original-format gzip artifacts per request and cannot authorize a certified lookup sidecar.
