# LP188.3 Statewide Community/Awareness Package Manufacturing Audit

## Decision

**Original LP188.3 classification: `REQUIRES_REVIEW — MANUFACTURING NOT STARTED`**

**LP188.3A resolution:** the minimum additive identity contract is now defined
in `Community-Packages/community-package-identity-contract.schema.json`. The
real certified LP188.2A outputs are known to exist in the governed Windows
workspace; their absence from this Linux checkout is only an environment
boundary, not evidence that the outputs do not exist. Statewide manufacturing
remains intentionally out of scope for LP188.3A.

LP188.3 stops after the required audit. The repository's current Community
Package contract is not identity-safe for the certified LP188.2A data, and the
four certified LP188.2A JSON inputs are not present in this checkout. Creating
254 payloads here would therefore require inventing a new contract and/or
reconstructing certified source data, both of which LP188.3 forbids.

No county package, runtime registry, activation manifest, deployment artifact,
address package, roadway package, crossing package, or protected launch
evidence was changed by this audit.

## Existing architecture discovered

1. **Package files.** `Community-Packages/<county-slug>/package-manifest.json`
   is the existing county unit. Liberty additionally has boundary and roadway
   GeoJSON assets.
2. **County structure.** A package manifest combines package status and asset
   flags with a `communities` array. Existing entries in that array are plain
   display-name strings.
3. **Schemas, manifests, and certificates.** The repository has the narrative
   `COMMUNITY-PACKAGE-SPEC.md`, the mutable
   `Community-Packages/county-manifest.json`, and per-county package manifests.
   No machine-readable community membership schema or certificate was found.
4. **Builders.** The documented builder flow names
   `Build-RegionalExpansion.ps1` and `Build-CommunityPackage.ps1`, but neither
   file exists in this checkout. County promotion tooling reads the legacy
   string array; it is activation tooling and is outside LP188.3.
5. **Naming.** Existing directories use lower-case county slugs and use
   `package-manifest.json`; county identity inside manifests is a county name.
6. **Serialization.** Existing per-county manifests contain UTF-8 BOMs,
   PowerShell-formatted JSON, and generated timestamps. They do not satisfy the
   requested timestamp-free, byte-deterministic governed payload contract.
7. **Validation/promotion.** The documented architecture describes temporary
   build validation followed by manifest update. The available county
   promotion scripts are coupled to runtime activation and cannot be reused by
   this manufacturing-only milestone.
8. **Runtime consumers.** `js/gridlyPackageRegistry.js` consumes registered
   community package metadata. `js/app.js` owns current operational awareness
   labels through `GRIDLY_COUNTY_REGISTRY.defaultAwarenessAreas`; this is a
   hard-coded, untyped, human-readable runtime model rather than a statewide
   Census-place package contract.
9. **Operational examples.** Liberty, Montgomery, and San Jacinto demonstrate
   named community arrays. Later operational county manifests frequently have
   empty arrays, so operational status does not establish a complete community
   membership contract.
10. **County identity.** Statewide governance elsewhere uses five-character
    Census county FIPS, but existing Community Package manifests identify a
    county only by display name.
11. **Community identity.** Existing Community Package manifests use display
    name alone. Runtime awareness configuration uses county-scoped labels/keys.
    Neither contract uses Census PLACE GEOID.
12. **Locality/display names.** Community strings and runtime labels are
    consumer-facing names with no separate canonical identity field.
13. **Duplicate names.** No existing Community Package rule preserves
    same-name places by PLACE GEOID. LP187 previously identified statewide
    same-name collision safety as uncertified.
14. **Incorporated places versus CDPs.** Existing package entries are untyped.
    No governed package policy for incorporated `C1`, inactive/nonfunctioning
    incorporated `C9`, or CDP records was found.
15. **Multiple communities.** Existing manifests permit multiple strings but
    do not encode one-to-many place/county membership or multi-county identity.
16. **Unincorporated awareness areas.** Runtime and the partial LP157 seed can
    represent recognized unincorporated labels, but these are not equivalent to
    Census PLACE membership and no statewide package policy is established.

## Blocking incompatibilities

### Certified inputs are unavailable

The required directory in this Linux checkout,
`Gridly-Source-Data/Processing/Census-Places/` and its four certified JSON
outputs are not mounted. The authoritative outputs exist in the governed
Windows workspace, and only the LP188.2A PowerShell producer is present here.
LP188.3 must consume those certified Windows outputs and must not replace
them by independently recomputing geometry or by trusting hand-authored
fixtures.

Required inputs:

- `texas-place-canonical.json`
- `texas-place-county-memberships.json`
- `texas-place-certification-summary.json`
- `texas-place-duplicate-names.json`

### Existing contract cannot represent the governed identity

The existing `communities: ["Display Name"]` contract cannot deterministically
establish PLACE GEOID, county FIPS, governed type, or multi-county membership.
Extending it with new object fields would be a new schema decision rather than
reuse of an established contract. In particular, no existing policy determines
whether `C9` records are included, excluded, or separately classified. The
required fail-closed result is therefore `REQUIRES_REVIEW`.

### Existing output convention is nondeterministic

Legacy manifests embed `generatedAt` and use a serialization format that is not
the governed LF/UTF-8-without-BOM convention used by current generated JSON
reports. Rewriting those manifests would touch operational package artifacts;
creating a parallel family would invent a second architecture.

## Decisions required before manufacturing

1. Approve an evolution of the existing Community Package contract that
   preserves county FIPS, PLACE GEOID, official name, governed type, and every
   certified membership without replacing existing operational asset metadata.
2. Explicitly govern `C9` treatment. The default must remain inclusion or
   fail-closed review; exclusion cannot be inferred.
3. Define whether Census places and non-Census unincorporated awareness areas
   share one typed collection or remain distinguishable within the same package
   architecture.
4. Mount or copy the exact four certified LP188.2A outputs into the governed
   source-data workspace available to the manufacturer.
5. Define the non-activation output location and its registry/certificate
   relationship without modifying current operational package manifests.

After those decisions and inputs exist, LP188.3 can implement temporary output,
structural validation, two isolated generations, byte comparison, promotion,
and exact 254/1,863/2,062 reconciliation. Until then, manufacturing or claiming
`PASS` would violate the milestone's fail-closed rules.
