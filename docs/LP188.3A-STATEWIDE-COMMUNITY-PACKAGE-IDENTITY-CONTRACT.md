# LP188.3A Statewide Community Package Identity Contract

## Classification

**`IDENTITY_CONTRACT_READY — STATEWIDE_MANUFACTURING_NOT_PERFORMED`**

LP188.3A approves the additive contract in
`Community-Packages/community-package-identity-contract.schema.json` and its
fail-closed construction rules in
`tools/lp188/community-package-identity-contract.mjs`. It does not manufacture,
promote, deploy, register, or activate a county package.

## Legacy schema and consumer audit

The on-disk legacy manifest identifies the county with `county` display text
and stores `communities` as an array of display strings. It also contains asset
status, notes, and build metadata. The promotion tool reads that array as
strings. The runtime package registry separately holds
`community.awarenessAreas` as strings, while `js/app.js` owns operational
selection through string-based `defaultAwarenessAreas`.

Repository consumers audited for this contract were:

- `tools/CountyPromotion/Promote-GridlyCounty.ps1`, which projects manifest
  `communities` into string awareness-area configuration;
- `tools/lp131/audit-statewide-readiness.mjs`, which counts manifest community
  strings;
- `tools/ProductionPackages/Build-GridlyProductionPackages.ps1`, which copies
  existing package manifests into production package work;
- `scripts/v814-county-automation-capability-audit.mjs`,
  `scripts/v815-bulk-county-preparation-orchestrator.mjs`, and related V816/V818
  audits, which test package existence/status rather than community identity;
- `js/gridlyPackageRegistry.js`, whose community metadata and awareness areas
  are currently shallow-copied/string-based; and
- `js/app.js` and its hierarchical-awareness regressions, which continue to
  own current operational selection behavior.

The precise weakness is that a display string cannot prove county FIPS, Census
PLACE GEOID, Census classification, or all certified county memberships. A map
keyed by name can collapse two different same-named places.

## Approved additive evolution

The evolved package payload retains `communities` unchanged as the legacy
string-only compatibility projection and adds four governed identity members:

1. `schemaVersion` identifies `gridly.community-package.identity.v1`.
2. `county` carries canonical five-character Texas `countyFips` plus
   `displayName`.
3. `censusPlaces` carries typed Census records keyed by eight-character PLACE
   `placeGeoid`, with display name, governed type, inclusion, consumer
   eligibility, and the complete sorted `countyMemberships` list.
4. `legacyAwarenessAreas` carries non-Census records with the existing
   county-scoped `legacyIdentity`, display name, and consumer eligibility.

No roadway, geometry, coordinates, timestamps, source paths, deployment state,
or product metadata are introduced by this identity contract.

### Backwards compatibility

The `communities` array remains an array of strings in the schema and is copied
without reinterpretation when supplied. Consequently, current operational
consumers need no code change and receive no new Census-derived areas during
LP188.3A. The richer collections are manufacturing/governance data until a
later, separately governed runtime migration explicitly consumes them.

This is additive coexistence (strategy A), not an automatic compatibility
projection from Census places. Automatically adding C1/CDP display names to
the operational string array would change runtime behavior and is prohibited
in this milestone.

## Identity and eligibility rules

### County

`county.countyFips` is the canonical county identity and must match
`^48[0-9]{3}$`. `county.displayName` is metadata only.

### Census place

`identitySource` is `CENSUS_PLACE`; `placeGeoid` is canonical identity and must
match `^48[0-9]{5}$`; `displayName` is metadata only. Package construction
rejects duplicate PLACE GEOIDs even when names differ and retains distinct
GEOIDs even when names are equal.

Every Census record has `includedInCensusFoundation: true`. Active incorporated
`C1` and CDP types have `consumerEligible: true`. Inactive/nonfunctioning `C9`
has `consumerEligible: false`, remains present, and is never dropped. The rule
is exclusively governed-type based; no place-name list exists.

### Legacy/non-Census awareness area

`identitySource` is `LEGACY_NON_CENSUS`. `legacyIdentity` retains the existing
county-scoped key mechanism and is in a separate identity namespace. A legacy
record has no `placeGeoid`; construction rejects a bare Texas PLACE GEOID in
`legacyIdentity` so it cannot masquerade as Census-derived data. Its display
name and consumer eligibility remain explicit and are not silently renamed.

### Multi-county membership

`countyMemberships` is a unique, sorted, non-empty list. A county package may
contain a Census place only if the package county FIPS appears in that list.
The same PLACE GEOID can therefore occur in every certified member county
without becoming multiple canonical place identities.

The explicitly non-certified structural Baytown fixture proves that PLACE
`4806128` can be represented in both Chambers (`48071`) and Harris (`48201`)
with one canonical identity and the complete membership list. This is a test of
the general rule, not a production special case.

## Runtime and manufacturing result

Runtime compatibility is preserved because no runtime file or legacy package
manifest was changed. No compatibility projection adds Census places to the
consumer surface. No generated county directory exists, no LP188.2A output was
read or fabricated, and no Census geometry was recomputed.

The contract is ready for deterministic statewide manufacturing on the Windows
environment once the real certified LP188.2A JSON outputs are supplied to the
manufacturer. LP188.3 manufacturing must still prove exact 254-county,
1,863-place, and 2,062-membership reconciliation before promotion.
