## C–E. Hash, county set and geometry comparison

Byte comparison applies only to identical file formats. The LP137 FeatureCollection, LP148 package and LP1904 package have different metadata/serialization and different file hashes; their **geometry is semantically and coordinate-exactly equivalent** by FIPS. The cartographic source is materially different, not merely differently encoded. The LP104 table has no local row data and is NOT COMPARABLE. The shared runtime and frozen responder files are not byte identical as whole files.

Read-only comparison found for LP137, frozen and shared runtime: exactly 254 rows, 254 unique FIPS matching the frozen set, zero missing/extra/duplicate/out-of-state FIPS, 254 Polygon parts, 254 closed rings, 604,979 2D coordinate pairs, zero out-of-range/nonfinite coordinates, and identical statewide bbox [-106.645646, 25.837048, -93.508039, 36.500704]. The ordered type and coordinate arrays match **254/254** for LP137→frozen and shared runtime→frozen; no normalization, rounding or orientation change was needed. County names match for these three sources. The 28 older per-county files have no missing FIPS relative to their own subset, but are not statewide complete; all 28 differ from the frozen polygon arrays. The cartographic 254 FIPS set matches, but its 254 tiny boxes cover bbox [-106, 25, -95.1, 30.4], every name differs, and every polygon differs. Syntactically complete FIPS cannot rescue fabricated geometry.

Exact ordered coordinate equality proves current polygon identity more strongly than bbox or vertex counts. It does **not** establish global topology, nonoverlap, legal source licensing, or deployed PostGIS equivalence. Polygon-versus-MultiPolygon wrapper changes in a database may require a geometry-aware comparison rather than byte or WKB hash equality. Shared-boundary test points remain mandatory.

The shared geometry is fit **with adaptation** for responder jurisdiction: canonical FIPS, full polygons, exact frozen equality and reproducible hashes are present locally. The [consumer resolver](../../js/app.js) reports an inclusive, deterministic lowest-county-id boundary policy. The [Phase 3 responder SQL](../../db/responder-local/003_phase3_county_authority_apply.sql) rejects any ST_Touches result, requires exactly one ST_Contains match, and fails closed on overlaps or an unapproved/stale county. A production server-side query must preserve strict point-in-polygon, shared-edge denial, exact version binding, current org/authority checks and no rectangle/nearest-county fallback. Geometry reuse is **not resolver reuse**.

## H–J. Duplication, shared-source risk and immutable binding

A responder-specific 254-row geometry table duplicates roughly 604,979 coordinate pairs conceptually, adds its own loader, GiST/RLS, version schedule and backup, and risks drifting from the consumer/LP137 source. The local Phase 3 fixture additionally copies a polygon into each organization authority row. Storage cost in PostGIS is not inferred from JSON file bytes, but duplicate rows and copied grants still increase audit and rollback complexity. A second catalog is justified only if a demonstrated, unfixable shared-source integrity or governance defect prevents immutable versioning; none was established locally.

Shared reuse has a real counter-risk: a consumer geometry refresh, display simplification or in-place SQL update could silently alter authority. The existing tracked public boundary table has a mutable county_fips primary-key shape and boundary_version text but no proven immutable version row or source hash. **Do not reference an unversioned live row for authorization.** The least duplicated target design is an immutable *shared* geometry-version row keyed by county_fips plus governed source/package version and hash, with one spatial index and historical versions retained. Each responder organization_authorities record stores its county_fips, independent authority_version, immutable geometry-version reference, source/package hash, effective interval, decision actor, status/revocation history and audit receipt; it does not need a full polygon copy. If the existing table can be proven complete and adapted to append-only versioning, use it. Otherwise create a governed shared versioned representation from the same approved source; do not create a parallel responder-only authority catalog by default.

The activation transaction must compare the grant's pinned source/version with the currently approved responder source version, use only that immutable geometry, and fail closed when versions disagree. A source change does not auto-widen an existing grant. Reapproval/revocation is a governance operation, with old geometry retained for audit and rollback. The source manifest flags remain false until separately authorized; local equality is not an activation decision.
