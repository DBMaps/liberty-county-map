## Identity and claim trust

Production subject is the **verified `auth.users.id` UUID**. Inside a trusted Supabase request, `auth.uid()` may identify that subject; no client `actor_id` or local `session_user` may substitute. A private server-controlled identity/eligibility link keyed by the UUID should hold disabled state and an invalid-before cutoff or session epoch. A narrow FK to `auth.users` is a candidate for this *live link only*, contingent on production deletion/restore semantics. The source of an active session is a validated access token plus a currently valid server-side binding/cutoff; the local boolean is not a production session. `aal1` and `aal2` are verified Auth session assurance, not browser fields. Exact claim names, factor lifecycle, access-token invalidation and `auth.uid()` behavior must be proven against the actual project before implementation.

| Input | Trust class | Enforcement |
| --- | --- | --- |
| Verified JWT `sub`/UUID | SAFE TO TRUST FROM VERIFIED JWT | Use `auth.uid()` as identity, then require a live enabled identity link. |
| Verified JWT `role` | SAFE TO TRUST FROM VERIFIED JWT | At most authenticated gateway audience; **not** agency/Governance role. |
| Verified JWT `aal` | SAFE TO TRUST FROM VERIFIED JWT | Require `aal2` for privileged routes, plus live factor/session freshness; an old signed `aal2` is insufficient after reset. |
| Verified JWT email | SAFE TO TRUST FROM VERIFIED JWT | Contact or invite-match hint only; verify current email on redemption; not durable authorization. |
| App role, membership state, organization ID/state, county authority, governance grant, publishing gate | MUST RECHECK IN LIVE DATABASE | Resolve against current private rows on every read/command. One active org is enforced live. |
| Update author | MUST RECHECK IN LIVE DATABASE | Compare immutable server-stamped author UUID to current verified subject where action requires authorship. |
| Session epoch/invalid-before | MUST RECHECK IN LIVE DATABASE | Compare server-controlled cutoff/binding to verified session issuance or identifier; never accept a client epoch. |
| Client actor, role, organization claim, assurance, factor status, eligibility or epoch | MUST NEVER COME FROM CLIENT CLAIM | Reject or ignore for authorization. A requested resource ID is only a scoped selector. |

This retains the [frozen contract](RESPONDER-V1-CONTRACT.md), [role matrix](RESPONDER-V1-ROLE-MATRIX.md), [state machines](RESPONDER-V1-STATE-MACHINES.md), [command contract](RESPONDER-V1-COMMAND-CONTRACT.md) and [owner decisions](RESPONDER-V1-OWNER-DECISIONS.md). The owner already approved authenticator-app TOTP/`aal2` for **all** dashboard roles, including VIEWER, and all agency mutations. AAL1 may reach only a minimal identity/invite/factor bootstrap endpoint. It cannot read membership details, redeem an invite, enter the dashboard, or execute agency/governance commands.

## Production assurance and enrollment

Every dashboard entry and bounded read requires verified identity, current fresh `aal2`, enabled identity, one active membership and a verified active organization. Invite redemption **and membership activation** require the target's fresh `aal2`, token digest/expiry, exact identity binding, current inviter/org checks and one-active-org constraint in one atomic operation. AGENCY_ADMIN invite/role/suspension/revocation actions require the actor's fresh `aal2`, live admin role, target-state/last-admin checks and audit. Agency create/edit/submit/return/activation requires fresh `aal2`, current role/org/authority, revision and replay checks; `activate_road_closed` additionally requires an independent, distinct qualified activator. GRIDLY_ADMIN verification, county governance, organization suspension/reinstatement and lost-admin recovery require fresh `aal2` and a separate live governance grant. No agency role grants governance authority.

First login sequence for an invited user: authenticate an individual account; give only a bounded eligibility result; enroll an authenticator TOTP factor; verify the factor and obtain a **new, verified `aal2` session**; bind the invitation to that exact UUID and verified target email; atomically redeem and activate membership; then run ordinary dashboard entry. Existing eligible users challenge their factor before dashboard entry. A wrong/expired factor or missing fresh `aal2` leaves the invite and membership unchanged and returns a bounded denial. An unknown or uninvited account gets no organization roster or identity enumeration. Account provisioning/delivery occurs before this sequence through an approved path; the current fixture's pre-existing target UUID must not be mistaken for an Auth provisioning implementation. The provisional seven-day invite lifetime remains an owner gate.

## Factor recovery, offboarding, and stale tokens

**Auth factor recovery** for a lost phone/factor, no remaining valid factor or suspected compromise needs independent identity proof and authorized human review, a durable reason/evidence receipt, temporary disabling of the live identity link, invalidation of earlier sessions, controlled factor reset, a newly verified TOTP factor, and a fresh `aal2` session. A compromise may also require membership suspension and incident escalation. Email possession alone, weak questions, or self-service bypass cannot grant dashboard access. The owner must approve the identity-proof/reviewer SOP before rollout. **Lost Agency Admin recovery** is a different Phase 2/6 governance action: independently verify the organization and admin vacancy, use a qualified GRIDLY_ADMIN actor, and invite a currently eligible target. It does not recover an Auth factor, auto-restore a revoked authority, or reactivate withdrawn posts. The target still needs fresh `aal2` before redemption.

Auth sign-out/revocation should be used where supported, but correctness cannot depend on immediate access-token expiry or refresh. Every privileged read and command rechecks live identity link, membership, org, governance grant, authority and gate. Phase 2 `session_epoch` remains useful as a **server-controlled invalidation concept**, not a JWT authorization claim. For a signed stale `aal2` after factor reset/downgrade, a private invalid-before timestamp compared with verified token issuance, or a server-side binding to a verified session identifier, must deny the old token. All factor changes must pass through this controlled invalidation path or a proven Auth event synchronization path; an out-of-band reset that leaves the link active is a launch blocker. The exact stable claims and reset event propagation require production capability tests; if they cannot be proven, fail closed and redesign before launch. Epoch increments on suspension, revocation, recovery and identity deletion can invalidate operation sessions/receipts, but operation replay must still bind the verified actor, organization, action and payload digest. No replay may create false duplicate events.

| Stale JWT case | Live defense |
| --- | --- |
| Role changed | Current membership role; no role authorization from JWT metadata. |
| Membership suspended or revoked | Current active membership and eligibility link; denial takes effect without refresh. |
| Organization suspended/unverified | Current organization eligibility; Phase 6 withdrawal remains effective. |
| County authority revoked | Current effective approved authority, scope/version and geometry. |
| Publishing gate disabled | Current gate at activation and consumer projection; no stale grant. |
| MFA factor reset/downgrade | Verified `aal2` **and** current server-controlled session cutoff/binding; old signed `aal2` rejected. |
| Auth user deleted | Absent/disabled live identity link; historical evidence remains. |

## RLS, commands, and governance adapter

Replace Phase 4 `session_user`/private fixture binding with `auth.uid()` for the subject and a narrow helper that checks verified `aal2`, session freshness, active identity, active membership, role and verified active org. RLS may directly compare row owner to `auth.uid()` **and** use private helpers for live eligibility; direct `auth.uid()` alone is inadequate for suspensions. Resolve current organization through the unique active membership, not a client claim. Separate governance helper checks the private active governance-user grant keyed by Auth UUID and fresh `aal2`, without requiring agency membership. Keep governance reads/routes isolated. Design helpers with fixed `search_path`, minimal grants, explicit function owner and no unnecessary `BYPASSRLS`; test FORCE RLS behavior, recursion, row-count/performance and security-invoker view access in the actual production schema. A helper that queries a table whose RLS calls the same helper will recurse; use a carefully owned narrow boundary and review the query plan. Do not copy local fixture roles into deployment.

Phase 5 `create`, `edit_own_draft`, `edit_active_update`, `submit`, `return`, `activate_non_closure` and `activate_road_closed` must all derive actor from verified Auth context, check fresh `aal2`, resolve current org/role from live membership, compare supplied update ID to that org, check current county authority and revision, then bind operation token/receipt to subject+org+action+payload. A request `organization_id` can at most confirm the resolved org; it cannot pick authority. Remove any production signature parameter that purports to be authoritative `p_actor`, `actor_user_id`, `db_role`, `assurance`, `session_active`, `session_epoch`, `member_role`, or `organization_id`. Keep target resource IDs, expected revision and operation token as untrusted inputs subject to scope and validation. Governance commands similarly derive GRIDLY_ADMIN actor from verified Auth, check separate live grant and `aal2`, and treat target organization as a resource selector, not caller identity. The command layer, not dashboard affordance hints, remains authoritative.

## Invitations, identity changes, deletion, and FK policy

Invites start as normalized email targets with random raw token delivered only through an approved channel and a stored digest, expiry, use state and inviter evidence. The current [Phase 1 schema](../../db/responder-local/001_agency_private_apply.sql) has no raw token and stores historical UUIDs without Auth FKs. Production may create/invite an Auth account before redemption or match an existing verified account. On redemption, atomically bind the **exact current Auth UUID** to the invitation and target membership, require verified current email equal to the target (or a governed reissue), fresh `aal2`, digest match, unexpired status, unique account/one active org, current inviter and org eligibility, then consume once. A stale JWT email alone cannot prove current email; the trusted path must obtain current verified Auth contact state or use a previously governed UUID binding and reissue after email change. A token held by another account fails without consumption. Duplicate accounts for the same email or one user in another active org fail closed for governed resolution. Invite delivery and account creation require an approved SMTP or bounded manual path; neither is in local code.

Membership binds to `auth.users.id`, never mutable email. Email change does not transfer role or authorship. An unredeemed invite whose target email changes must be reissued or governed-rebound; an old address's new owner cannot inherit membership. Existing active membership remains with its original UUID, with contact verification handled separately. Deleting an Auth user must disable/remove the live identity link and block unexpired tokens while retaining UUIDs and rows for memberships, updates, reviews, governance events, audit events and receipts. Do not cascade historical evidence from `auth.users`. Candidate FK policy: optional narrowly scoped `auth.users.id` FK on a disposable live eligibility link, with delete affecting only that link after production delete/restore semantics are verified; **no cascading direct Auth FK** on current/historical membership, invite binding, author, reviewer, governance actor, event actor or receipt actor. Current access additionally requires the live link and Auth validity proof. If a reliable FK/live absence check is unavailable, use controlled deletion plus tombstone/reconciliation and block launch until stale deleted-user JWT denial is demonstrated. This preserves restore/replay portability and immutable history.

## Privilege and browser boundaries

Client-safe authenticated operations are only Auth sign-in/TOTP challenge and bounded responder reads protected by JWT, RLS and live checks. Agency mutation uses narrow database command functions; governance-only functions use the separate grant. Security-definer code needs ownership/grant review and must not turn JSON claims into authority. A server-only service-role credential may be justified for **Auth administration** such as controlled account provisioning or factor reset if the platform requires it, behind a dedicated authenticated, audited, rate-limited server endpoint. It never belongs in browser code or ordinary dashboard reads/commands. The unrelated geocode service-role use does not change this boundary.

For `responders.gridlygo.com`, isolate private routes from the public PWA service-worker scope and caches; private HTML/API responses require no-store, and secrets/tokens must not enter URLs, logs, analytics or persistent app caches. Choose session persistence only after the owner resolves shared-workstation risk; do not assume SDK defaults are the responder policy. Logout clears browser Auth state and private UI state and attempts server session invalidation, while live eligibility/freshness checks continue protecting against stale tokens. Browser autofill and remembered-device behavior need threat review. No inactivity timeout is frozen, so none is asserted here.

Dashboard flow: individual sign-in → verified UUID → narrow eligibility bootstrap → fresh `aal2` challenge → live identity, one active membership and verified active organization → bounded context/queue/map/inspector. An `aal1` session sees only MFA bootstrap; unknown/not invited, revoked, no active org, suspended org and unverified org receive bounded denials without roster detail. Governance uses a **separate protected route on the same proposed host**, with individual Auth accounts, fresh `aal2` and current private governance grant; it does not appear as an agency dashboard role. This route is a design recommendation, not a hosting deployment decision or paid-service requirement.

No responder login brute-force, MFA verification, recovery or account-enumeration controls are implemented in this local repo. Production must verify platform rate limits, MFA enrollment/challenge and recovery safeguards, token invalidation and audit hooks. Add bounded endpoint throttles for invite digest attempts, bootstrap and recovery using existing infrastructure if platform controls are insufficient; preserve generic errors and operation-token replay protection. Never invent a paid anti-bot dependency. Invite digest entropy, expiry and one-use consumption must be tested against guessing/replay. Abusive recovery attempts need reviewer escalation and receipts.
