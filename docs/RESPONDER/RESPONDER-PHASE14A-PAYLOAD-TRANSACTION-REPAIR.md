# Phase 14A: transaction-neutral county payload repair

This is a **local-only** repair. Phase 13 successfully certified the frozen 254-county dataset and its disposable PostgreSQL rehearsal. Phase 14 correctly stopped before a production write: the Phase 13 rehearsal SQL owned `BEGIN` and `COMMIT`, while Phase 14 required separate certification and a commit decision in the same open transaction. No accepted production backup/recovery checkpoint or recovery owner had been established. Phase 14A preserves that history and separates the data payload from the executor's transaction. No production service was accessed in this phase.

## Historical evidence and new payload

The unchanged [Phase 13 rehearsal SQL](../../db/responder-local/phase13_county_population_rehearsal.sql) is 13,965,684 bytes with SHA-256 `9e17bb6a0f08580aabcc4943ab9b3bdda6f41e7205a78a7dab8d696a8037815e`. It has a top-level `BEGIN` and final `COMMIT`, and no top-level `ROLLBACK`; it remains historical certification evidence, not the payload for a production retry.

The new [transaction-neutral payload](../../db/responder-local/phase14a_county_population_payload.sql) contains exactly 254 FIPS-sorted `INSERT INTO public.gridly_texas_county_boundaries` statements and no transaction control, DDL, other DML, conflict handling, connection details, or credentials. It is outside production migration history. Each statement uses the Phase 13 `ST_GeomFromGeoJSON` → `ST_SetSRID(...,4326)` → `ST_Multi` transform, with the same certified Polygon coordinates, no simplification, buffering, rounding, or ring reordering. The [generator](../../tools/responder-local/build-phase14a-county-payload.mjs) reuses the Phase 13 frozen-source validator; it emits no timestamp. Two independent generations returned identical size and SHA-256, and the contract test compares the complete bytes.

The frozen Git source SHA-256 is `6c6eeb549bb5e03d79efbc4d421783c06988c81c0f728c79add32f8c219e3d49`; its 254 unique FIPS have digest `7e80dd17d4d295d904f986a193ab259850e607c6bdfde3a7454e9af5a54a2092` and contain 604,979 coordinate pairs. The new payload is 13,965,052 bytes, SHA-256 `464565b291946ff12e948d683e402c83caa39e2737748996f669fa2327a25a9e`. Its generator version is `responder.phase14a.transactionNeutralPayload.v1`. ## Executor-owned transaction

A future separately authorized owner/admin session must obtain an accepted recovery checkpoint, then start an explicit transaction and take `SHARE ROW EXCLUSIVE` on only the target county table. It must recheck that table still has zero rows and that schema, grants, trigger, RLS, index, migration, and control preconditions remain valid **after the lock**. Only then may it execute the exact hash-verified payload on that same connection. The payload cannot commit or roll back.

The executor must keep the transaction open while checking 254 rows, 254 exact FIPS, no nulls, valid MultiPolygon/SRID 4326, 604,979 points, approved version, source/payload provenance and an ordered table digest, strict Liberty–Chambers boundary behavior, GiST index, unchanged migration/control evidence, and absence of unrelated writes. Only a complete pass permits one `COMMIT`; every other path issues `ROLLBACK`. The empty-table precondition is mandatory even though a primary-key collision would also fail. There is no upsert, overwrite, merge, or no-op branch for a populated target. A fresh read-only transaction must then repeat certification and match the in-transaction digest. See the [repaired retry runbook](RESPONDER-PHASE14A-PRODUCTION-COUNTY-RETRY-RUNBOOK.md).

Local PostgreSQL/PostGIS disposable tests prove an intentional rollback after 254 visible in-transaction rows, a deliberately failed post-insert/precommit certification with explicit rollback, a successful commit followed by fresh read-only verification, and rejection of a nonempty target. Sentinel rows for reports, feedback, history/control-like objects, and migration history remain unchanged. The SQL token scan ignores comments and quoted geometry strings and rejects transaction-control, DDL, forbidden DML, conflict handling, and alternate mutation targets.

## Recovery checkpoint gate and production limits

The [empty recovery evidence template](../../reports/responder/responder-phase14a-recovery-checkpoint-template.json) is **not** evidence of an existing backup. Before a future retry, an owner must accept a recent backup or PITR point with a timestamp preceding the write, target-database/table coverage, known restore method and operator, referenced recovery runbook, confidence in restoring the prepopulation state, and no unresolved backup degradation. Any unknown or unacceptable field stops the write. Phase 14A does not assume an entitlement or invent a checkpoint.

The local fixture uses PostgreSQL 17 and local PostGIS 3.6.2. Phase 12/14 read-only production evidence recorded PostgreSQL 17.6/PostGIS 3.3.7. The payload uses only the same geometry construction functions as Phase 13; production 3.3.7 behavior still requires the later separately authorized transaction and postcommit proof. The future executor is a server-side owner/admin only. The payload adds no public RPC, browser path, permanent loader grant, Auth capability, RLS change, or migration. P12-01 and B03 remain open; county population does not authorize responder activation or publishing.
