# Responder Phase 3: local county authority certification

This is a disposable PostgreSQL/PostGIS fixture, not a Supabase migration or a production RPC. It implements the county-authority precondition for later agency commands. It does not create drafts, publish updates, expose consumer data, or enable the agency publishing gate.

## Certified source and loading

The source is `assets/location-resolution/gridly-authoritative-texas-county-geometry-v1.json` at the Phase 2 baseline commit. The frozen SHA-256 is `6c6eeb549bb5e03d79efbc4d421783c06988c81c0f728c79add32f8c219e3d49`, matching `reports/responder/responder-v1-county-authority-manifest.json`. The loader reads the committed Git blob bytes, not a Windows line-ending-converted working copy. It checks byte length, schema/package versions, all 254 canonical FIPS, unique county IDs, Polygon type, closed rings, and finite in-range two-dimensional longitude/latitude coordinates before writing. A single local transaction loads all 254 rows through `ST_GeomFromGeoJSON` and assigns SRID 4326. PostGIS then validates each polygon. The source itself does not declare a CRS; EPSG:4326 lon/lat is the frozen manifest's explicit local assumption, certified here, not inferred from a client claim.

The private `county_geometry_catalog` contains **source polygons only**. Its 254 rows do not grant any organization statewide authority. The catalog is immutable after load, its FIPS are limited to the 254 Texas odd-numbered county codes, and its source hash/schema/package columns are frozen. Only a verified organization's explicitly approved per-county row in `organization_authorities` is a grant. A local guard requires authority geometry and provenance to match the catalog. The Phase 1 approved-authority guard preserves geometry, hash, county, version, approver and approval time; it permits approved-to-revoked transition but never deletes history. The existing unique approved `(organization_id, county_fips)` index permits one current approval, and the version guard requires each subsequent version to increase. The Phase 3 approval fixture requires an eligible, active synthetic Gridly admin at aal2, a verified organization, and a complete catalog; it appends a governance event. It issues no production receipt claim.

## Exact authorization predicate

`phase3_authorize_point` is local-only and takes an explicitly supplied synthetic actor. A production implementation must derive that actor from trusted Auth context. The function requires active eligible aal2 identity, active same-organization membership in RESPONDER, SUPERVISOR, or AGENCY_ADMIN, and verified/active organization state. A suspended organization or member returns `suspended`; inactive, revoked, unverified, wrong-organization, or inactive-session cases return `forbidden`.

The candidate must be a valid, nonempty, finite, in-range 2D `Point` with SRID 4326. Null, nonpoint, and wrong-SRID input returns `invalid_request`. The server checks the complete catalog, rejects a point for which **any** county `ST_Touches` is true, then requires **exactly one** county `ST_Contains` result. A shared boundary, polygon overlap, or gap fails closed as `out_of_scope`; no buffer, nearest-county inference, or coordinate rounding is used. A point extremely near a boundary is accepted only when it is strictly inside exactly one county and does not touch any county boundary. The approved effective authority for the resolved county must also strictly contain the point. There is no municipal or district polygon proxy.

Optional client FIPS, authority UUID and version are comparison claims only. If supplied, each must match the server-resolved FIPS and current effective approved authority. Unknown FIPS, PLACE GEOIDs, another organization's authority, stale UUID/version, future, expired and revoked grants return `out_of_scope`. The bounded accepted response contains only `status`, `county_fips`, `authority_id`, and `authority_version`; denial responses contain only `status`. The local function does not mutate agency updates, create receipt claims, or grant public visibility.

## Fixture and contract boundary

Run the Node test only with explicit `RESPONDER_LOCAL_PGBIN`, `RESPONDER_LOCAL_PGPORT`, `RESPONDER_LOCAL_PGUSER`, and `RESPONDER_LOCAL_PGDATA` pointing to a unique `gridly-responder-phase3-*` cluster beneath Temp on localhost. The test verifies the server's actual `data_directory` before creating a unique test database, applies Phases 1–3, loads the certified source, uses synthetic identities and organizations, then drops schema/fixture roles and the database. The cluster directory is stopped and removed separately by the operator after verifying it contains no fixture databases or roles. No Supabase environment or remote access is used.

`reports/responder/responder-phase3-vector-map.json` keeps the nine fully executable Phase 2 vectors and records eight Phase 3 authority subchecks. Those eight frozen vectors also require a draft or approval command, business event, and/or receipt claim; they are **not** represented as complete Phase 0 vector executions. Their full command behavior remains deferred to Phase 5. The municipal approval denial is a future negative gate only: municipal geometry and jurisdiction are excluded from county-first V1. Phase 4 production security/RLS work is not started here. The agency gate remains false, consumer privacy/source separation and community-reporting separation are unchanged.
