# Phase 6 local governance and organization verification

This phase is a disposable PostgreSQL 17.10/PostGIS 3.6.2 fixture. It is not a production RPC or Auth integration. Apply `db/responder-local/006_phase6_local_governance_apply.sql` after Phases 1–5. The synthetic PostgreSQL login is bound to a live `GRIDLY_ADMIN` identity through Phase 4; the command never accepts an actor ID from the request. Its non-login definer uses `BYPASSRLS` only inside the disposable fixture. Agency roles receive no `EXECUTE`, DML, or raw governance evidence grant.

The `phase6_governance_command(jsonb)` envelope carries `contract_version`, action, UUIDv4 `operation_token`, `organization_id`, `expected_revision`, and an action-specific object. The command rejects unknown keys and requests over 4 KiB. `organizations.governance_revision` is the local optimistic-concurrency revision; each accepted action advances it. The organization `operation_epoch` advances on suspension, verification revocation, and reinstatement. Reasons are mandatory and bounded to 1,000 bytes. Denials use frozen bounded status codes, except that a direct SQL privilege denial remains outside the command result because agency roles cannot execute this governance function.

Verification follows `requested → pending_review → verified/rejected`, with `start_verification_review` required before either decision. A verified decision requires an explicit independent official callback flag, initial-admin review flag, bounded evidence reference, and Gridly review reason. Those flags are recorded as reviewer assertions in an append-only `organization_verification_events` row, not inferred from an email address, invite, membership, agency name, or authority. The verification event carries a correlation ID in `method_reference`; a matching governance event and separate receipt carry the same operation. Rejection is terminal for that claim. A new claim after rejection or revocation requires a new governed record and is not implemented here. `revoke_organization_verification` moves verified to revoked, suspends operation, and withdraws effective active posts atomically. Verification does not activate the organization or enable publishing.

`activate_organization` requires verified status, current approved county authority, and an active eligible AGENCY_ADMIN identity. `suspend_organization` increments the operation epoch and changes operation state to suspended, which immediately blocks Phase 4 private access, Phase 5 commands, and Phase 3 authority use. It also changes every currently effective active `AGENCY_OFFICIAL` update to `withdrawn`, increments each revision, and appends an `update_withdrawn` event with the governance correlation ID in the same transaction. Already expired stored active rows are effectively terminal under the frozen Phase 1 lifecycle trigger and cannot be revised; they are already hidden by effective-expiry logic. Historical authority, membership, post, and audit rows remain. No other source family is changed. `reinstate_organization` requires valid verification plus fresh authority/admin checks; old withdrawn posts stay terminal and a revoked authority stays revoked. The independent `agency_publishing_enabled` gate remains false throughout governance actions.

`approve_authority` requires an active verified organization, complete 254-county catalog, canonical Texas county FIPS, matching certified source SHA-256 and schema version, an advancing authority version, valid effective interval, and a review reason. The full polygon is copied from the immutable county catalog; client geometry is never accepted. A municipal PLACE presentation point explicitly returns `out_of_scope`; no municipal authority is created. `revoke_authority` marks the version revoked, preserves its provenance/history, and atomically withdraws affected currently effective active updates. New authority requires a higher explicit version.

Governance tokens use a **separate** `governance_operation_receipts` table, not the Phase 5 agency receipt domain. The server hashes canonical UUID bytes and canonical request content; exact replay returns `already_processed` with only the correlation ID. Token reuse with a different payload returns `invalid_request`. Receipts, verification events, and governance events are append-only. An injected failure in the local suite proves organization, update, event, and receipt effects roll back together. Rejected commands create no accepted receipt or business event.

`recover_lost_admin` checks an active verified organization, separate live aal2 Gridly governance identity, review reason, and independent-contact assertion before calling the Phase 2 recovery helper. Phase 2 preserves revoked membership history and its own audit event; Phase 6 adds a correlated governance event and receipt. Suspended organizations cannot use this wrapper. Neither recovery nor Gridly governance identity grants agency publishing rights. The Phase 2 trusted owner-only helper remains a local fixture and must not be exposed as a production RPC.

The Phase 6 suite exercises local checks for replay, direct-write denial, role separation, evidence privacy, atomic rollback, verification, authority, suspension, reinstatement, recovery, and a final false publishing gate. Fixture activation occurs only in a disposable local database and the gate is restored false immediately. Phase 1–5 regressions and the frozen contract runner remain separate checks.

The Phase 6 vector map marks 3 new full vectors: N33 (municipal proxy fail-closed), P14 (independent verification with event/receipt), and P15 (certified county approval with event/receipt), for 45/54 complete. N26 remains deferred because agency roles receive SQL permission denial rather than the frozen bounded `forbidden` result; granting them `EXECUTE` would violate the governance boundary. N34 remains deferred because no owner-approved publication-rate threshold exists. P18 has atomic backend withdrawal, but the frozen `publicVisibilityResult=hidden` cannot be observed until the consumer projection exists. Two dashboard and four consumer vectors remain deferred. No publication-rate policy or consumer projection is invented here.

Production deployment is explicitly deferred. This phase does not access Supabase, production Auth, remote data, live verification, email, dashboard, consumers, Cron, or agency publishing. The final local value of `agency_publishing_enabled` is false.
