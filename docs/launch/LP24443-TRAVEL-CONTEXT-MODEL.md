# LP244.43 — Travel context model

Audit baseline: `647c85a30d042a90276c3915ba92538df78ddf1c`, 2026-09-21. **Design only.** File/line references below address that unchanged baseline. Static source inspection and existing tests establish repository behavior, not physical-device certification or live source availability.

## 1. Home Area ownership (request parts 1–3)

`js/app.js:18600` defines `gridlyHomePersonalizationV1`. `gridlyReadHomePersonalizationRecord` (18667) validates on read; `gridlyBuildHomePersonalizationRecord` (18679) includes schemaVersion, ZIP, countyId/name, communityKey/label, awarenessAreaKey, consumerLabel, identityType, canonicalRegionId, resolutionStatus/method, sourceVersion and confirmedAt. `gridlyApplyConfirmedHomePersonalization` (18681) validates, persists, calls `saveGridlyHomeTownPreference`, updates profile/settings/active county, synchronizes awareness and providers, focuses the map, optionally completes onboarding, and restores prior storage on failure.

Compatibility storage is **not disposable**: `gridlyHomeTown`, `gridlySettingsV1` (17512), `gridlyUserProfileV1` (19553), welcome/walkthrough keys, and canonical Home all participate. `gridlySavedPlacesV1` and `gridlySelectedPlaceIdV1` (19551–19552) are separate saved route destinations; a saved place named Home is not the complete Home Area identity contract. `gridlySmartAlertsV1` (17508) is another preference record.

Canonical PLACE is retained through `PLACE_GEOID`, placeGeoid, membership FIPS, and a separately governed operational county. `gridlySaveCanonicalMultiCountyPlaceHome` (102415) refuses absent/invalid explicit operational membership; it never chooses the first membership. `getGridlySelectedAwarenessArea` (48555) re-derives persisted canonical identity, membership and operational projection before falling back to community settings/profile. This is startup rehydration authority, not simply a transient selected-place getter. `gridlyLp240ResolveGovernedHomeIdentity` (18616) also preserves governed non-PLACE communities; San Antonio regions have their own identity (17734). Do not force every community into a PLACE or county-wide fallback.

Home consumers include settings (101898, 102250), profile/walkthrough (47838, 48718), local reports and counts (`gridlyGetLifecycleCorrectActiveCommunityRecords`, 3136), KBYG canonical awareness revisions (3275, 3292), crossings, DriveTexas selected-awareness ownership (127792), and weather. `getGridlyHomeTownAwarenessAnchor` (48718) calls the selected-awareness getter. `gridlyResolveGovernedWeatherPoint` (48524) accepts only governed registered areas/canonical focus, refuses county-wide/fallback areas, and by default reads that same getter. `gridlyWeatherLiveConnector.js:26` calls this resolver without a temporary context.

**Exact coupling:** a global getter named selected awareness prioritizes persisted Home. Moving the map or setting a destination is insufficient to replace it. Calling the Home save path to work around this would overwrite user preference and rehydration authority. Writing temporary data then restoring Home is unsafe under asynchronous fetches, cache publication and app termination.

## 2. Destination/search reuse

`getGridlyCanonicalSearchTerms` (40062) and `resolveGridlyStatewideCanonicalBarePlaceQuery` (40181) support canonical place discovery. The destination input is `gridlyAddressSearchInput`; `gridlySearchAddress` (95959) composes local seeds, runtime POIs and governed geocoding. `js/lp101-search-quality.js` supplies normalization, token/road-family matching and explicit geography; `js/lp097-search-governance.js`, `js/lp099-business-search.js`, `js/lp24110-poi-search-certification.js` and `js/gridlyPoiBrowserProvider.js` are additional search foundations. `resolveGridlySearchCandidateCountyId` (95813) handles candidate county metadata. County qualification must remain visible when names collide; a provider coordinate alone does not prove canonical PLACE membership.

`selectGridlySearchResult` (46335) normalizes coordinates, invalidates stale route publication, sets `GridlySearchState.activeResult/selectedDestination`, retains up to five recent searches in that state, creates the destination marker, updates the destination card, and offers a route preview. It does **not** invoke Home saving. `setGridlyDestinationMarker` (97689) and `focusGridlyDestinationOnMap` (97587) own marker and camera. `activeDestinationPlace` additionally represents saved-place activation. Selecting a saved route ID persists through `gridlySelectedPlaceIdV1`; saving an address explicitly persists precise coordinates through `gridlySavedPlacesV1` (95233). These are distinct from transient search selection.

**Cleveland → inspect Crosby:** the existing search can select Crosby without changing Cleveland Home. Reuse that selection pipeline. The full requested Crosby road/weather/official/crossings/POI/community/KBYG quick check is **partial**, because Home-derived awareness/weather readers do not atomically switch with it. Route preview and destination impact are not proof of complete temporary-community awareness. KBYG has explicit selected-area arguments in some model builders (3292, 3403), providing a better extension seam than Home mutations.

## 3. Around Me/native location

`userLocation` and window mirrors (`gridlyUserLocation`, `gridlyCurrentLocation`, etc.) are set by `setGridlyUserLocation` around 54738. This updates marker, route-origin recovery and route intelligence, without a Home/storage write. `getGridlyAwarenessAnchor({preferUserLocation:true})` (48741) prefers GPS; the governed weather resolver does not. `gridlyGetCurrentGovernedLocationContext` (48609) can derive a temporary LOCAL coordinate plus county from geographic presentation. Neither is a unified current PLACE across all surfaces.

`requestGridlyUserLocationFromControl` (54444) calls **browser** `navigator.geolocation.getCurrentPosition`, pans the map and refreshes nearest/crossing/pulse/portrait context. It requests high accuracy, timeout 10 seconds and maximumAge 60 seconds. Its error handler marks cached permission denied for every error, conflating timeout/unavailability with denial. It does not clear prior coordinates. `requestGridlyDestinationAutoCurrentLocation` (43705) has separate startup/recovery ownership; onboarding has additional browser calls (51063, 51547). Startup auto-location is deliberately deferred. Do not infer equal behavior from these separate paths.

`getGridlyForegroundLocationProvider` (87497) selects `Capacitor.Plugins.GridlyGeolocation` when available, otherwise browser geolocation; `requestGridlyForegroundPosition` (87512) is used in report-placement flow. Android `GridlyGeolocationPlugin.kt:20` declares coarse/fine foreground permissions and implements one-shot `LocationManagerCompat.getCurrentLocation`, permission continuation, disabled-service and null-location errors. `MainActivity.kt:9` registers it. The native plugin returns accuracy but no fix timestamp; its Kotlin implementation does not consume passed timeout/maximumAge options. The report owner supplies its own bounded watchdog; other callers must not assume native enforcement of JS options.

`startGridlyRouteWatchPositionUpdates` (54773) uses browser `watchPosition` with maximumAge 5 seconds and timeout 20 seconds; errors are ignored. It holds one subscription and updates live journey state without replacing immutable route origin. Stop clears the watch (54788, 100602). This is foreground WebView capability, not a native background service. iOS has a when-in-use description in `ios/App/App/Info.plist` but no equivalent custom geolocation implementation or installed official geolocation package. Device behavior, accuracy-only permission and revocation are unproven here.

**Around Me result:** temporary coordinates are possible and do not directly overwrite Home, but canonical current-PLACE resolution, shared context publication, weather handoff and stale/denied recovery need integration. County resolution is available (`gridlyResolveCountyIdForCoordinate`); point-in-PLACE geometry and memberships must be reused with accuracy/border ambiguity. Do not label the nearest town as the user's actual PLACE without containment evidence.

## 4. Proposed context contract (parts 29–30)

| Owner | Persistence | Responsibility |
|---|---|---|
| homePlace | Existing validated local Home storage | User-confirmed persistent community; changes only through Home chooser |
| selectedPlace | In-memory, context generation | Temporary community/POI/map inspection; preserve source and precision |
| currentPlace | In-memory coordinate, accuracy, acquiredAt, expiresAt, optional PLACE/memberships | Foreground fix; uncertain identity stays coordinate-based |
| destinationPlace | In-memory unless explicitly saved | Trip endpoint; may reference selectedPlace or saved place |
| activeContext | In-memory mode + identity + generation | `HOME`, `SEARCH`, `AROUND_ME`, or `ROUTE_WATCH`; one publisher for visible awareness |
| routeWatch | Explicit trip session; optional bounded resume descriptor | Route geometry/progress/expiry separate from Home and saved-place catalog |

Each context snapshot needs identity kind, canonical ID, countyMemberships, operationalCountyId where required, point/geometry authority, label, timestamp and source freshness. Every asynchronous result must carry its requested context generation; discard late Crosby results after switching to Beaumont. Fetch/cache identity includes mode/geometry version, not just county. One context publisher feeds Location Context, KBYG, weather, roads, crossings and nearby places atomically. Maintain an independent Home subscription even while inspecting elsewhere.

Portrait UX: retain one Home chooser in Settings; Home returns to persistent area. Search opens existing search/card and chooses temporary inspection. Around Me uses the existing map location control with explicit current-area label. KBYG renders the same selected context; Route Watch is an explicit trip action on the destination card with visible Stop and expiry. Do not add a second area-selection panel. Manual destination fallback never writes Home. Saved-place management remains distinct from Home Area.

## 5. Existing route/corridor foundation (parts 5–8, 26–28)

Route Watch is implemented, not absent. `startInlineRouteWatch` (101410) resolves saved start/destination, validates distinct coordinates, requests a route and activates monitoring. `renderRoutePreviewLine` (99240) uses `OSRM_ROUTE_API` (19558), public `https://router.project-osrm.org/route/v1/driving`; `OSRM_NEAREST_API` (19559) is present. Requests use GeoJSON/full overview and `steps=false` (99316). Destination previews, alternate-route comparison (`useAlternateRoute`, 99617), saved routes, map layers, route ownership/cancellation (`js/gridly-route-publication-ownership.js`) and start/stop all exist. These are awareness foundations; automatic rerouting/emergency routing is not the launch promise.

`getRoutePolylineLatLngs` (61535) reconciles monitored destination, preview and saved layers. `buildRouteHazardAssessment` (62124) uses a 0.8-mile threshold, severity weights and lifecycle/dedupe reduction. `findGridlyDestinationRouteCorridorMatches` (45648) applies expanded bounds and point-to-route distance. `buildGridlyDestinationRouteDistanceProfile` (45501) builds cumulative distance; `buildGridlyDestinationRouteImpactProximity` (45517) uses a nearest vertex and distance from **route start** for some “ahead” copy. Remote corridor reports have a separate `routeWatchSourceHazards` collection (19649), `getRouteWatchCommunitySourceIncidents` (78587) and route-aware hydration tests LP1783. `getLiveProximityRouteIntelligenceIncidents` (78619) requires active watch, active report, route relevance and a live distance band. ### Proposed bounded trip model

Use `INACTIVE → CONFIGURING → ACTIVE → ENDED`; `ENDED` carries completed/cancelled/expired reason. Add `PAUSED` only if explicit pause/resume semantics are delivered; degraded/stale is a separate health field, not silent continued progress. Keep existing Preview separate from Active. Proposed maximum trip lifetime: 12 hours, explicit renewal, not a perpetual saved-route subscription. This number is a product default to validate, not existing behavior.

Track session ID, origin and destination identities, immutable route geometry/hash/provider timestamp, start/expiry, latest foreground fix with accuracy/age, last evaluation, health, and terminal reason. Do not persist a breadcrumb trail. Stop/expiry invalidates asynchronous route work, server watch and pending deliveries. Process death should restore Preview or a clearly stale bounded watch after validation, never silently assume the user is still driving.

Relevance order: source eligible → active/not expired → authorized public projection → geometry valid → corridor intersection → position/progress quality → severity/advisory/confidence → dedupe/quiet hours. Proposed starting parameters for validation: road-point lateral tolerance 200m, conservative accuracy-aware uncertainty cap 400m, fresh fix <=2 minutes and <=100m accuracy for numeric “ahead”, high-impact look-ahead <=10 road miles, suppress >0.25 road miles behind. Calibrate on Texas rural and parallel roads; these are proposals, not tuned truth. Road name/carriageway evidence must exclude adjacent frontage roads. Low-impact work 4.8 miles off corridor is suppressed. A verified high-water impact 6.2 route miles ahead may qualify; community wording remains “reported”.

Project current position and event onto route **segments**, calculate signed chainage, account for loops and ambiguous nearest segments, and suppress directional/numeric copy when ambiguous. No fresh position: “Along your saved trip corridor”, never “6.2 miles ahead”. A server holding static trip geometry cannot know that an event is behind the user. Foreground progress upload is optional explicit scope; expire it quickly and label background state accordingly. Do not infer direction from a single noisy fix.

NWS current connector is selected **point** lookup, not a route-wide alert catalog. `gridlyWeatherProvider.js:196` preserves event/severity/urgency/certainty/expiration/affectedZones but only polygon **type** in geographyAudit; full source polygon is lost in this normalized object. Fetch and retain official Polygon/MultiPolygon (holes included) or official zone geometry before corridor intersection. Point lookup answers that point, not an entire PLACE. Polygon intersects the remaining road corridor + valid progress permits “severe weather ahead”; zone/county-only evidence permits named area advisory, no exact ahead distance. Existing `gridlyWeatherAuthorityFoundation.js:68` flattening of rings is not a certified hole-aware intersection implementation.

DriveTexas normalizer (`js/gridlyDriveTexasProvider.js:188`) now retains validated sourceGeometry and a separate representative marker point. Geometry authority supports Point/LineString/MultiLineString (`gridlyDriveTexasGeometryAuthority.js:18`); use full line intersection/distance, not just midpoint. Community reports are points, crossings are point infrastructure, POIs usually points; county-only records cannot prove route intersection. Polygon hazards require polygon intersection, road segments require travel-connected overlap. County membership is discovery/scoping, not notification relevance.

Crossing infrastructure may appear in trip brief as “Crossing ahead” once real route intersection is established. “Reported crossing blockage” requires an active, timestamped report with source attribution and dedupe by report/event. Nearby road hazard remains a road hazard unless crossing linkage is proven. There is no verified live train detector in this repository; location catalogs and community blockage reports are not live train telemetry.

## 6. Location privacy (part 4)

Precise coordinates **can leave the device today**: OSRM endpoints put origin/destination in request URLs (99316); report RPC payloads carry submitted lat/lng (`js/gridly-report-protocol.js:7,56`); governed geocoding sends query/structuredAddress/context (`js/gridly-geocoding-client.js:145`, `supabase/functions/gridly-geocode/index.ts`), with server geocode-cache storage; NWS sends governed focus coordinates in point URLs (`gridlyWeatherLiveConnector.js:9–10`). Weather focus is currently Home/governed selection, not automatically precise GPS. Map tile requests reveal viewed geography to map providers. No claim is made that passive GPS always transmits, or that providers retain nothing.

Local saved addresses contain coordinates; pending report payloads persist before network in `gridlyPendingCommunityOperationV1` (`js/gridly-report-protocol.js:3`; bounded cancellation after 24h). UserLocation/watch samples are memory/window state; no periodic GPS breadcrumb writer was found. Route diagnostics include start/destination objects and coordinates (`routeDebugLog`, 39346; calls 101432/101436); debug gating does not make copied logs anonymous. Audit globals also expose current positions. Analytics/operational telemetry modules concern event/report history and counters; no dedicated advertiser SDK or continuous GPS analytics upload was identified in scanned source. This is a code finding, not a network traffic attestation. Crash-vendor/server access-log retention was not available for inspection.

Additional local persistence must not be overlooked: `gridlyMovementIntelligenceV1` (19554; normalize/save at 47860–47938) stores corridor start/end coordinates, labels, timing/confidence and route observations; report-sourced observations are filtered out on read/write. `gridly_commute_baseline_samples_v1` (19555; writer 23333) stores samples whose route key incorporates Home/Work labels and coordinates rounded to four decimals (23344). These can expose sensitive travel associations even without a GPS trail. Legacy event-history storage (`gridlyEventHistoryV1`, gridly_event_history_v1, gridlyHistoricalIntelligence) is actively removed by `gridlyReadEventHistoryState` (20602), and its writer is persistence-disabled; historical analytics functions are not proof of active history retention. Current `loadSharedReports` (60100) reads complete client-visible active/clear pages and filters county/route locally; that path does not transmit the user's route or GPS bounds. Future server-side relevance would introduce a new transmission boundary.

The scan covers localStorage/sessionStorage/IndexedDB/cache references. No IndexedDB GPS trail implementation was found. Session guards and diagnostics are not evidence of continuous GPS retention. `service-worker.js` caches named same-origin shell/geometry GETs, excludes cross-origin requests and POSTs; it has no route/GPS cache or push handler. Future same-origin location APIs must remain uncached. Navigation network-first/offline shell fallback can show stale code; deep-link initialization must validate current data and context after hydration.

Future default: ephemeral fixes; zero server breadcrumb history; optional active route geometry deleted on end/expiry (maximum 12h proposed); terminal cleanup retries cannot extend privacy lifetime. Public push payloads contain opaque event/watch IDs, not coordinates, home address or route geometry. Current policy already discloses foreground location and provider requests (`legal/privacy.html:5`); new token subscriptions, watched routes, precise progress uploads, retention/deletion and platform disclosures still require review before rollout.
