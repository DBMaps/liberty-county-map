# LP244.44 — Notification backend and anonymous ownership contract

Contract `LP24444.v1`; future design only, **no SQL, migrations, live queries or service configuration**. [Machine contract](../../reports/lp24444-launch-contracts.json) owns defaults; [LP244.43 backend evidence](LP24443-NOTIFICATION-ARCHITECTURE.md) establishes that existing report identity/retention/geocoding are not push infrastructure. Supabase skill security guidance is applied: distinguish ownership from anonymous role/key, restrict grants and privileged APIs, and never expose service credentials.

## PUSH-01 — Architecture and contexts

Governed official/report ingestion → normalized public event projection → subscription geometry/relevance evaluation → transactional event/revision dedupe + outbox → native FCM/APNs adapter → bounded delivery ledger. Native registration and opt-in settings synchronize through a narrow ownership API. Web Push/PWA is not a launch dependency. Source ingestion runs server-side independently of any foreground device; no permanent JavaScript monitor or browser-tab polling assumption.

Launch server subscription kinds are HOME and ROUTE_WATCH only. HOME uses canonical PLACE/governed locality geometry; avoid broad county dispatch when finer geometry exists. If a locality has only a governed focus/extent, preserve that precision and wording; do not claim every part of a PLACE is covered by one point. Explicit county-wide legacy Home cannot be silently advertised as precise locality alerts; require a supported notification locality or explain regional-only unavailability. ROUTE_WATCH uses explicit static geometry and bounded expiry. AROUND_ME is foreground in-app only. DESTINATION is reserved for an explicit SHOULD HAVE bounded opt-in feature; v1 public API rejects unsupported kinds, and Search never creates a subscription.

One event can match multiple consented contexts, but WHY (HOME/ROUTE_WATCH/etc.) is separate from WHAT (SEVERE_WEATHER/ROAD_HAZARD/ROAD_CLOSURE/WINTER_HAZARD/COMMUNITY_UPDATE/OFFICIAL_NOTICE/CONSTRUCTION). Visible context does not alter existing server subscriptions. Select strongest valid reason deterministically: HIGH relevance before MEDIUM, then ACTIVE ROUTE_WATCH before HOME, then future DESTINATION/AROUND_ME, then stable watch ID. Aggregate matching reasons in the delivery record; no precise geometry or device location goes in push payload.

HOME spatial eligibility uses the governed PLACE/locality polygon when available: complete event polygon/line intersects it, or valid event point lies within it, with source precision retained. This establishes area relevance, not a claim the user is near that hazard. A governed focus-only Home can match official weather containing the point but must be labeled “At your selected locality focus”; it cannot invent a roadway radius or whole-place coverage. County-only matches remain qualified regional MEDIUM awareness and cannot trigger exact-locality HIGH claims. Missing/ambiguous geometry suppresses high-priority Home delivery until resolved. HIGH impact and authority/confidence requirements are the same as SEND-01. Home change synchronizes an explicit confirmed new subscription revision; stale in-flight old-place matches recheck before send. Offline Home change shows pending alert-area sync rather than pretending the server moved.

## ID-01 — Installation enrollment and ownership

No mandatory account or Supabase anonymous-auth account in v1. Installation ID is server UUIDv4, separate from report device ID, provider registration/Firebase installation identifier, email, phone, hardware identifiers and advertising IDs. Client generates 256 random bits as ownership secret using OS CSPRNG, sends it only over TLS, and server stores a one-way digest with credential version. High-entropy bearer secret is not a password; compare digests in constant time. Raw bearer never appears in URLs, public records, logs or diagnostics.

Store credential in Android Keystore-backed encrypted native storage or iOS Keychain ThisDeviceOnly; never ordinary localStorage. iOS also has an app-container installation marker: if marker disappears on reinstall but Keychain item remains, erase orphan local credentials and start new enrollment. Native secure storage implementation/provider choice is a LP244.49 dependency; no plugin added now. Loss of credential means no automated recovery of old private subscriptions. Report ownership identity remains untouched and unjoined.

Bootstrap `POST /v1/installations` accepts `{v,bootstrapId,platform,appVersion,environment,ownershipSecret}`; returns opaque installationId and credentialVersion. bootstrapId UUID is idempotent for 24h using keyed digest, never raw secret. If response is lost, retry same bootstrapId/secret; a different secret for same bootstrapId fails without disclosing existing ID. Unverified bootstrap records expire after 24h; a verified installation follows the 90-day inactivity limit. A registration probe expires separately after 5min. No event notifications until token binding, permission/consent and preferences are confirmed. The explicitly consented foreground setup probe is the sole pre-binding transport exception and contains no event or private subscription data.

Bearer secret possession is the sole installation mutation authorization (with anti-abuse limits); installation_id alone is never sufficient. Endpoint resolves installation from authenticated credential and rejects a conflicting body/path owner. All route/watch reads are authenticated and scoped the same way. Use uniform not-found/forbidden response shapes, bounded pagination, no installation/token existence lookup API.

## ID-02 — Token lifecycle and binding

Token registry stores provider/platform/environment plus opaque registration value; never assume all platforms use FCM tokens. Standard plan uses Android FCM and iOS direct APNs. Provider registration representation is adapter-versioned: current provider documentation evolves independently of Gridly installation IDs. Pin tested SDK/API versions during implementation and do not substitute a provider ID for Gridly ownership.

States: PENDING_VERIFICATION → ACTIVE → ROTATED / INVALID / REVOKED. One active token per installation/provider/environment; multiple historical metadata rows permitted. Registration refresh is expected on startup/resume and provider callbacks, with idempotent unchanged token writes. A replacement does not retire the old working token until new binding is verified; after verification replacement/revocation is atomic.

**Binding protocol:** explicit foreground setup registers a candidate token; server creates unpredictable one-use probe nonce/attempt ID with 5-minute expiry. A minimal setup notification is sent to that token; its native foreground receipt returns the nonce only to a locally pending matching attempt. Client acknowledges using its installation credential. The API response never returns the nonce, so a claimant of another device's token cannot acknowledge it. No ongoing subscription is transferred or disclosed before the challenge completes. This is a visible/foreground registration test, not reliance on unsupported iOS silent background push. Foreground setup may explain “Checking alert delivery”; a lost probe leaves registration pending and offers bounded Retry.

Registration endpoint permits <=3 probes per token digest/hour and <=5 enrollment attempts per IP/hour as initial configurable abuse limits; production mobile-carrier false positives require monitoring and approved adjustment. Duplicate probe requests reuse the pending attempt, not another push. Provider invalid responses delete raw unusable token material and stop sends; generic invalid-payload errors do not indiscriminately revoke a valid token. No provider success response alone proves device ownership or user delivery.

Reinstall creates new Gridly identity and new consent. If the same provider token is verified for the new installation, revoke old token binding without copying old prefs/watches; previous subscriptions no longer send through it. Token-only knowledge cannot trigger this transfer. Uninstall has no reliable callback; last_seen inactivity 90 days revokes installation, with deletion cleanup below. No unusable raw token retained indefinitely. [Provider registration lifecycle](https://firebase.google.com/docs/cloud-messaging/manage-tokens).

## API-01 — Narrow write/read surface

| API action | Authorization / concurrency | Return / side effect |
|---|---|---|
| Create installation | Rate-limited bootstrap, no public listing | ID + credential version only |
| Begin/ack token registration | Owner credential + pending probe nonce on acknowledgment | State/status; never echo raw token or other owners |
| Get/update preferences | Owner + If-Match revision for writes | Safe preference DTO; conflict on stale revision |
| Put Home subscription | Owner; server resolves canonical locality/membership/version | One active HOME watch; identity/geometry validated server-side |
| Create route watch | Owner; real geometry/provider provenance/caps and consent | ID/expiry/generation; terminate prior active/paused watch atomically |
| Pause/resume/stop/complete watch | Owner + expected generation + idempotency key | New state/generation; cancel unsent route-only candidates |
| Get own watch | Owner | Only owner's current bounded route descriptor/geometry; terminal data inaccessible |
| Rotate credential | Current owner + one-use rotation operation | New version; bounded overlap/retry semantics |
| Delete installation | Owner + idempotency key | Revocation accepted immediately; no public identifier lookup |
| Receipt/tap acknowledgment | Owner, known delivery/event, bounded action ID | Informational receipt; never grants new authority or proves display without callback |

Mutations require UUIDv4 Idempotency-Key and expected resource revision where present. Store keyed digest of key + method/path + canonical body hash for 24h; retry exact same request returns same safe result, different body/key reuse conflicts. Validate server timestamp/expiry for probe/revocation/rotation tokens; nonce consumed atomically. Maximum API body 64KiB, route geometry 10,000 vertices, strings bounded per deep-link/event contract. General mutation rate starting cap 60/min/installation; watch create cap 6/hour; sensitive delete/stop requests remain available within a separately bounded emergency-control allowance (10/min) so ordinary rate exhaustion cannot trap a watch. Limits are configuration, not covert tracking; retain IP limiter data at most 1h with no location enrichment.

Routine credential rotation at 30 days or immediately on suspected compromise. Client creates new secret, presents old credential + same rotation operation; server stores pending digest/version, allows old credential only to recover/ack the pending rotation for <=10min, then destroys it. Normal mutations require newest activated version. Revocation/deletion has no overlap. Offline rotation does not extend expired credentials indefinitely; reconnect through bounded recovery or enroll afresh.

## DB-01 — Proposed tables (no schema implementation)

All entities reside in a **non-exposed `notification_private` schema**, with default-deny client grants and defense-in-depth RLS. PUBLIC/anon/authenticated get no raw-table SELECT or mutation. Privileged workers own outbox/events; authenticated installation API returns narrow DTOs. Security-definer routines, if used later, need fixed search_path, least EXECUTE grants and explicit authorization; no broad anonymous RPC exposing credential checks as table access.

Engineering retention limits below are implementation bounds for review, **not finalized legal retention policy**. A stricter source policy wins. After revocation/terminal expiry deny access immediately; erase sensitive rows within 15min. Backup/log retention and a purge-before-restore procedure are release gates, not magically solved by SQL DELETE.

|---|---|---|---|
| consumer_installations — ownership | id UUID; secret_digest/version, platform/environment, app_version, created_at/last_seen_at/revoked_at/deleted_at | Private; owner DTO via API; worker checks digest/version; no raw client access | Revoke at 90 idle days; immediate deny on Delete; physical row/credential purge <=15min, deleted_at transient until purge |

| consumer_watch_subscriptions — why alerts match | watch_id UUID; installation_id, kind, place identity/memberships/version, state, generation, expires_at | Server derives geometry, owner may create/stop only supported kinds | HOME until consent revoke; ROUTE linked TTL; reserved kinds rejected in v1; delete with owner |

No position/progress table exists in launch scope. Server watch geometry contains sensitive endpoints and is private even if road geometry is public. PostGIS spatial capability is available in repository migrations, but deployment/indexes/cost require future validation. Use bounding-box prefilter then correct geometry predicates; no public spatial endpoint for other installations' trips.

## EVT-01 — Normalized event payload

`{v:1,event_id,source,source_event_id,episode,source_revision,material_revision,condition,subtype,severity,advisory,authority_class,source_domain,issuer,authority_evidence,confidence,confidence_basis,lifecycle,change_type,geometry,geometry_precision,starts_at,ends_at,observed_at,updated_at,last_source_success_at,place_ids,county_memberships,source_references,public_projection_version}`. Required keys may be null only where [hazard contract](LP24444-HAZARD-NORMALIZATION-CONTRACT.md) permits. source_event_id missing/unstable-index fallback suppresses push. event_id is server UUID, not a coordinate hash. Keep raw source field values in bounded adapter-owned evidence, not unlimited raw-payload archives.

`route_relevance` and `deep_link_target` belong to a **per-installation delivery projection**, never a shared event row containing a private watch ID. Projection adds matched context IDs/reasons/generations, relevanceClass/geometryRelation, priority, freshness deadline, validated target and eligibleUntil. Server projection never adds numericAheadMiles. Native envelope <=3KiB total; target <=1KiB; no coordinates, route endpoints, raw report detail or credentials on lock screen.

Material revision begins at1 and monotonically increases for validated changes to normalized condition/impact/severity, authorized advisory, lifecycle/episode, substantive official instruction or geometry/affected segments. Ignore fetch/sent ordering noise, formatting and topologically equivalent geometry. Retain raw source_revision separately. A changed geometry can create a new semantic revision, but re-alert that installation only if impact/relevance materially changed, not a subprecision point jitter. Official expiry-only extension updates ends_at/queued TTL but does not ordinarily increment material_revision or re-alert. Shorter expiry immediately suppresses unsent work. A resolved/expired event legitimately reactivated is a new episode/event_id linked to original source; feed timeout is never reactivation evidence.

## SEND-01 — Priority, dedupe and lifecycle

Two priorities only: HIGH_AWARENESS and ROUTINE. No OS Critical Alerts/emergency authority. HIGH requires active/fresh authorized severe weather warning, explicit closure/impassability/avoid-area instruction, or relevant HIGH/SEVERE road/winter/crash blockage with adequate evidence. Official weather watch/advisory is not automatically a warning. Community MEDIUM confidence requires at least two independent valid observations or a separately corroborating source under governed report rules; confirmations change confidence, never official authority. One unsupported observation remains MEDIUM relevance/in-app qualified. Significant-hazard preference explicitly includes qualified community evidence; Community Updates switch is for additional lower-impact updates, not a hidden source-authority toggle.

Dedupe unique key is **installation_id + event_id + material_revision**, with no context suffix. Transaction reserves this key and one outbox row after aggregating all eligible watches. Home+Route+future Destination flood → one delivery decision. Repeated fetch, additional match reason, token rotation, app reopen, restarted watch or expiry extension does not resend unchanged event. Material escalation/newly affecting geometry can alert again; a 15min same-event update cooldown applies except verified severity increase to HIGH/SEVERE or newly authorized ROAD_CLOSED/IMPASSABLE/AVOID_AREA. Terminal resolution cancels active alerts; launch does not push routine “all clear” from expiry. New source-proven recurrence is a new episode.

Routine is off by default. If opted in, batch at15min, maximum3 routine notifications per installation/local calendar day, respect quiet hours and event freshness; discard expiry rather than send a stale digest. Separate distinct HIGH events are not hard-capped away; dedupe and same-event update control are mandatory, with explicit burst/fatigue acceptance fixtures and nonidentifying rate metrics before release. Do not silently drop a newly relevant severe alert to satisfy a cosmetic counter.

Routine batching groups eligible rows for one installation into one `batch_id` at each 15min boundary, with a maximum of one notification for that batch and a single best valid context target (TRAVEL_BRIEF). Keep each event/revision reservation separately, so grouping never bypasses the unique dedupe key. Summary carries a count and source-qualified general label, not a potentially oversized list; current brief refetches details. TTL is the minimum of all included eligibility deadlines; remove stale members immediately before submission. Atomically claim daily quota and member reservations with the batch. One provider result/attempt applies to every submitted member; UNKNOWN blocks blind member resends. Known rejection may retry that batch within bounded attempts/TTL, and unused quota is released only when non-submission is certain. If no quota remains, eligible routine members wait for next allowed batch only while still fresh; expiration cancels them. Table outbox fields include nullable batch_id and quota reservation, and deliveries can share provider message ID across its event members. HIGH events are never hidden in a routine batch.

Outbox states: PENDING, LEASED, SUBMITTED, UNKNOWN, CANCELLED, EXPIRED, FAILED. Lease30s; up to5 bounded attempts on known transient rejection before expiry, exponential backoff starting5s capped60s with jitter; respect provider Retry-After if still eligible. Provider timeout after possible acceptance → UNKNOWN; do not blindly resend same revision and claim exactly once. Provider accepted ≠ displayed/read. Stable per-event collapse identifier can replace obsolete visible revisions, but does not merge distinct hazards or guarantee removal.

Before enqueue and **immediately before provider submission**, recheck installation/token/consent/preference revision, watch state/generation/expiry, event lifecycle/material revision/public authority, all source freshness deadlines, current geometry relevance and quiet hours. Actual provider TTL in seconds = `max(0,min(300,eventEnd-now,watchExpiry-now,sourceFreshnessDeadline-now,outboxExpiry-now))`; omit invalid/no-positive-lifetime messages. HOME has no trip expiry, so that term is positive infinity. Missing official end time cannot produce unbounded eligibility: derive eventEnd from the adapter's finite observation/freshness ceiling or suppress if none exists. APNs expiration and FCM TTL receive equivalent bounded expiry. Never rely on a provider's longer default lifespan. [FCM message lifespan](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan).

Cancellation removes affected watch matches; another valid Home match may keep one queued event eligible. Expired/resolved/cancelled/reopened/suppressed/withdrawn events, stopped/completed/paused/expired watches, lost relevance or deleted installations cancel pending work. Serialize claims/revocation per installation; a final check cannot recall an already in-flight network request or provider-held notification, and UI/legal copy must not promise that. Tap always refetches current truth. Quiet hours cannot extend TTL; a deferred stale item drops.

## SEC-01 — Default deny and privacy deletion

Existing Supabase `anon` key is not ownership. A narrowly deployed Edge endpoint may accept bearer installation credentials independently of Supabase JWT only with explicit authentication inside that handler. It must not expose general-purpose SQL/RPC or forward caller-selected user IDs. Server/service-role credentials bypass RLS and stay private; policies alone do not secure such handlers. Explicitly test public grants, views, table functions, cross-owner read/write and guessed IDs, token replay and body-owner reassignment. Do not use editable metadata claims for authorization. [Supabase RLS and grants](https://supabase.com/docs/guides/database/postgres/row-level-security).

Delete authenticates first, revokes credentials/tokens/watches and disallows new sends in one transaction, then purges prefs, route geometry/endpoints, owner-linked dedupe/outbox/delivery/receipts within15min. Offline deletion is marked pending, not complete; local opt-out immediately suppresses local surfaces and retries server request while securely retaining only necessary credential/operation until acknowledged. Users choosing immediate local erasure must be told remote deletion is unconfirmed; automatic inactivity expiry and existing privacy assistance remain fallback.

Backups may contain deleted rows. Launch recovery policy is conservative: restore into an isolated environment with notification APIs/workers disabled, then purge all installation-owned credentials, tokens, preferences, watches, route geometry and identifying queue/delivery/dedupe/receipt records before reconnecting devices or workers. Revalidate public events against current sources. Surviving devices must enroll again with explicit consent; never automatically recover old subscriptions. This avoids retaining a separate identifying deletion journal merely to restore this ephemeral subsystem. The owner must review actual backup expiration/access restrictions and disclose that physical backup copies expire under that bounded policy. If backup horizon/purge enforcement cannot be established, block production activation rather than claim deletion from backups. No raw location/token data in logs; errors use bounded codes, endpoint/body redaction and aggregate counts. No exact GPS telemetry or movement history table. Retention and privacy/store disclosures require owner/legal review before activation; this plan is not legal approval.
