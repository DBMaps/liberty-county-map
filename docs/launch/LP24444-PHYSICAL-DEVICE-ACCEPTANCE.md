# LP244.44 — Physical Android and iPhone acceptance

Contract `LP24444.v1`; **planned tests, none executed in LP244.44**. A documentation PASS does not certify device behavior. Both platforms must pass on newly built candidates after native work. Emulator/simulator/browser evidence supplements physical tests and cannot replace them. Release cannot waive MUST HAVE notifications or winter coverage by labeling them optional.

## CERT-01 — Candidate and evidence rules

Record test ID, tester/date, exact source commit, candidate checksum/version/build number, device model/OS/API, signing/provider environment, consent/channel/Focus/power/network states, fixture event ID/revision, expected result, actual result, timestamped redacted screenshot/video and relevant server/native result codes. Do not record raw secrets, tokens, exact personal coordinates or route endpoints in general-purpose test logs. Use synthetic approved test routes/events and isolated delivery recipients; never inject a fake emergency into public production feeds.

Physical Android matrix: API24–29 compatibility device, API30–32 permission/location behavior and API33+ notification-runtime-permission device, including current target36 behavior on suitable hardware. If minimum-supported hardware is unavailable, its acceptance remains unproven; emulator evidence alone cannot certify the advertised minimum. Physical iPhone: supported oldest release/device class and current supported iOS, signed APNs sandbox and distribution-equivalent production path as appropriate to candidate. Final support versions are pinned by implementation dependency review and recorded, not invented in this planning phase. Include small-screen portrait, safe areas, enlarged text and real touch targets on both platforms.

Controlled positive delivery tests run with reachable network, permission/channels enabled, verified token and active fresh eligible source. Each foreground/background/terminated case needs three distinct eligible events delivered and opened correctly, with timestamps; any unexplained miss is investigated, not averaged away. This is a repeatability gate, not a promise of universal latency. Record ingestion-to-submit and submit-to-observed timing and confirm observed notification freshness. Provider UNKNOWN/timeout must be handled truthfully and not blindly resent. OS force-stop/Focus/Doze restrictions are separate negative/degraded cases; success there means accurate state and safe resume, not guaranteed alert arrival.
