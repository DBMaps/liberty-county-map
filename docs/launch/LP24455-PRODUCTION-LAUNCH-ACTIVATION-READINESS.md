## Current reporting and retention architecture

- [Client protocol](../../js/gridly-report-protocol.js) exports version 2. Creation calls `submit_community_observation`; confirm/edit/clear call `mutate_community_observation`; cancellation calls `cancel_community_operation`. The app's [availability runtime](../../js/app.js) uses `get_community_reporting_status`, requires protocol 2, a boolean enablement value and valid `changed_at`, and blocks before a new submission when unavailable or unknown. A writer `maintenance` response remains authoritative even after a status read. The status RPC was added by [LP244.29A](../../supabase/migrations/202609160001_lp24429a_reporting_availability_contract.sql) and returns only version, enablement and timestamp from private admission state.
- [Atomic transition](../../supabase/migrations/20260908200554_lp24422a_prelaunch_reset_and_atomic_report_transition.sql) creates admission state with `reporting_enabled=false`; all three writer RPCs return `maintenance` while closed. [Owner release SQL](../../supabase/retention/release-community-reporting.sql) alone couples the consumed prelaunch guard's `launched` transition with enabling protocol 2. No later tracked migration enables it. Old anonymous direct report/history writes were revoked; [LP244.23D](../LEGAL/LP24423D-PROTOCOL-V2-CLIENT-READINESS.md) traced all report writes through RPCs and disabled the old history writer. The generic adapter's direct INSERT is limited to feedback. The LP244.36 production postflight confirmed writer definitions unchanged and direct/private grants bounded.
- One random UUIDv4 operation ID is persisted before send; the client reuses it on manual retry/restart, retains it on transport failure or maintenance, and does not auto-loop. The server stores a private SHA-256 replay digest, consumes accepted/rejected terminal operations as designed, and prevents a replay from creating a new report. The client does not invent a row from a replay response. At 24 hours a pending operation becomes cancellation with its original token. A missing RPC yields `stale_client`; obsolete clients cannot use direct INSERT. Version 2 is a client/bundle and server admission contract, not an extra RPC argument. See [LP244.23D](../LEGAL/LP24423D-PROTOCOL-V2-CLIENT-READINESS.md) and [protocol source](../../js/gridly-report-protocol.js).
- [Retention migration](../../supabase/migrations/20260908200554_lp24422a_prelaunch_reset_and_atomic_report_transition.sql) and [LP244.21 review](../LEGAL/LP24421-REPORT-RETENTION.md) establish original submission clocks, private device links and receipts, append-only replay evidence, day-149 report cleanup, a day-180 association ceiling, count-only health and restricted client access. The later [Google Play compliance migration](../../supabase/migrations/20260916183911_google_play_compliance_closure.sql) adds moderation/deletion evidence and visible-only reads; [LP244.36](GRIDLY-LP24436-PRODUCTION-COMPLIANCE-CERTIFICATION.md) certifies it in production without changing admission. [Recovery tooling and runbook](../LEGAL/LP24421-RECOVERY-RUNBOOK.md) require isolated restore, a complete independent replay witness, sanitization, read-only certification and separate reconnection approval. The older runbook's numbered step 3 refers to now-no-op 001/002 checkpoints and is explicitly superseded by its opening warning; it is not a current restore execution recipe.
