## 3. StoreKit operations and product metadata

The only product request is `Product.products(for: ["com.gridlygo.gridly.monthly"])`. The bridge requires one auto-renewable monthly product, a USA storefront, no introductory/promotional offer, and purchased ownership rather than Family Sharing for evidence. Product display name, price and currency are read from StoreKit. JavaScript returns only bounded allowlisted metadata for USD/US/P1M and never invents $2.99 if StoreKit returns another price. A different returned price remains visible as returned; the owner must reconcile such a difference with the approved launch/store configuration before release.

Operations:

| Method | Behavior |
| --- | --- |
| `getProducts` | Exact product query; bounded display metadata or product_unavailable |
| `purchase` | StoreKit purchase; verified evidence, distinct cancellation/pending, or safe error |
| `getCurrentEntitlement` | Silent current evidence; latest transaction fallback for expired/revoked evidence |
| `refreshEntitlement` | Same silent inspection |
| `restorePurchases` | Requires userInitiated=true; explicit AppStore.sync then silent inspection |
| `finishTransaction` | Finishes only an in-memory verified transaction identified by an opaque handle |
| `startObserving` / `stopObserving` | Idempotent StoreKit update observation and foreground notifications; cleanup |

Native state is advisory. Verified expiration/revocation and verified subscription/renewal status yield active, expired, canceled_pending_expiry, not_entitled or unknown hints. Renewal disabled does not immediately end access. Billing retry/revoked deny; grace/ambiguous renewal data is unknown. Missing evidence is a native not_entitled hint only, never a backend-confirmed ownership denial.

The coordinator ignores these hints as access authority. Only a valid nonce-bound signed server proof can pass the existing shared accessDecision. A sandbox proof cannot pass a production session. Expired/revoked server decisions deny access even when a synthetic native hint says active.

## 4. Purchase and finish semantics

Sequence:

1. StoreKit purchase returns a verified canonical transaction; unverified success is rejected.
2. A bounded JWS and environment travel transiently through the fixed LP244.62 verification request.
3. The coordinator validates the returned server proof against the pinned ES256 P-256 public key, nonce, product, platform, environment, audience and lease.
4. For entitled state, a trusted `deliverEntitlement` application port must confirm service delivery. It receives a current-operation guard and must check it before committing any runtime effect.
5. Only after confirmed delivery, finish the exact native completion handle. There is no finish-all call.

[Apple documents finish as confirmation that content/service was delivered](https://developer.apple.com/documentation/storekit/transaction/finish()). Receipt validation alone does not satisfy this ordering. The current application has no configured delivery port, so missing delivery composition blocks entitlement/finish. Final delivery/gating belongs to LP244.65; nothing here enables the production paywall or service.

Cancellation, pending, malformed/unverified evidence, wrong environment, empty evidence, forged proof, server HTTP503/error/timeout, unknown server state, or failed delivery do not finish. Definitive signed non-entitlement is returned as denial without finishing the purchase in this phase. Handling historical inactive unfinished transactions beyond this conservative policy requires later Apple runtime certification; it is not silently treated as delivered service.

Native completion handles retain only Transaction objects in memory, at most sixteen; repeated observation of a transaction reuses its handle. No JWS is stored in that map. StoreKit retains unfinished transactions across process loss; fresh native evidence allows reconciliation again. Stop clears transient handles, never finishes them. JavaScript holds one operation's evidence only until provider response/error and never puts it into read/UI state.

Operations are serialized. Silent refresh and provider work have a fifteen-second response budget; purchase/explicit restore allow up to two minutes for store interaction, with a separate bounded provider call. Late timeout work cannot overwrite session state or initiate finish. A finish already issued after valid proof and delivery may complete after timeout; timeout is not transaction cancellation. Recovery re-queries StoreKit.

## 5. Lifecycle, restore and recovery

`start()` registers transaction/foreground listeners, starts observation and silently inspects current evidence once. Repeated start does not install duplicate observers. `launch()` is silent; `resume()` and transaction/foreground signals coalesce while one refresh is outstanding. `stop()` removes listeners/observers and invalidates access state. There is no timer refresh loop or sync at ordinary launch/resume.

Explicit `restore()` calls native `restorePurchases({userInitiated:true})`. [AppStore.sync](https://developer.apple.com/documentation/storekit/appstore/sync()) is reserved for this action; ordinary [current entitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements) inspection does not request intrusive restore authentication.

After reinstall/new device, fresh StoreKit/App Store purchase evidence enters the same verifier. No old Gridly installation ID, consumer account, Apple account email or report-device identity is required. This behavior is contract-tested with separate synthetic sessions; actual App Store restore remains unproven until Mac/sandbox work.
