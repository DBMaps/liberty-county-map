Window 3D continued from this uncommitted draft. See [the Window 3D closure record](LP24466-WINDOW3D-NATIVE-AUTHORIZATION-CLOSURE.md) for the current implementation and verdict; the statements below record the Window 3C checkpoint.

## Decision and threat model

**NOT READY FOR WINDOW 4 DEPLOYMENT REVIEW.** This is a local implementation draft. A copied request, forged native hint, public Supabase key, old challenge, or Play verdict alone must never mint entitlement. The server must establish app legitimacy and fresh, exact request binding before asking the store about ownership. Attestation keys, challenge hashes, Play tokens, device identifiers, and continuity records are not subscription or account ownership. Store verification and signed proof remain separate gates.

The two production verifier entrypoints still return 503. The release client still has `authority: null`. No remote migration, function, scheduler, reporting, purchase, or paid admission was activated.

## Challenge protocol and canonical binding

`createNativeChallengeHandler` accepts only bounded POST JSON `{platform:"apple"|"google"}`. It requires an injected source limiter and store. It generates 32 random bytes, returns their 43-character base64url representation and an expiry two minutes later, and stores only SHA-256 of the challenge. The proposed private RPC checks platform and purpose, caps issuance at 300 per minute and 10,000 simultaneously live rows, and deletes at most 500 expired or consumed rows on each issue. A challenge has no account or installation identity and cannot itself mint a proof. The source limiter remains unimplemented, so there is deliberately no deployed challenge endpoint.

`nativeVerificationBinding` validates the store verifier request and builds a JSON array with fixed field order: `gridly-subscription-verification-v1`, challenge, platform, environment, product ID, Google base plan or empty string, nonce, optional continuity binding or empty string, and SHA-256 base64url of the single bounded evidence array. SHA-256 of this canonical UTF-8 array is the 32-byte native client data hash; its base64url encoding is the Play Integrity `requestHash`. Reordering JSON object fields does not change it. Changing a bound value changes it or is rejected. Raw purchase evidence is absent from challenge storage.

The trusted server authorizer independently recalculates that digest, verifies a platform proof through a server-only verifier port, then atomically consumes the hashed challenge. Provider verification follows only on success. The SQL transaction locks the challenge row, rejects wrong platform, purpose, expiry and prior consumption, and updates Apple counters under the same transaction. Duplicate Google tokens tied to the same challenge fail on reuse; a new challenge requires a new bound Play token. Production safety still depends on the missing verifier composition and source rate limit below.

## iOS App Attest client and unsupported devices

`GridlyAppAttest` is a first-party Capacitor bridge registered in the iOS target. It exposes `isSupported`, `authorize` and `confirm`. On supported devices it generates a `DCAppAttestService` key, retains only its key ID in ThisDeviceOnly Keychain storage, and calls `attestKey` with the canonical digest for initial authorization. After server proof and local confirmation, it calls `generateAssertion` with the same digest contract on subsequent requests. It bounds object size, exports no private key, and emits no sensitive logs. The local entitlement has the App Attest development value; the production signing profile and entitlement must be verified in an Apple build before shipping. Development and production attestation must use separate server policy and records.

Policy **A**: if `isSupported` is false or native attestation fails, deny new paid authority. There is no DeviceCheck fallback. An already verified subscriber may have only the separately bounded LP244.65 signed continuity behavior; unsupported service is not an entitlement bypass. Apple documents that App Attest is not available on every device, including some Mac environments. Gridly targets iOS 16.4+, but device support must still be checked at runtime. [Apple App Attest service](https://developer.apple.com/documentation/devicecheck/dcappattestservice); [support property](https://developer.apple.com/documentation/devicecheck/dcappattestservice/issupported); [environment entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.devicecheck.appattest-environment).

## iOS server verification and retained state

The authorizer defines the trusted Apple verifier port, but **there is no Apple server verifier implementation**. Before deployment it must verify the Apple App Attest certificate chain to Apple's App Attest root, nonce extension, authenticator data and RP ID for the exact team ID and `com.gridlygo.gridly`, environment AAGUID, credential ID/key, and initial counter. For assertions it must load the registered key, verify the signature over authenticator data plus canonical client data hash, validate RP ID and monotonic counter, and reject wrong key, replay, chain, identity, or environment. It must use Apple's published root and independently validated fixtures, not an untrusted key supplied by the request. The Apple team/App ID prefix and production certificate trust assets are not in this repository. [Apple server validation guidance](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server); [Apple certificate authority](https://www.apple.com/certificateauthority/private/).

The local migration drafts a private `apple_app_attest_keys` table with only key hash, public SPKI, environment, monotonic assertion counter, and timestamps. It contains no purchase, user, email, or install ID. Its initial registration currently accepts only production; development fixture acceptance needs a separately isolated path. Since the validator is absent, no app key is currently admitted.

## Android standard Play Integrity

`GridlyPlayIntegrity` registers in Android and uses Play Integrity library 1.6.0 standard requests. A build property `GRIDLY_PLAY_INTEGRITY_PROJECT_NUMBER` supplies the Google Cloud project number; missing or invalid configuration resolves to zero and fails closed. `prepare` obtains a standard token provider, then `authorize` sets the canonical digest as `requestHash` and returns one bounded token. The client cannot infer paid authority from local token acquisition. The fixed package is `com.gridlygo.gridly`; Android minSdk 24 meets the library's documented minimum. [Standard requests](https://developer.android.com/google/play/integrity/standard); [setup](https://developer.android.com/google/play/integrity/setup); [release notes](https://developer.android.com/google/play/integrity/reference/com/google/android/play/core/release-notes).

The local server verifier sends the opaque token to `playintegrity.googleapis.com/v1/com.gridlygo.gridly:decodeIntegrityToken` with a Google OAuth token scoped to Play Integrity. It accepts only production, exact request package and hash, a timestamp within 120 seconds (five seconds future allowance), `PLAY_RECOGNIZED`, `LICENSED`, and `MEETS_DEVICE_INTEGRITY`. It never interprets this as ownership; the Google Play subscription API remains the ownership source. The trusted decode response is not read from the client. The policy is intentionally strict and may exclude otherwise legitimate devices; review its cohort impact before deployment. [Verdict meanings](https://developer.android.com/google/play/integrity/verdicts).

For owner dashboard setup: in Play Console, link `com.gridlygo.gridly` to the intended **Gridly Play Billing** Cloud project and enable/configure Play Integrity for that app. In that Cloud project enable the Play Integrity API, record its numeric project number for the Android build, and grant the server service account only the required Play Integrity access for decode in the linked project. Verify in Google Cloud/Play Console that the existing billing service account is eligible before reusing it; billing API access alone does not prove decode permission. Place the server credential only in Edge secret storage and configure the Play Integrity OAuth scope there. Confirm app signing/distribution and Play licensing verdicts with a release-channel fixture. No project number or credential was present in the repository and none was invented. [Google setup](https://developer.android.com/google/play/integrity/setup).

## Database, abuse bounds and endpoint inventory

Local unapplied draft: `supabase/migrations/20260928030000_lp24466_native_authorization.sql`. It adds `subscription_ops.native_challenges` and `subscription_ops.apple_app_attest_keys`, enables RLS, revokes direct table access from `PUBLIC`, `anon`, `authenticated`, and `service_role`, and grants only service-role execution on three fixed security-definer RPCs: issue, read key, consume. The draft is additive to the also-unapplied LP244.62 `subscription_ops` migration. Challenge rows retain only hash, platform, purpose, timestamps and consumption time. The fixed bounded cleanup on issue is not a scheduler. The Supabase CLI was unavailable locally, so this file was named manually and SQL execution has **not** been validated against a local database.

The issuance RPC provides a global circuit breaker, not a source/IP limiter. A challenge endpoint must additionally have a trusted gateway source identity and a per-source/IP bound before it can be exposed; `X-Forwarded-For` supplied by a caller cannot be trusted without gateway normalization. Generic bounded 429/503 responses should reveal no key, challenge lookup, or account status. Store RPC access must remain service-role server-side. Anon/publishable credentials may route Edge calls but cannot grant native admission. A client Supabase transport has not been composed because a safe early native-only invocation path and complete server gate are still missing. No service-role credential belongs in the app. Supabase's default Edge `verify_jwt` behavior remains enabled for the dormant verifier functions; gateway JWT alone is not native authorization. [Function configuration](https://supabase.com/docs/guides/functions/function-configuration).
