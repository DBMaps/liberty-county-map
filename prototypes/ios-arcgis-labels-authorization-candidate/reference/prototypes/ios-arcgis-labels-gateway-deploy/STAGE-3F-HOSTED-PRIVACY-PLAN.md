- [Postgres connections](https://supabase.com/docs/guides/database/connecting-to-postgres): current code pins direct `db.<ref>.supabase.co:5432` with a dedicated role. Direct normally uses IPv6; the paid IPv4 add-on replaces the AAAA record rather than adding dual stack. Supabase recommends a transaction pooler for serverless connections, but this candidate does not support pooler DSNs. PostgreSQL functions provide transactions for the existing reserve/admit/finish operations; do not split these operations across HTTP calls.
- [DB TLS](https://supabase.com/docs/guides/platform/ssl-enforcement) and [network restrictions](https://supabase.com/docs/guides/platform/network-restrictions): require project CA plus hostname verification (`verify-full` equivalent), test actual Edge-to-DB IPv6 and TLS, and prove wrong CA and wrong hostname fail. ## Ingress and invocation gates

Use one temporary first-party HTTPS proxy with a valid certificate, exact hostname and independent source restriction (named static tester CIDR or a private authenticated access layer with equivalent isolation). Keep it closed until ready. The [existing template](ingress.nginx.conf.example) is a baseline, not sufficient by itself: independently require the tester restriction, an absolute request deadline, route-specific limits, and egress controls on the chosen host. Enforce source restriction at the perimeter, using the actual peer or an explicitly trusted load balancer; ignore client forwarding headers.

1. Match original method and raw target before normalization: `GET /health`, `POST /v1/labels/challenge`, `POST /v1/labels/lease`, `POST /v1/imagery-labels/tile`. Reject wrong Host, legacy coordinate URLs, queries, encoded slashes, dot segments, duplicate proof headers, ambiguous framing, and disallowed methods. Reject browser preflight; no CORS or shared caching. Send `no-store`, never follow redirects or retry.
2. Cap tile bodies at 64 bytes at Edge and in the rendered ingress, lease bodies at 48 KiB and challenge bodies at zero. Verify the proxy rejects over-limit streaming bodies and unexpected encodings. Cap successful tile responses at 512 KiB at Edge and verify the same limit through ingress, including over-limit or malformed upstream replies; bound proxy-generated error bodies and return generic codes. Use the existing 6-second application deadline and a separate hard 10-second ingress request ceiling including slow input; Nginx socket inactivity timeouts alone are insufficient. For the run use up to 8 connections total, 4 per source, 2 requests/second aggregate with burst 4, and a runner budget of 100 HTTP probes. These do not limit platform calls made directly.
3. Allowlist only content headers and the four native proof headers; discard inbound Authorization, unexpected headers and any client-supplied ingress header. Inject the private ingress header only toward the pinned Supabase HTTPS host; require upstream SNI, valid CA and hostname. The synthetic direct test uses no valid ingress header; valid proof or a wrong/forged ingress header cannot authorize direct traffic. The real function stays unwired and should return unavailable even if someone reaches it directly.
4. Canary egress by construction: the reviewed bundle has only a fixture transport (embedded validated PNG and synthetic OAuth response) and the pinned TLS DB connector. There is no callable outbound HTTP fallback, dynamic provider URL, or external fetch in the entrypoint’s reachable provider graph. Enforce outbound ACLs where available (proxy to the one Supabase HTTPS host; worker to approved database/platform endpoints only), with no Apple or Esri route. Supabase worker-level network fencing and visibility are **UNVERIFIED**. Verify the bundle/import graph, absence of secrets, fixture-only dispatch counters and available network evidence; if the owner requires independent network enforcement that the managed runtime cannot provide, do not deploy the canary.
5. Direct calls can still reach Supabase’s public gateway, produce metadata logs and count as invocations before the application rejects them. Even the fixed route does not prevent a caller putting arbitrary strings in a *rejected* URL. Do not test direct bypass with real coordinates or secret-looking data. Neither proxy auth nor the DB breaker caps direct-request costs. Delete the temporary functions if unexpected direct traffic persists.

## Privacy certification matrix

Create a fresh random synthetic run marker roster in protected operator memory. Use distinct values for A–I, and distinct actual proof values for positive and negative probes. Do not write those values into URLs except the intentionally harmless **A** route probe. Do not change canonical JSON to inject arbitrary keys on the positive tile; inject B in synthetic lease evidence and the exact G tile tuple in a valid canonical body. Inspect route, query, headers, body, event text, exception fields, SQL diagnostics, metric labels and exports, including JSON escaped or encoded copies of markers. Never log the search values or include them in reusable analytics queries whose text could itself be logged.

First-party raw access logging remains off. | Any accepted tile path/query contains coordinates or another sensitive value. A rejected A-only path in provider gateway metadata is expected, not a privacy failure. |
| B. Body | Distinct synthetic paid/attest evidence marker in a valid lease; separate malformed tile body to exercise parser errors. | Either value appears in any log, response, metric or export. |

| D. Native proof | A valid synthetic P-256 signature plus a different invalid proof marker. | Signature, digest, lease/request IDs or invalid proof appear in logs, response errors, metric labels or exports. | E. Unexpected header | Dedicated dummy custom header on proxy and direct probes. | Header value is forwarded by ingress, echoed or retained. |
| F. Exception | Fixture transport throws once with a unique sentinel for one preselected signed request. Confirm it executes and produces a generic 502; no deliberately uncaught test exception. | Exception text, stack containing private values, or raw provider/DB details are retained or echoed. |

## Authorization and database procedure

Before deploying, prepare a **separate** canary artifact and review its complete inventory; no such artifact or keys are created in this stage. Use the pinned gateway protocol, database state adapter and existing PNG validator. The canary entrypoint must be unmistakably separate and refuse boot unless exact pilot project ref, canary slug/origin, short absolute UTC window, and two registered synthetic P-256 public keys match. Use server-owned test verifiers: they validate server-issued one-time challenge, proof by a registered key over challenge and canonical admission binding, and map the key to server-owned test entitlement/installation/lineage and fixed short expiry. The client can supply evidence but cannot assert trusted verdicts. No genuine Apple evidence, no client flag, and no switch to enable this path in `index.ts`. The test driver keeps ephemeral private keys in memory. Require the mock-only provider call path to work with real Esri disabled and unconfigured; a fixture failure must never fall back to fetch.

The current Edge adapter hardcodes the `gridly-labels` slug, and the existing provider checks the Esri enable flag before calling its transport. Neither is a drop-in canary switch. Require a reviewed **canary-only** adapter that accepts exactly the canary slug, preserves the fixed suffix and proof origin, and injects a bounded synthetic PNG provider at the gateway seam without enabling the real adapter. Verify this separation and the denial probes locally before Stage B approval. Check the absolute expiry on each request and before fixture dispatch, including in warm isolates; boot-time expiry alone is insufficient.

After separate migration approval, from an audited scratch copy validate the explicit project and install both drafts, in order, as the isolated migration owner. With the selected project hostname, `PGSSLMODE=verify-full`, `PGSSLROOTCERT` and protected operator auth already set:

## Run order and stop conditions

1. **Before activation:** record approved project ref, Git SHA, bundle/fixture hashes, ingress hostname, named operators, timer, spend status, expected log sources, baseline counters and expiry. Inspect CLI `supabase --version` and `supabase functions deploy --help`; use the explicit approved project ref (v3: `supabase functions deploy gridly-labels --remote="$PILOT_REF"`). Never use a linked/default target, deploy-all or prune. Verify the disabled real function and direct unauthenticated denial first. Render the proxy privately, validate with `nginx -t -c "$PILOT_NGINX_CONFIG"`. Create no public canary route without the tester restriction.
2. **Transport probes:** use certificate validation and `curl --max-time 8 --path-as-is` for harmless status probes only. Confirm wrong hostname/CA fails, correct HTTPS succeeds, wrong Host/verb/path/query/encoding is refused, injected ingress header does not authorize, and slow/large bodies, throttling and disallowed sources are bounded. Test both ingress and the direct function route. Inspect proxy and platform responses for generic error bodies; require no cache or CORS headers granting access. No secret-bearing command lines.
3. **Signed sequence:** request two challenges; use the pinned [fixed POST proof](FIXED-PATH-PRIVACY.md) and the dedicated synthetic admission scope. Valid leases return 201; wrong evidence, reused challenge, expired/revoked lease, wrong key, modified body and duplicate proof must fail. For successful tiles require 200, `image/png`, `no-store`, exact fixture SHA-256 and no response sharing; verify both users incur separate reservations. Compare attempt deltas on every case. Only an accepted reservation can call the fixture; failed provider work is still debited once.
4. **Quota sequence within the cap:** expect baseline +2 valid reservations for the two independent users, +1 for the winner of a deliberately held two-request concurrency race, +1 for the injected fixture error, and optionally +1 for the worker-termination exercise. No debit for losing/denied calls. To exercise installation and then shared lineage limits, temporarily lower only the corresponding cap to its current observed nonzero count, require 429/no debit on a fresh valid request, and restore at most 20. Finally lower aggregate cap to its observed positive count, require 429/no debit, and leave the lower cap in place. This proves boundary enforcement without burning the remaining allocation. Abort if any test would need more than 20 reservations or if accounting differs from the ledger. The absolute cap remains in effect throughout; no refund, reset, or automatic retry.
5. **Shutdown:** at first unexpected response, egress, privacy marker, billing anomaly, or at T+600s: close ingress, stop the driver, disable the canary and real switches, run `select label_pilot.pilot_disable();` in the isolated database, and fence outbound traffic. Recheck direct and proxy denial and observe counters settle; do not claim an already dispatched request was recalled. Retain only a sanitized record of active slots, attempts, log matrix and artifact hashes.
6. **Recovery/cleanup:** do not clear stranded slots until old workers are demonstrably stopped and egress is fenced. As migration owner, `select label_pilot.recover_after_drain();` clears slots without refunding attempts or replay; follow with `select label_pilot.cleanup_expired();`. If quiescence is unverified, keep disabled and remove the canary. Revert proxy to closed, remove the canary and disabled function from the approved project, revoke/delete its synthetic secrets and login, remove DNS and ingress, and delete the project by the 48-hour deadline. Confirm platform retention/deletion behavior before testing; deleting the project does not prove immediate erasure from backups or provider logs. No raw export or third-party drain. Retain the sanitized report for up to 30 days for review.

Before running signed cases, repeat direct denial against the canary without the ingress proof and confirm zero database work or fixture dispatch. Do not print full URLs with markers, body data or authorization/proof headers in command transcripts.
