# LP202.2 statewide consumer crossing selector RCA

## Scope and determination

This is an observational RCA. It does **not** change selector, renderer, classification, awareness-selection, package, or synchronization semantics. The authoritative Sherman capture remains `240` governed/runtime records, `46` rendered markers, and `0` consumer-selected records.

The first bad stage is `gridlyCrossingOwnedByAwarenessArea`. For a generated Sherman PLACE area, `gridlyBuildRegistryCommunityAwarenessArea` supplies neither coordinates nor geometry because Grayson is absent from the 28-county legacy `GRIDLY_COUNTY_AWARENESS_BOUNDS_BY_ID` table and the Sherman `consumerAwarenessAreas` record has no `focus`. Meanwhile `inferCrossingCity` reads lowercase aliases but not governed `CITYNAME`, so every normalized Grayson row has `city: "Unassigned"`, not `Sherman`. `isGridlyRecordInAwarenessArea` therefore fails both its text branch and its radius branch. This is not a classification failure: all 240 records are `PUBLIC_ROADWAY`.

Root-cause classifications: **`LEGACY_AWARENESS_AREA_FILTER`**, **`LEGACY_LOCALITY_OWNERSHIP_FILTER`**, **`MISSING_RUNTIME_METADATA`**, and **`STALE_REVIEW_PACKAGE_ASSUMPTION`**.

## Intended “crossings watched” contract

LP037.1 and LP037.2 establish the phrase as the number of unique, active-county runtime crossings which satisfy production visibility/classification, reportability, and selected awareness-area geographic ownership. It is not the package total, current viewport marker count, incident count, or Route Watch count (except that the existing bottom-panel wrapper deliberately preserves its separate Route Watch override). `getGridlyBottomPanelAwarenessCrossingCount` delegates to the shared selector and uses the summary only as its established non-countywide fallback.

Accordingly, selector and renderer intentionally answer different questions. The selector is awareness-area scoped. The renderer is render-policy and viewport scoped. The defect is not that these sets differ; it is that the selector's current proof of PLACE ownership depends on legacy inline metadata which the governed statewide records and generated PLACE area do not jointly provide.

## Actual production selector trace

`gridlySelectConsumerVisibleCrossings` performs these conditions in this exact order:

1. `gridlyGetActiveCountyCrossingInventory` input and `gridlyCrossingSampleMatchesCounty`;
2. `gridlyCrossingSatisfiesConsumerVisibilityPolicy`, which calls `shouldShowCrossingInLaunchMode` and enforces `PUBLIC_ROADWAY` when classified;
3. `isGridlyReportableCrossing`;
4. `gridlyCrossingOwnedByAwarenessArea`, which delegates non-countywide areas to `isGridlyRecordInAwarenessArea`;
5. FRA ID extraction and case-insensitive de-duplication.

There is no separate locality filter after awareness ownership, no separate containment gate after the awareness helper, and no later hidden eligibility gate. Text/locality and radius geometry are alternative branches *inside* awareness ownership. The audit exposes them as conservation labels without pretending they are additional production filters.

## Renderer comparison

`getGridlyPolicyVisibleCrossings` applies reportability plus `PUBLIC_ROADWAY`, verifies active-county/inventory identity, and then applies Leaflet viewport bounds and render-mode candidate rules. Its phase called “awareness-area filtering” is only active-county ownership plus active-inventory ID membership; it does not call `gridlyCrossingOwnedByAwarenessArea` or require PLACE locality metadata. The captured Sherman viewport contains 46 eligible points, so 46 render even though the consumer selector's independent PLACE-ownership proof rejects 240/240.

Renderer membership is viewport-state dependent. This repository audit certifies the captured Sherman `46`; it does not fabricate Dallas, Liberty, or additional-control marker counts without equivalent live viewport captures. Their renderer pre-viewport eligible counts are Dallas 789, Liberty 80, El Paso 198, Bexar 380, McLennan 169, and Smith 123.

## Dallas and Liberty controls

Dallas (`dallas-tx`, selected Dallas) is positive but not fully equivalent: the explicit governed Dallas focus (`32.7767,-96.7970`) lets the legacy seven-mile radius branch retain 263 of 789. Trace: `789 → 789 county → 789 classification → 789 reportable → 263 awareness/locality-geometry → 263 deduped → 263 final`. This is healthy only as a radius approximation; it does not demonstrate PLACE polygon membership.

Liberty (`liberty-tx`, selected Liberty) retains the original-era assumptions. Classification is 80 public, 28 private, 5 industrial, 1 rail yard, and 1 temporary access. Trace: `115 → 115 county → 80 classification → 80 reportable → 25 awareness/locality-geometry → 25 deduped → 25 final`. Its explicit governed/legacy focus allows the radius branch to work.

The pattern is a statewide package/context cohort defect, not Grayson-specific and not a multi-county-PLACE-only issue.

## Statewide impact

There are 202 `ACTIVE_POSITIVE` production counties. The legacy awareness-bounds table contains 28 counties, 27 of which are active-positive. Therefore **175 active-positive counties lack that fallback** and are vulnerable to the exact Sherman zero whenever the selected PLACE also lacks an explicit focus (as Sherman, El Paso, Waco, and Tyler do). This is a conservative, reproducible cohort count, not a claim that every PLACE in every one of those counties is zero: an individually supplied `focus` (Dallas and San Antonio) can mask the defect through the radius branch.

## Smallest generic repair for owner review

Do not weaken classification or make the banner equal the viewport marker count. The smallest generic repair is to make the existing awareness-ownership owner consume current governed PLACE context: preserve `CITYNAME`/PLACE identity during normalization and/or use the governed PLACE geometry/identity resolver for `placeGeoid` containment. A coordinate-radius fallback may remain a fallback, but absence of a legacy 28-county bounds entry must not be the deciding statewide eligibility condition. Confirm the preferred identity-vs-polygon contract before implementation.

Protected systems remain untouched: Wave 3A.3, governed packages/FRA authority, LP202.1/LP202.2 synchronization, renderer and classification policy, awareness selection, Shared Reports, Route Watch, Hazard Lifecycle, Alert Generation, and Supabase.
